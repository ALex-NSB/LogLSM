# Заметки рабочей сессии — 8 июня 2026
## Тема: формат упаковки данных IMU (продолжение работы над ТЗ LogLSM)

Цель — зафиксировать достигнутый консенсус, чтобы продолжить с этого же места в следующий раз.

---

## 1. Контекст и разделение идеологий

Зафиксировано принципиальное разделение двух режимов записи (раздел 6 ТЗ):

| | Режим 1 — «Регистратор цикла вращения» | Режим 2 — «Потоковая регистрация» (Logger) |
|---|---|---|
| Идеология | Формирует ОДИН итоговый нормированный результат за рабочий период (начало–конец вращения) | Формирует поток сырых сэмплов друг за другом, непрерывно |
| Частота записей | Редко (раз в цикл) | Часто (сотни Гц, по ODR) |
| Критичность объёма | Низкая (записей мало) | Высокая (поток большой) |
| Подход к разрядности | Можно расширять без последствий | Нужна компактная упаковка |

Из этого разделения следует, что **схема с автоподстройкой масштаба нужна только для Режима 2**. Для Режима 1 экономия разрядности не имеет практического смысла.

## 2. РЕЖИМ 1 — Регистратор: новая структура записи (КОНСЕНСУС ДОСТИГНУТ)

Решение: все смысловые поля результата цикла переводятся на **единую разрядность 32 бита** — не ради точности (для температуры/батареи и 16 бит избыточны), а ради **унификации структуры**: единый код сериализации через `float32`/`uint32`, выравнивание по 4 байта, меньше особых случаев в коде.

### Итоговая структура записи (30 байт, было 20):

| Поле | Разрядность | Формат |
|---|---|---|
| Время начала цикла | 32 бита | uint32 (timestamp) |
| Время окончания цикла | 32 бита | uint32 (timestamp) |
| Длительность цикла | 32 бита | uint32 |
| MAX вибрации | 32 бита | float32 |
| MAX скорость вращения (RPM) | 32 бита | float32 |
| Температура | 32 бита | float32 (°C) |
| Напряжение батареи (НОВОЕ поле) | 32 бита | float32 (В) |
| CRC + флаг | 16 бит | служебное |

**Обоснование избыточности (просчитано количественно, признано пренебрежимым):**
- Разница "компактный вариант" (26 байт) vs "единообразный" (30 байт) = 4 байта/запись.
- В масштабе всего проекта (даже 10 000 записей за весь срок службы) — это ~40 КБ против 16 МБ Flash = ~0.0025%.
- Не влияет измеримо ни на объём хранилища, ни на время выгрузки, ни на износ Flash, ни на энергопотребление.
- Вывод: экономия здесь была бы избыточной оптимизацией с реальной ценой (сложность кода) и без измеримой выгоды. Унификация — рациональный выбор.

✅ Эта часть полностью согласована и готова к фиксации в документе.

## 3. РЕЖИМ 2 — Logger: формат блока с автомасштабированием (КОНСЕНСУС В ОСНОВНОМ ДОСТИГНУТ, остался 1 параметр)

Идея (от автора): данные хранятся в 16-битном формате, но имеют переключаемые диапазоны — аналогично добавлению разрядов, только информация о диапазоне выносится в заголовочное слово блока. Множитель диапазона переключается кратно 2 (степень двойки) ⇒ классическая схема **block floating point** (общий экспонента/масштаб на блок сэмплов).

### Согласованная схема (Вариант 1 — общий масштаб на блок):

**Заголовочное слово блока (16 бит):**
- биты [15:12] — код масштаба SCALE (4 бита → 16 значений → множитель от 2⁰ до 2¹⁵);
- биты [11:8] — флаги/режим (Low-g/High-g, ODR-код и т.п.);
- биты [7:0] — резерв / счётчик / номер блока.

**Слова данных (16 бит):** знаковая мантисса (two's complement); физическое значение = (мантисса << SCALE) × LSB_датчика.

### Алгоритм автоподстройки (АВТОВЫБОР — ключевое требование автора):
1. Сэмплы блока (N штук, по всем осям/каналам) сначала накапливаются в RAM-буфере (логгер может себе это позволить — не контур реального времени).
2. По завершении накопления ищется **пиковое по модулю значение по всему блоку, по всем осям сразу** (автор подтвердил: не нужно следить за "хвостами" слабых осей — важна именно экстремальная нагрузка, что соответствует общей идеологии проекта — событийная регистрация ударов/экстремумов).
3. SCALE = минимальное значение, при котором пик помещается в мантиссу без насыщения: `SCALE = max(0, ceil(log2(|peak| / MANTISSA_MAX)))`.
4. SCALE пишется в заголовок; все N сэмплов кодируются как `raw >> SCALE`.
5. **Гистерезис**: повышать SCALE сразу при угрозе насыщения, понижать — только при устойчивом (несколько блоков подряд) падении пика — чтобы избежать "дребезга" масштаба.
6. Поскольку масштаб выбирается по итоговому пику ВСЕГО блока (за счёт буферизации), переполнение внутри блока невозможно в принципе.

### ОТКРЫТЫЙ ВОПРОС — продолжить с этого места завтра:
**Размер блока N (количество сэмплов на одно заголовочное слово).**

Обсуждавшиеся варианты и их компромиссы:

| N (сэмплов/блок) | Доля заголовка (накладные расходы) | Задержка буферизации (при ODR=416 Гц) |
|---|---|---|
| 8 | ~11% | ~19 мс |
| 16 | ~6% | ~38 мс |
| 32 | ~3% | ~77 мс |

Вопрос для продолжения: выбрать N (рассматривались 16 или 32), возможно — с привязкой к удобству выравнивания записей и размеру страницы Flash (256 байт).
