# Сессия 05.07.2026 — «Работа» (Stop2 со сном) не будит: SYS_WKUP vs EXTI

> **КОРЕНЬ НАЙДЕН. Фикс подготовлен частично, второй (главный) — ждёт решения A/B.**
> Читать вместе с `session_notes_2026-07-04_test_mode.md` (там «Тест» 0x23).

## Симптом
«Работа» (`CMD_START_REGISTER` 0x1D, Stop2 со сном) — **«нет ответа» на ВСЕХ
циклах, любая скорость (42→300 об/мин)**, столбец «Регистратор» пуст.
Передёргивание питания не помогает (и не должно). При этом **«Тест» (0x23,
без сна) живёт** — на тех же скоростях пуши идут.

## Корень (подтверждён по коду проекта, не гипотеза)
`LOGLSMA.ioc`: `PC13.Signal=SYS_WKUP2`, `PA0.Signal=SYS_WKUP1` — оба заведены
как **PWR-wake-пины**, НЕ EXTI. `stm32l4xx_it.c` — **нет ни одного
EXTI-обработчика** (только DMA1_Channel6 + USART2).

Архитектура STM32L4 (RM0394):
> **SYS_WKUP-пины будят ТОЛЬКО Standby/Shutdown. Из Stop-режимов (Stop0/1/2)
> выход — ТОЛЬКО по EXTI-линии.**

Текущая прошивка спит в **Stop2** (`HAL_PWREx_EnterSTOP2Mode`), EXTI на PC13
нет → фронт INT1 (Wake-Up акселерометра) доходит до пина и латчит флаг WUF2,
но **ядро из Stop2 не поднимает**. Устройство спит вечно → пуша нет.

## Почему всё сходится
- **«Тест» живёт**: сна нет, код опрашивает защёлкнутый WUF2 на ходу (флаг
  латчится и в Run — EXTI не нужен). Это ДОКАЗЫВАЕТ, что электрический тракт
  INT1→PC13→WUF2 исправен — значит дело не в датчике/пороге/ODR, а в способе
  выхода из сна.
- **03.07 «417 HP работало»**: тогда PC13 был **EXTI13**. Позже пользователь
  перевёл оба входа в SYS_WKUP (задел под будущий Standby-ярус) — это и
  сломало текущий Stop2. **Пины настроены под БУДУЩИЙ Standby, а код ещё на
  Stop2 → рассинхрон. Это и есть баг.**

## Что уже сделано
- `main.c` (строка ~559): ODR акселерометра **104 Гц LP → 417 Гц HP**
  (подтверждённая точка Wake-Up; 104 LP никогда не подтверждался, низкий
  LP-ODR отфильтровывает ВЧ-вибрацию шагового мотора). **Само по себе НЕ
  лечит** — без EXTI Stop2 всё равно не проснётся. Оставлено, т.к. для
  рабочей точки 417 HP нужен в любом случае.

## Главный фикс — СДЕЛАН (путь A, 05.07.2026, ждёт проверки на железе)
Выбран путь **A** (оживить Stop2 через EXTI). Правки в LOGLSMA:
1. `main.c`, блок инициализации PC13 (USER CODE 2): `Mode = GPIO_MODE_IT_RISING`
   (было `GPIO_MODE_INPUT`) + `HAL_NVIC_SetPriority/EnableIRQ(EXTI15_10_IRQn)`.
   Теперь фронт INT1 поднимает ядро из Stop2 по EXTI13.
2. `stm32l4xx_it.c` (USER CODE 1): добавлен `EXTI15_10_IRQHandler()` →
   `HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_13)` (сбрасывает pending, callback не
   нужен — дефолтный weak пустой).
3. `main.c` ODR акселерометра — 417 Гц HP (см. выше).
Опознание источника после Stop2 НЕ менял — оставил на флагах WUF2/WUF1
(латчатся независимо, EWUP2/EWUP1 включены). SYSCFG-клок для EXTI включён
(`stm32l4xx_hal_msp.c:69`) — проверено.

Минимализм осознанный: PA0/WKUP1 в EXTI0 НЕ переводил — фронт кабеля во сне
не критичен (основной стоп — CMD_STOP_REGISTER 0x22 в бодрой фазе). Если
понадобится будить Stop2 подключением кабеля — добавить EXTI0 тем же
паттерном.

**СЛЕДУЮЩИЙ ШАГ: перешить A, запустить «Работа» на стенде.** Ждём: столбец
«Регистратор» заполняется пушами (WKUP2→CONFIRM→ROTATING→пуш вживую из
реального Stop2). Если пошло — автономный режим со сном подтверждён.

## Путь B (на будущее, НЕ делали)
Настоящий **Standby-ярус** (`HAL_PWREx_EnterSTANDBYMode` + восстановление
после reset через backup-регистры / Flash-stub, перенос `reset.c` из
rp_device). Тогда SYS_WKUP корректен, EXTI не нужен, но ОЗУ теряется при
пробуждении. Следующий крупный проход после подтверждения Stop2.

## NB на будущее (не потерять)
Когда/если пойдём в Standby (путь B) — конфликт снимется сам: SYS_WKUP там
единственно верный, EXTI не работает в Standby. То есть текущий SYS_WKUP в
.ioc — НЕ ошибка, а преждевременная настройка под ещё не реализованный ярус.
Для интерим-Stop2 её надо дополнить EXTI (путь A), не убирать.

## ⚠ Регрессия EXTI и её фикс (05.07.2026, вечер)
Первый вариант EXTI13 включал `EXTI15_10_IRQn` ГЛОБАЛЬНО из init. Итог: INT1
(движение/Wake-Up) сыпал прерывания в бодрый путь ПОСТОЯННО → переставали
отвечать и «Тест», и Flash, хотя МК не спит (устройство на связи —
WHO_AM_I проходил, но FLASH_READ и пуши в таймаут). Передёргивание питания
временно оживляло (INT1 без движения молчит).

**Фикс (правильный паттерн для wake-only прерывания):** EXTI15_10 НЕ включаем
глобально — только `HAL_NVIC_EnableIRQ` прямо перед `EnterSTOP2Mode` (с чистого
pending: `__HAL_GPIO_EXTI_CLEAR_IT` + `HAL_NVIC_ClearPendingIRQ`), и
`HAL_NVIC_DisableIRQ` сразу после пробуждения. Вне сна EXTI выключен → бодрый
путь (Тест/Service/Flash) чист. `HAL_NVIC_SetPriority` остаётся в init.

Урок: прерывание, нужное ТОЛЬКО для выхода из сна, нельзя держать включённым
в рабочем цикле — оно конкурирует с UART/Flash. Включать точечно вокруг сна.

## СОСТОЯНИЕ НА КОНЕЦ СЕССИИ 05.07 + план на новую сессию

**Перешить A** (самой свежей версией `main.c`+`it.c`):
- ODR акселерометра 417 Гц HP;
- EXTI13 **wake-only**: в init только `HAL_NVIC_SetPriority` (НЕ Enable);
  `Enable`+чистка pending прямо перед `EnterSTOP2Mode`, `Disable` сразу после
  пробуждения. Вне сна EXTI выключен (иначе шторм INT1 глушит UART/Flash/Тест);
- Stop2-ветка: убран ложный «стоп по WUF1» (кабель держит WKUP1 в HIGH),
  зависимости от WUF2 нет — любой выход из Stop2 = движение → CONFIRM.

**Пересобрать W**: «Флеш» (заголовок), бар — текст вправо (`setAlignment`),
явное состояние «Flash не отвечает / устройство спит» вместо застывшего бара.

**ЧИСТАЯ процедура проверки (порядок критичен!):**
1. Перешить A свежим кодом.
2. Переподключить порт в LOGLSMW (SWD-сброс роняет VCP → нужен свежий PING;
   старый зелёный «Регистратор» может быть устаревшим).
3. Запустить **«Тест» ПЕРВЫМ**, БЕЗ «Работы». Ждём: пуши идут = база жива.
   - Тест молчит даже так → **откатить** firmware-изменения (EXTI+ODR) к
     последней рабочей версии (session_notes_2026-07-04), вернуть базовый Тест,
     Stop2 брать с нуля.
4. Только если Тест ожил → проверять «Работу».

**⚠ КЛЮЧЕВОЙ ВЫВОД:** «Работа» надёжно оставляет устройство застрявшим в
Stop2 — входит в сон и НЕ выходит даже с EXTI13 (после Работы даже PING/0x23
таймаутят: спящий МК глух к UART; «Тест» после «Работы» молчит именно
поэтому, сам Тест исправен). Значит корень — **сам вход/выход Stop2**
(восстановление клока/I2C после сна) ЛИБО EXTI13 реально не поднимает ядро.
Следующий заход: (1) в лоб отладить вход/выход Stop2, либо (2) перейти на
**Standby-ярус** (восстановление через reset — чище, SYS_WKUP там корректен).

Принципы пользователя (не нарушать): диагностика только рассуждением, без
осциллографа/тестеров; никаких обесточиваний как ШТАТНОГО механизма (SWD/reset
в dev-цикле — можно, это не полевое обесточивание).

## 🐛 БАГ СТЕНДА: мотор крутится сам на подключении — коллизия кодов на общей линии (05.07.2026)

**Симптом:** при подключении LOGLSMW мотор стенда начинал вращаться сам, без
команд. «Раньше не было».

**Корень:** `Stend/Stend LOGLSM/Core/Src/com_interr.c`:
- `HAL_UARTEx_RxEventCallback` скармливает КАЖДЫЙ байт от ПК И в `relay_pc_byte`,
  И в `ltp_parser_feed` (свой парсер стенда) — т.е. парсер стенда видит и
  пакеты, адресованные РЕГИСТРАТОРУ (0x8D), которые лишь ретранслируются;
- `handleCmd()` исполнял команду по `lp.pkt.cmd` **не проверяя `lp.pkt.addr`**;
- коды стенда `CMD_START/SPEED/STOP` = **0x04/0x05/0x06** численно совпадают с
  флеш-командами регистратора (`FLASH_READ_ID/ERASE/PAGE_ERASE`);
- при `CMD_SPEED`(0x05) payload флеш-адреса читается как «скорость» →
  `StepDriverSetSpeed(мусор)` → мотор крутится.

**Триггер именно сейчас:** в этой сессии добавлено **авто-чтение флеша/архива
при подключении** (`probeFlashImageState`/`flashBinSearchStart`/
`archiveRescanFull` в onLinkUp) — эти флеш-команды к 0x8D пошли через релей
стенда и «просветили» баг. Раньше на подключении их не слали → не проявлялось.
Баг латентный, существовал всегда (ADDR никогда не проверялся).

**Фикс (сделан):** в начале `handleCmd()` —
`if (lp.pkt.addr != LTP_OWN_ADDR) return;` — стенд исполняет ТОЛЬКО пакеты на
свой адрес 0x8C, релей регистратору (0x8D) игнорирует. **Требует перепрошивки
СТЕНДА (Nucleo-L476)**, не регистратора.

**Урок:** на общей линии с ретрансляцией по ADDR — обработчик команд ОБЯЗАН
проверять адрес назначения, даже если «коды у разных устройств разные»
(коллизия кодов + отсутствие проверки ADDR = чужие команды исполняются).
