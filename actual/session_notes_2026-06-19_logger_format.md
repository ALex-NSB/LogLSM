# Сессия 19 июня 2026 — Формат упаковки данных Logger

## Статус: завершено, перенесено в `data_format_spec_v1.md` (раздел Logger v2)

---

## Зафиксированные термины

| Термин | Размер | Что это |
|---|---|---|
| **Сэмпл** | 12 байт | Ax/Ay/Az/Gx/Gy/Gz — 6 каналов × 16 бит |
| **Фрейм** | 256 байт | = 1 страница Flash, типизированный контейнер |
| **Цикл** | N фреймов | Данные одного рабочего цикла (движение началось → закончилось) |

---

## Базовый принцип

**Байт [0] каждого фрейма = тип.** `0xFF` = чистая память (NOR Flash default),
любое другое значение — фрейм с данными. Фреймы пишутся строго вперёд, без
возврата: 1 фрейм = 1 страница, либо страница записана полностью, либо переходим
к следующей.

Биться за битовую кодировку байта типа не стали — сравнение байта с маской и
сравнение байта на равенство константе практически равноценны по стоимости,
поэтому типы — это просто линейный список из 10 фиксированных констант, без
смысловой нагрузки в отдельных битах.

---

## Финальный список типов фреймов

| Байт | Тип | Назначение |
|---|---|---|
| `0xFF` | чистая память | не фрейм, конец записанных данных |
| `0xFE` | ЗАГОЛОВОК | полные метаданные начала цикла (вариант «не экономим страницу») |
| `0xFD` | ДАННЫЕ | обычный фрейм сэмплов |
| `0xFC` | СТАРТ+Д+T0 | сэмплы + старшая часть часов на старте цикла (экономия страницы) |
| `0xFB` | СТАРТ+Д+T1 | сэмплы + младшая часть часов на старте цикла |
| `0xFA` | ДАННЫЕ+E1 | сэмплы + температура+статус батареи (периодическое обновление, 2 байта) |
| `0xF9` | *свободно* | освобождено 19.06.2026 объединением E1/E2 (см. ниже) |
| `0xF8` | ДАННЫЕ+E3 | сэмплы + старшая часть часов в момент записи (чекпойнт восстановления) |
| `0xF7` | ДАННЫЕ+E4 | сэмплы + младшая часть часов в момент записи (чекпойнт восстановления) |
| `0xF6` | СТОП | штатное завершение цикла: точная длительность + накопительный итог |

Цикл начинается одним из двух способов:
```
Вариант А (полные метаданные):     [0xFE] [0xFD] [0xFD] ...
Вариант Б (экономия страницы):     [0xFC] [0xFB] [0xFD] [0xFD] ...
```
Выбор варианта — по ситуации (где выгоднее), формат это не ограничивает.

## Layout фреймов

### ЗАГОЛОВОК (`0xFE`)
```
[0]       0xFE
[1..4]    unix timestamp начала цикла (uint32) — здесь помещается целиком,
          т.к. фрейм не делит место с сэмплами
[5]       температура (uint8, целый °C, смещение −60: °C = raw − 60, диапазон −60…195)
[6]       status (uint8: биты[2:0] = voltage_zone, биты[7:3] резерв)
[7]       тип датчика (0 = DSO/вариант A, 1 = DSV/вариант B)
[8]       ODR-байт: показатель степени относительно ODR_base
[9]       FS-байт: AccelExp[2:0] | GyroExp[2:0]
[10..255] 0xFF резерв (новые поля добавляются последовательно сюда)
```
Структура фиксированная, поля в строго заданном порядке, без вариаций.
Поля temperature/status — единая 2-байтовая упаковка, общая с ДАННЫЕ+E1 и с
Регистратором v2 (см. ниже и `session_notes_2026-06-19_registrator_format.md`).

### ДАННЫЕ (`0xFD`)
```
[0]        0xFD
[1]        FS-байт: AccelExp[2:0] | GyroExp[2:0]
[2..253]   до 21 сэмпла × 12 = 252 байта
[254..255] 0xFF резерв (или занято в вариантах ДАННЫЕ+E)
```

### СТАРТ+Д+T0 / СТАРТ+Д+T1 (`0xFC` / `0xFB`)
```
[0]        0xFC или 0xFB
[1]        FS-байт
[2..3]     T0 (старшая часть часов старта) или T1 (младшая часть)
[4..251]   до 20 сэмплов × 12 = 240 байт (1 сэмпл отдан под экономию страницы)
[252..255] 0xFF резерв
```
T0 и T1 — части одного и того же 32-битного значения часов (RTC/unix timestamp),
снятого в момент старта цикла. Та же кодировка, что у E3/E4 (см. ниже) — только
момент снятия другой.

### ДАННЫЕ+E1 / ДАННЫЕ+E3 / ДАННЫЕ+E4 (`0xFA`/`0xF8`/`0xF7`)
```
[0]        тип (один из E1, E3, E4)
[1]        FS-байт
[2..253]   до 21 сэмпла × 12 = 252 байта (сэмпл не теряется — занимаем штатный резерв)
[254..255] значение E (формат зависит от типа, см. ниже)
```
- **E1** — температура+статус батареи: `[254] temperature (uint8, целый °C,
  смещение −60, диапазон −60…195)`, `[255] status (uint8: биты[2:0] =
  voltage_zone, биты[7:3] резерв)` — тот же формат, что в ЗАГОЛОВКЕ
- **E3** — старшая часть часов (тот же источник и формат, что T0)
- **E4** — младшая часть часов (тот же источник и формат, что T1)

**Объединение E1+E2 (согласовано 19.06.2026).** Раньше E1 нёс только
температуру (int16, 0.01°C), E2 — только напряжение батареи (uint16, мВ) —
два типа фрейма на два диагностических поля. После пересмотра упаковки в
Регистраторе v2 (temperature → uint8 целый °C со смещением, напряжение →
3-битная зона `voltage_zone`) оба значения укладываются в те же 2 байта
вместе — тип E2 не нужен, константа `0xF9` освобождена. Один код
сериализации temp+status общий для ЗАГОЛОВКА, E1 и Регистратора v2.

Назначение E1/E3/E4: не диагностика, а чекпойнты для восстановления после сбоя/
сброса/потери питания — последний успешно записанный ДАННЫЕ+E восстанавливает
последнее известное состояние без необходимости штатного завершения цикла.
Длительность цикла как таковая через E3/E4 не считается — это просто
периодический снимок часов, разница вычисляется на ПК при разборе, если нужно
оценить, до какого момента дошла запись при аварийном обрыве.

### СТОП (`0xF6`)
```
[0]        0xF6
[1]        FS-байт
[2..241]   20 сэмплов × 12 = 240 байт (1 сэмпл отдан под доп. данные)
[242..245] длительность текущего цикла (uint32, секунды)
[246..249] суммарная длительность по всем циклам устройства (uint32, секунды)
[250..255] 0xFF резерв
```
Пишется только при штатном (не аварийном) завершении цикла — в этот момент ОЗУ
не теряется, поэтому можно посчитать точную длительность = часы_стоп − часы_старт
и записать готовое число, а не реконструировать его на ПК. Суммарная
длительность — накопительный счётчик, который прошивка ведёт постоянно
(к предыдущему накопленному значению прибавляется длительность текущего цикла);
позволяет, прочитав последнюю запись на Flash, сразу получить суммарный
наработанный ресурс устройства без сканирования всей истории.

## Масштабирование — аппаратный auto-range

IMU сам переключает Full Scale (FS) диапазон — аппаратный аналог block floating
point, программное масштабирование не нужно.

Поскольку все шаги изменения чувствительности (и accel, и gyro) кратны 2,
байт FS хранит не код из таблицы, а сам показатель степени (экспоненту)
относительно базового диапазона:
```
FS-байт: AccelExp[2:0] | GyroExp[2:0]   — 6 бит заняты, 2 бита резерв
LSB_actual = LSB_base(датчик, канал) × 2^Exp
```
`LSB_base` — по одной константе на акселерометр и на гироскоп, отдельно для
DSO и для DSV (4 числа всего, берутся из даташита каждого датчика — не
табулированы в этом документе, см. TODO).

ODR-байт в ЗАГОЛОВКЕ кодируется тем же способом: `ODR = ODR_base × 2^Exp`
(у LSM6DSO 8 ступеней ODR — ровно 3 бита под экспоненту).

## Конец данных в последнем фрейме цикла

Парсер читает сэмплы, пока не встретит 12 байт `0xFF` подряд — это конец данных
в данном фрейме. Если реальный сэмпл оказался бы всё 0xFF (коллизия с
сентинелом), firmware вычитает 1 из любого канала перед записью этого сэмпла.

## Расширяемость

- Байты [254..255] в ДАННЫЕ-фреймах (или [242..249] в СТОП, [2..3] в СТАРТ) —
  единый механизм «компактного приложения» доп. инфы к фрейму сэмплов без
  затрат отдельной страницы; какую величину несёт фрейм — определяет сам
  байт TYPE.
- Список типов открыт для расширения — свободные константы: `0xF9`
  (освобождена объединением E1+E2) и `0xF5` (следующая после текущего списка).

## На будущее (не входит в формат данных, отдельная тема)

**USB MSD-эмуляция + переключение в VCP.** При подключении по USB устройство
может представляться как флеш-накопитель (Mass Storage) с минимальным
синтетическим FAT («FAT без FAT» — структуры boot sector/root dir/FAT-таблицы
генерируются на лету, без настоящей файловой системы, поскольку раскладка
данных в нашем формате полностью фиксирована и предсказуема). Это даёт один
виртуальный read-only файл, отражающий уже записанные фреймы; имя файла может
включать суммарную длительность из последнего СТОП-фрейма — мгновенно видимый
результат без запуска LOGLSMW. По специальной команде устройство переключается
в обычный VCP (Virtual COM Port) для штатной работы по LTP. Требует отдельной
проработки на будущей сессии (зависит от формата данных, но не меняет его).
