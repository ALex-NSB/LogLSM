## 1. Firmware/LOGLSMA/App/Src/Data.c — запись во Flash реализована

**`SaveParamOnEEPROM`**: была `return HAL_OK;` без действий. Теперь пишет
24-байтную запись на цикл:

```
[0..3]   tsStart       uint32  секунды с 2000-01-01 (см. rtcToSec())
[4..7]   duration      uint32  длительность цикла, с
[8..11]  durationTotal uint32  суммарная наработка (totalSec), с
[12..15] maxVibro      float   максимальная вибрация — ПОКА ВСЕГДА 0.0,
                                акселерометр не подключён к подсчёту
[16..19] maxRpm        float   максимальная скорость, об/мин
[20..21] reserved      0x0000
[22..23] crc16         CRC16-CCITT по байтам 0..21 (ltp_crc16)
```

Раскладка: страница 0 = заголовок устройства (не трогается), лог начинается
со страницы 1 (`LOG_START_PAGE`), 10 записей на страницу
(`RECORDS_PER_PAGE`, 24×10=240 из 256 байт).

**`flashFindWritePos()`** — линейный скан страниц при первом обращении:
читает первые 4 байта каждой страницы (0xFFFFFFFF = страница пуста), если
страница не пуста — ищет первый пустой слот внутри неё. Это **линейный**,
не двоичный поиск (отличается от алгоритма LOGLSMW ниже — решают разные
задачи: здесь ищем позицию для следующей ЗАПИСИ при заведомо небольшом
количестве уже занятых страниц, там — границу для ЧТЕНИЯ по всему чипу).
Курсор кэшируется в статиках `s_writePage`/`s_writeSlot`, повторный полный
скан не требуется до следующей перезагрузки МК.

**`LoadTotalSec`/`SaveTotalSec` реализованы**: `SaveTotalSec` — no-op
(totalSec и так пишется в каждую запись, поле `durationTotal`).
`LoadTotalSec` находит последнюю записанную запись (по курсору
`flashFindWritePos`), проверяет CRC16 — при несовпадении (старый формат без
CRC либо повреждение) откатывается на `totalSec=0` (безопасный fallback),
иначе восстанавливает `r->totalSec` из байт [8..11]. Закрывает пробел,
отмеченный 30.06: раньше `totalSec` сбрасывался в 0 при каждой перезагрузке
МК.

**`Poll_Sensor`**: цикл сэмплирования уменьшен с 10 до 3 итераций —
комментарий в коде: «3 samples x 80 ms (ODR=12.5 Hz) = 240 ms per call»
(было 800 мс блокировки за вызов). Причина — не дать `ComPoll()` голодать
во время блокирующего опроса DRDY.

## 2. Firmware/LOGLSMA/App/Src/com.c — правки вокруг Service()/Flash

- **Новая команда 0x21 `CMD_RESET_TOTAL`** (`cmdResetTotal`) добавлена в
  таблицу `CMD[]`. Обнуляет `s_reg->totalSec` и `state` по запросу с ПК.
  ⚠️ **Комментарий в коде говорит, что LOGLSMW её больше не вызывает** —
  раньше вызывалась при «Старт» циклограммы стенда, теперь «Сессия»
  считается как дельта на стороне ПК (`m_lastRegTotS - m_preTestRegTotS`),
  а `totalSec` в прошивке остаётся lifetime-счётчиком и не обнуляется.
  Команда, получается, реализована, но с ПК не вызывается — **не разобрано,
  сознательный ли это задел на будущее или забытый недоделанный откат**,
  стоит уточнить у пользователя при следующей сессии.
- `Service()`: добавлен статический флаг `s_flash_on`, разделяемый с
  `cmdFlashOn()` — исключает повторный `flashActiv()` (в QPI-режиме второй
  вызов давал таймаут QUADSPI 5–16 с). `LoadTotalSec(r)` теперь вызывается
  при входе в `Service()`. `s_reg = r` сохраняется, чтобы `cmdResetTotal`
  (вызывается из callback без прямого доступа к `r`) мог его найти.
- **GET_STATS (`cmdGetStats`)** — поле `total_sec` теперь реальное значение
  из `s_reg->totalSec`, остальные поля (`ts_first`, `ts_last`,
  `ts_activation`, `restarts_timer/power`) остаются заглушками (0xFF/0x00),
  как и раньше — не тронуты в этой сессии.
- Фиксы DMA/UART устойчивости: убран/переработан рестарт circular DMA
  (предотвращает порчу `prevFill`), `HAL_UARTEx_RxEventCallback` обрабатывает
  wrap-around по кольцевому буферу, `HAL_UART_ErrorCallback` сбрасывает
  парсер + принудительно ставит `RxState=READY` + гасит DMA half-transfer
  IRQ при ORE/framing после переподключения VCP.

## 3. SoftWare/LOGLSMW/mainwindow.cpp/h — три новых куска

### a) Заполнение колонки «Регистратор» (`stendFillRegColumn`)

Разбирает payload CMD_CYCLE_PUSH (16 байт: RTC_DateTime + duration_s u32 +
total_s u32 + max_rpm u16). Сопоставление — **позиционное, не по
времени**: берётся первая запись в `m_stend.history`, у которой
`!hasRegData && !inProgress` (ещё идущие циклы намеренно пропускаются —
иначе «хвост» push от затухающего предыдущего цикла попал бы в только что
начатый следующий и испортил бы длительность).

`totalRegS` **не берётся** из `total_s` прошивки напрямую — пересчитывается
как накопительная сумма `durationRegS` по всем предыдущим записям с данными
в истории. Причина (см. комментарий в коде): `total_s` прошивки включает
тормозные хвосты мотора во время пауз между стенд-циклами, которые
LOGLSMW отбрасывает — прямое использование дало бы растущее смещение.

Каждый пуш логируется в общий лог: `"Рег.пуш: durS=%1с totS=%2с → циклN
/отброшен"` — удобно для диагностики матчинга.

Новые поля `StendCycleRecord` (mainwindow.h): `hasRegData`, `startReg`,
`speedReg`, `durationRegS`, `totalRegS`.

`stendRenderReport()` дополнен веткой «обе колонки + дельта» — показывает
Старт/Стоп только если год RTC регистратора ≥2020 (иначе часы не
синхронизированы после прошивки), считает дельту интервала/общей/скорости
(в % для скорости).

### b) Двоичный поиск первой свободной страницы Flash

`flashBinSearchStart/SendNext/HandlePage/UpdateUi` (mainwindow.h/.cpp) —
реализация пункта из TZ_LOGLSMW_v2 §10 / «Идеи на будущее» в CLAUDE.md,
до этой сессии не существовавшая. `lo=1` (`kLogStartPage`), `hi=65536`
(sentinel = «чип заполнен», = P25Q128H: 16 МБ / 256 Б = 65536 страниц),
до ~16 запросов FLASH_READ (log2(65536)). Страница считается свободной,
только если **все** 256 байт читаются как 0xFF (не только первые 4, в
отличие от `flashFindWritePos` в прошивке — там читаются только первые 4
байта заголовка записи, здесь — полная страница, задачи разные).

Триггеры запуска: переключение на вкладку «Тест памяти»/«Данные» (строки
~1203/1209 mainwindow.cpp), после успешного стирания чипа/образа
(`archiveRescanFull(); probeFlashImageState(); flashBinSearchStart();`),
и повторная попытка через 1500 мс при таймауте/неудаче.

UI: новый `QGroupBox groupFlashStat` (mainwindow.ui) с `QProgressBar
barFlashMem` (% занятости) и `QLabel lblFlashDetail` (текст — первая
свободная страница / «чип заполнен» / «нет ответа Flash»).

Закрывает TODO из CLAUDE.md «Известные ограничения»/«Идеи на будущее»:
«Прочитать» не видит реальные данные устройства + «Образ: страниц/начало»
— индикаторы теперь считаются независимо от того, как данные попали в
Flash (тестовая запись сессии или реальная работа в поле).

### c) Панель «Память устройства» (`lblFlashStat`, `stendUpdateFlashStat`)

Новая HTML-табличка (Общее / Сессия / Циклов):
- **Общее** — lifetime-наработка устройства, `m_lastRegTotS` (из
  CMD_CYCLE_PUSH.total_s или GET_STATS).
- **Сессия** — `m_lastRegTotS - m_preTestRegTotS` (снапшот наработки на

- **Циклов** — `m_pushCount`, число полученных CMD_CYCLE_PUSH в текущей
  сессии.

Новые поля MainWindow: `m_lastRegTotS`, `m_preTestRegTotS`, `m_pushCount`,
`m_sessStendAcc`/`m_sessRegAcc` (сессионные аккумуляторы для «Общей» —
без них счётчик сбрасывался бы к нулю при сдвиге 4-циклового окна

## Баг: FLASH_READ (cmd 0x07) не отвечает никогда — НЕ РЕШЁН, отложен

Обнаружен при попытке проверить реальную запись во Flash (см. раздел 1) на
живом железе через вкладку «Тест памяти»: WRITE (0x08) стабильно работает
(«Запись OK» ×N), а READ (0x07) — **систематически не получает ответа**,
таймаут+5 повторов, «Flash: нет ответа после 5 попыток», в 100% попыток.

**Проверено и исключено:**
- **Конкуренция трафика со стендом.** Флаг `m_stendActive`-гейт для
  `flashBinSearch` уже существовал (см. выше), но проверили и ручное
  «Чтение» — таймаут воспроизводится и при полностью остановленном стенде
  (мотор стоит, циклограмма выключена). Не в этом дело.
- **Зависание всей прошивки.** Опровергнуто дважды: (1) во время таймаутов
  0x07 продолжают исправно приходить unsolicited CMD_CYCLE_PUSH от
  регистратора (BENCH-режим) — то есть основной цикл `Service()` жив и
  работает; (2) FLASH_ON (0x0E), WHO_AM_I, GET_STATS отвечают **всегда и
  сразу**, в том числе непосредственно перед очередным зависшим 0x07. Раз
  FLASH_ON успешно возвращается, вся QSPI/QPI-инициализация
  (`flashActiv()`→`P25Qx_Init`→`P25Qx_SetQPI`) точно отрабатывает и не виснет
  — проблема локализована именно в обработчике чтения
  (`cmdFlashReadHandler`→`cmdReadMem`→`P25Qx_QPI_Read`), не раньше.
- **Dummy-циклы Fast Read (0x0B) в QPI-режиме.** Первая правка сессии
  (10→8, по догадке) не помогла. Найден локальный даташит
  (`Components/P25Q128H (2023).pdf`, §10.22 «Set Read Parameters C0h»,
  стр. 55) — точная таблица P5-P4: `00→10, 01→4 (POWER-UP DEFAULT), 10→6,
  11→8`. `P25Qx_SetQPI()` никогда не отправляет команду C0h (блок с ней
  закомментирован) — регистр остаётся на заводском значении, это **4**, не
  8. Исправлено на 4 (`p25q128.c::P25Qx_QPI_Read`, ветка `qpi_mode`) —
  **тоже не помогло**, чтение всё равно не отвечает вообще (не «мусорные
  данные», а полное молчание — что вообще-то нехарактерно для чисто
  фазового сдвига дискретизации, наводит на мысль, что дело не только/не
  столько в dummy-циклах).
- **Регрессия последних дней.** Сравнили `p25q128.c` с архивом проекта за
  30.06.2026 (`LogLSM_3006.rar`, пользователь предоставил) —
  **код идентичен** (то же `dummy=10`, без изменений с 18.06 по git log,
  см. предыдущую сессию). То есть баг не свежий — похоже, реальное чтение
  по QPI никогда раньше не проверялось на живом железе, просто не было
  повода. Единственное реальное отличие в `com.c` с 30.06 — `Service()`
  теперь сама вызывает `flashActiv()` сразу на входе (раньше — только по
  явной команде FLASH_ON с ПК), из-за необходимости реальной записи
  (см. раздел 1). На сам код чтения это не влияет, но меняет момент
  перехода чипа в QPI.

**Не проверено (отложено пользователем 02.07 вечером):**
- Живая отладка под CubeIDE (breakpoint на `cmdFlashReadHandler`,
  проверка возврата `HAL_QSPI_Command`/`HAL_QSPI_Receive` — HAL_OK или
  HAL_TIMEOUT/HAL_ERROR). Пользователь говорит, что пробовал отладчик
  раньше («много было различных вариаций»), но не помнит результат — не
  зафиксирован нигде. Стоит переделать целенаправленно именно под этот
  баг, с чистого состояния.
- Явная отправка Set Read Parameters (C0h) вместо расчёта на
  заводское значение по умолчанию — сейчас код полагается на то, что
  регистр не сбрасывается при переключении SPI→QPI (датащит явно
  предупреждает: «Whenever the device is switched from Standard SPI mode
  to QPI mode, the number of dummy clocks should be set again» — то есть
  предположение о сохранении дефолта в 4 dummy-цикла зафиксировано, но не
  на 100% гарантировано датащитом дословно). Раскомментировать и
  реализовать в `P25Qx_SetQPI()`, синхронно поменять dummy в
  `P25Qx_QPI_Read` — не сделано, отложено.

**Побочное наблюдение по вкладке «Стенд»:** пока шла эта диагностика,
колонка «Регистратор» в `cmpReport` иногда заполнялась явно
бессмысленными значениями (напр. −41 секунда / −56.7% в одной строке) —
похоже на позиционный матчинг `stendFillRegColumn` с «чужим»/устаревшим
CMD_CYCLE_PUSH, а не на баг самой функции матчинга (код
`stendFillRegColumn` перечитан — логика `best = первый !hasRegData &&
!inProgress` выглядит корректно, `hasRegData` нигде не сбрасывается
обратно). Не расследовано до конца, вероятно тот же корень (нестабильность
чего-то вокруг Flash-транзакций), либо отдельная проблема — не приоритет
до решения основного бага чтения.

**Важное уточнение (после отправки на паузу, тем же вечером) — смена
направления поиска.** Сравнили `p25q128.c` с `rp_device/Core/Src/p25q128.c`
(старый прототип на протоколе WAKE, до перехода на LTP) — файл **побайтово
идентичен**, включая dummy=10 в ветке `qpi_mode` у `P25Qx_QPI_Read`.
Пользователь подтвердил: на rp_device чтение Flash по QPI **реально
тестировалось** (запись байтов в область → чтение той же области → сверка
— совпадало) и работало нормально, именно с dummy=10. Это прямое
свидетельство, что dummy-циклы (10/8/4 — перебраны все три версии в ходе
этой сессии) **не являются причиной** текущего бага — драйвер Flash сам по
себе рабочий, баг нужно искать в LTP-слое (`com.c` командный диспетчер,
`ltp.c` сборка/разбор пакета, `sendPacket`), который появился поверх этого
же Flash-драйвера при миграции с WAKE на LTP и которого в rp_device не
было вообще (там `WakeContext`, не `LtpPacket`).

**Правка дозакрыта:** `p25q128.c::P25Qx_QPI_Read` dummy **откачен обратно
на 10** (исходное значение, совпадающее с подтверждённо рабочим
rp_device) — менять его дальше нет оснований, играть допустимо было бы
только доказательными, а не любыми, значениями.

**РЕШЕНО (02.07.2026, поздний вечер) — найдена и исправлена настоящая причина.**

Диагностика жёстко зашитыми сырыми LTP-байтами через PowerShell-скрипт
напрямую на COM-порт (в обход LOGLSMW — `test_flashread_debug.ps1`/`.bat`
в корне репозитория), сначала на LOGLSMA (случайно — CubeIDE залил её
вместо TEST_PING из-за старой launch-конфигурации, что само по себе стало
подсказкой), показала: FLASH_READ (0x07) **отвечает корректно на любой
size вплоть до 240**, а начиная с **size=250 ответ систематически
обрывается** — приходит только "хвост" пакета, причём число долетевших
байт растёт линейно 1-в-1 с size сверх порога (250→5 байт, 254→9, 255→10,
256→11). Это не было заметно раньше, т.к. все предыдущие ручные тесты
(включая PING/WHO_AM_I/FLASH_ON/GET_STATS) гоняли маленькие payload'ы —
только LOGLSMW систематически запрашивает целую страницу (256 байт),
поэтому баг и выглядел как "FLASH_READ вообще не отвечает".

**Причина**: `sendPacket()`/`sendError()` (`com.c`) слали готовый LTP-ответ
одним блокирующим `HAL_UART_Transmit()` за раз. На 921600 бод без
аппаратного flow control (`HwFlowCtl=UART_HWCONTROL_NONE`, `usart.c`)
внутренний буфер USB-UART моста не успевает сливать данные по USB при
непрерывной передаче куска длиннее ~250 байт и роняет середину потока —
классическое поведение дешёвых USB-serial мостов на высокой скорости без
flow control. Дальше проверки не задокументированы — граница была нащупана
бисекцией (16→32→64→128→200 — работает; 224→240 — работает; 250 —
ломается), устраивает как объяснение, отдельно не подтверждали
осциллографом/анализатором USB.

**Исправлено** (`com.c`, новая функция `UartTransmitChunked()`):
`sendPacket`/`sendError` теперь шлют `TxBuf` кусками по 64 байта с паузой
`HAL_Delay(2)` между кусками вместо одного большого `HAL_UART_Transmit`.
Протокол LTP не менялся (та же последовательность байт на линии, просто
пришедшая с паузами) — изменений на стороне LOGLSMW не потребовалось.

**Подтверждено на реальном железе**: после перешивки A вкладка «Тест
памяти» → «Чтение» реально читает страницы (лог: «Чтение 256 байт: совпало
с 0x00» ×N, счётчики Страниц/Старт/Циклов идут корректно, остановка по
кнопке работает).

**Побочные важные находки этой ветки диагностики (не выбрасывать):**
- `Firmware/TEST_PING/` (старый debug-проект на чистом UART без периферии,
  `com.c` содержит `dbg_print()`-инфраструктуру и heartbeat) — полезный
  задел для будущей диагностики, но baudrate был на 115200 (переведён на
  921600 в этой сессии, `usart.c`), и в нём же был добавлен, но так и не
  использован реально, диагностический вариант `cmdFlashOn`/`cmdReadMem`
  с маркерами `[DBG]` на каждом шаге — можно пригодиться позже, если
  всплывёт другой Read-подобный баг.
- В `Firmware/TEST_PING/App/Src/com.c::cmdFlashOn` был задокументирован
  ДРУГОЙ реальный баг (не связанный с текущим): повторная инициализация
  Flash, когда чип уже в QPI-режиме с прошлой сессии, подвешивает QUADSPI
  на 5–16 секунд (SPI-детект не понимает QPI-only чип). В LOGLSMA это
  обходится флагом `s_flash_on` (не переинициализировать повторно) — актуально
  держать в уме при любых будущих изменениях порядка `flashActiv()`.
- CubeIDE: Build с галочкой на нужном проекте **не гарантирует**, что Debug/Run
  зальёт именно его — есть отдельная launch-конфигурация (в этом случае
  осталась "LOGLSMA" по умолчанию), которая определяет, что реально
  прошивается. Проверять по консоли Debug/Download, какое имя `.elf` там
  фигурирует, а не по диалогу Build.
- `test_flashread_debug.ps1` — рабочий, оставлен в репозитории
  (`D:\...\LogLSM\test_flashread_debug.ps1`/`.bat`). Функции
  `Build-LtpPacket`/`Get-Ltp16Crc` внутри него **считают CRC неверно**
  (проверено — расходится с Python-реализацией того же алгоритма и с
  реальным рабочим ACK-вектором), поэтому реальная отправка в скрипте идёт
  жёстко зашитыми байтами, посчитанными отдельно в Python. Причина
  расхождения PowerShell-версии не найдена и не разбиралась — если скрипт
  понадобится для новых size/adr, пересчитывать байты через Python
  (см. код в истории чата), не через встроенные PS-функции.

**Баг в `stendJournalWrite()` (файл журнала на диске): колонка дельты
пропадала целиком при значении 0** (`dInterval != 0 ? sep+secDelta(...) :
QString()`) — из-за этого часть блоков в файле имела 2 колонки, часть 3,
файл выглядел «рваным» (обнаружено пользователем 02.07 на скриншоте
реального журнала). Исправлено: дельта пишется всегда (`secDelta(0)` и так
возвращает «0 секунд»), плюс мини-заголовок каждого блока дополнен
подписью «Ошибка» (был только «Стенд»/«Регистратор» без третьей колонки).

## Guard: flashBinSearch не конкурирует с трафиком стенда

Разобрали причину «нет ответа Flash» во время идущей циклограммы — не
блокировка на стирании страницы (opcode `0x81`, быстрое постраничное
стирание Puya, единицы-десятки мс, не 500 мс, как думали раньше), а
конкуренция за один физический линк: `flashBinSearchStart()` мог быть
запущен переключением вкладки прямо во время активного теста стенда и
слал `FLASH_READ` вперемешку с `STEND_SPEED`/`CMD_CYCLE_PUSH`.

Исправлено (`mainwindow.cpp`):
- `flashBinSearchStart()` — не стартует, если `m_stendActive == true`.
- `flashBinSearchSendNext()` — если циклограмма стартовала посреди уже
  идущего поиска, шаг откладывается на 1 с (lo/hi/step сохраняются),
  не сбрасывается.
- `stendStop()` — вызывает `flashBinSearchStart()` после остановки, чтобы
  отложенный поиск возобновился/перезапустился сразу.

Проверены и признаны корректными (без изменений) все 3 режима стирания:
Страница/Сектор (`Wait_Busy()` блокирующий внутри firmware-функции, ACK
только после реального завершения) и Чип (осознанно без `Wait_Busy` —
ACK мгновенный, готовность через WIP-опрос `FLASH_STATE` каждые 700 мс,
т.к. полное стирание ~30 с блокировало бы всю связь). Риск гонки при
ручном стирании во время идущего теста стенда — признан пользователем
неопасным, защиту не добавляли.

Также найдено (не исправлено, отдельная задача низкого приоритета):
`actual/test_dumps/registrator_dump.hex` (и README) описывают **старый**
28-байтный формат записи — не совпадает с актуальным 24-байтным (см.
`SaveParamOnEEPROM`/`archiveParseRegistratorPage`). `logger_dump.hex`
актуален. Пересборка дампа под 24 байта с реальным CRC16 — отложена.

## Найден реальный баг чтения Flash (`P25Qx_QPI_Read`, dummy-циклы)

При тестировании вкладки «Тест памяти» вживую: «Запись» работала («Запись OK»
x N), «Чтение» — систематически ноль ответов (таймауты cmd=0x07 после каждой
попытки), «Стирание чипа» подозрительно «за 0 с» (см. выше). Сначала выглядело
как аппаратная проблема («нет ответа Flash»), но пользователь настоял
проверять сначала софт/прошивку — и в `Firmware/LOGLSMA/App/Src/p25q128.c`
нашлось: `P25Qx_QPI_Read()` в ветке `qpi_mode` слала Fast Read (`0x0B`) с
**10 dummy-циклами**, а соседние ветки той же функции (`standart_mode`/
`quadspi_mode`) — с 8. По даташиту P25Q128H (проверено через веб-поиск)
Fast Read в QPI поддерживает только 4/6/8 dummy-циклов (регистр Set Read
Parameters) — 10 чип не поддерживает. Несовпадение по факту сдвигает фазу
данных на 2 такта → STM32 читает мусор → пакет не проходит CRC на приёме в
LOGLSMW → выглядит как «нет ответа», хотя чип отвечал. Запись/стирание не
задеты, т.к. используют 0 dummy-циклов.

Исправлено: `10` → `8` в qpi_mode-ветке `P25Qx_QPI_Read`. Это правка
прошивки — требует пересборки и перешивки LOGLSMA, до сих пор не
проверялась на реальном железе (только по коду + датащиту). Также, вероятно,
объясняет и подозрительное «Чип стёрт за 0 с» — если это тоже было
случаем «чтение статуса вернуло мусор», но статус стирания (WIP) читается
не через P25Qx_QPI_Read, а через P25Qx_ReadSR — отдельный путь без dummy
циклов вовсе, так что это, возможно, отдельный вопрос, не закрытый этой
правкой.

## Риски / стоит проверить в следующей сессии

1. **`CMD_RESET_TOTAL` (0x21)** реализован в прошивке, но, судя по
   комментарию, не вызывается с ПК — уточнить, сознательный ли это задел
   или недоделанный откат решения.
2. **`maxVibro` в Flash-записи всегда 0.0** — акселерометр физически не
   подключён к подсчёту вибрации в `HandleSensorData`. Не баг, но
   заглушка, легко забыть при последующем анализе данных.
3. **Два разных алгоритма поиска границы Flash** (линейный на стороне
   прошивки в `flashFindWritePos`, двоичный на стороне LOGLSMW в
   `flashBinSearchStart`) решают разные задачи (курсор записи vs граница
   чтения) — не баг, но важно не путать при будущей отладке.
4. `.cproject` тронут по времени (mtime сегодня), но `git diff` пустой —
   похоже, IDE просто пересохранила файл без реальных изменений.
