# ТЗ — LOGLSMW v1.0

**Сервисное приложение устройства LogLSM (LOGLSMA + MA00)**
Дата: 11.06.2026 | Статус: черновик на согласовании
Протокол: LTP v1.0 | Транспорт: всегда COM (USART2, 921600)
Бесконтактно: через регистратор-ретранслятор BLE (этап 6)

---

## 1. Назначение

LOGLSMW — приложение для ПК (Windows, Qt 6.5+, CMake) для работы с автономным
инерциальным логгером LogLSM в режиме SERVICE:

- диагностика устройства (связь, датчики, время, температуры);
- мониторинг IMU и температур в реальном времени с графиками;
- управление Flash-памятью: статус, чтение (дамп), стирание;
- подготовка устройства к работе: установка времени, параметров IMU, запуск регистрации.

### 1.1 Бесконтактная работа — топология «ретранслятор»

**ПК всегда подключается к регистратору проводом (UART, COM-порт).**
Для бесконтактной работы используется второй регистратор: подключённый кабелем
работает как **BLE-ретранслятор** для удалённого (например, на вибростенде):

```
ПК ←─ кабель USART2, 921600 ─→ LogLSM №1          LogLSM №2 (вибростенд)
                               (ретранслятор) ←─ BLE (HLK-B40 ↔ HLK-B40) ─→
```

Следствия для архитектуры:
- приложению **не нужен Bluetooth вообще** — только COM-порт, всегда;
- маршрутизация — по полю **ADDR** пакета LTP: ретранслятор обрабатывает пакеты
  со своим адресом (0x8D), а чужие пересылает в BLE-канал (USART1) и обратно;
- для UI «бесконтактный режим» = выбор адреса целевого устройства (§3.2);
- ключевой сценарий — **мониторинг изделия на вибростенде в реальном времени**:
  вкладка «Мониторинг» работает одинаково с прямым и ретранслируемым устройством
  (медленнее: BLE-канал 115200 бод / эфир ~30–50 КБ/с).

Режим ретрансляции — функция firmware (этап 6), на структуру приложения не влияет.

## 2. Режимы работы приложения

| Режим | Описание | Вкладки |
|---|---|---|
| **SERVICE** | Ручные команды, диагностика, настройка | Команды, Flash |
| **MONITOR** | Периодический опрос, графики в реальном времени | Мониторинг |
| **LOG** | Выгрузка содержимого Flash в файл, прогресс | Flash |

Режимы не переключаются явно — определяются тем, какая вкладка активна и что запущено.
Одновременно активен только один потребитель канала: при запуске дампа Flash
опрос мониторинга приостанавливается (и наоборот) — арбитраж в `LinkManager` (§5.2).

```
│ [Порт: COM3 ▾] [Обновить] [Подключить] [Цель: Прямое (0x8D) ▾]    │
├──────────────────────────────────────────────────────────────────┤
│ ┌────────┬─────────┬────────────┬───────┬───────────┐            │
│ │Команды │Мониторинг│   Flash    │ Лог   │ Настройки │            │
│ └────────┴─────────┴────────────┴───────┴───────────┘            │
│                                                                  │
│                [ содержимое активной вкладки ]                    │
│                                                                  │
├──────────────────────────────────────────────────────────────────┤
│ СТАТУСБАР: ● COM3 921600 | ADDR 0x8D | TX:124 RX:123 CRCerr:0 | t │
└──────────────────────────────────────────────────────────────────┘
```

Изменение против текущей версии: панель подключения выносится из вкладки
наверх — подключение нужно из любой вкладки. Отдельная вкладка «Подключение» упраздняется.

### 3.1 Меню

| Меню | Пункты |
|---|---|
| Файл | Сохранить лог…, Экспорт графиков CSV…, Выход |
| Устройство | Ping, Who Am I, Синхронизировать время, Старт регистрации |
| Помощь | О программе (AboutDialog: версия, LTP v1.0, адрес устройства) |

### 3.2 Панель подключения (postоянная)

| Виджет | objectName | Тип | Поведение |
|---|---|---|---|
| Порт | `cmbPort` | QComboBox | список COM-портов |
| Обновить | `btnRefresh` | QPushButton | пересканировать порты |
| Подключить | `btnConnect` | QPushButton | toggle Подключить/Отключить |
| Цель | `cmbTarget` | QComboBox | «Прямое (0x8D)» / «Через ретранслятор (0x8E)» — v1: только прямое, второй пункт disabled |
| Индикатор | `lblLinkState` | QLabel | ● зелёный/серый/красный (подкл./откл./ошибка) |

`cmbTarget` задаёт ADDR исходящих пакетов (DeviceController.targetAddr).
Физический канал всегда один — COM.

### 3.3 Статусбар

`lblPort` (порт+скорость), `lblAddr` (адрес устройства), `lblCounters`
(TX/RX/CRCerr — счётчики из QLtp), `lblDevTime` (последнее известное время устройства).

## 4. Вкладки

### 4.1 Вкладка «Команды»

```
┌─ Устройство ─────────────┐ ┌─ Время ───────────────────────┐
│ [Ping] [Who Am I]        │ │ Устройство: 00:00:37 01/01/00 │
│ WHO_AM_I: 0x6C (LSM6DSO) │ │ [Прочитать] [Синхронизировать]│
└──────────────────────────┘ └───────────────────────────────┘
┌─ Датчики ────────────────────────────────────────────────────┐
│ [IMU Raw] [Temp LSM] [Temp TMP117] [Temp STM32]              │
│ Acc: X.. Y.. Z..   Gyro: X.. Y.. Z..   T: 28.5 / 28.1 / 29.0 │
└──────────────────────────────────────────────────────────────┘
┌─ IMU параметры ──────────────────────────────────────────────┐
│ Acc FS: [±2g ▾]  Gyro FS: [±250dps ▾]  [Прочитать] [Записать]│
└──────────────────────────────────────────────────────────────┘
┌─ Регистрация ────────────────────────────────────────────────┐
│ [▶ Старт регистрации]  (выход из SERVICE, устройство в WORK) │
└──────────────────────────────────────────────────────────────┘
```

Главное отличие от текущей версии: результаты показываются **в полях рядом с кнопками**
(QLabel), а не только строками в логе. Лог дублирует всё (вкладка «Лог»).

| Группа | Виджеты (objectName) | Команды LTP |
|---|---|---|
| Устройство | `btnPing`, `btnWhoAmI`, `lblWhoAmI` | 0x01, 0x02 |
| Время | `lblDevDateTime`, `btnGetTime`, `btnSyncTime` | 0x1B, 0x1C (время ПК) |
| Датчики | `btnImuRaw`, `btnTempLsm`, `btnTempTmp117`, `btnTempStm`, `lblAxes`, `lblTemps` | 0x1A, 0x10, 0x0A, 0x11 |
| IMU параметры | `cmbAccFs`, `cmbGyroFs`, `btnFsRead`, `btnFsWrite` | 0x13, 0x15, 0x17, 0x19 |
| Регистрация | `btnStartRegister` | 0x1D, с подтверждением QMessageBox |

Кнопка «Синхронизировать»: отправляет 0x1C с текущим временем ПК, затем читает 0x1B
и показывает результат — закрывает замечание со стенда (RTC = 01/01/2000).

### 4.2 Вкладка «Мониторинг» (режим MONITOR, ключевая для вибростенда)

```
┌─ Управление ───────────────────────────────────────────────────┐
│ ☑Acc ☑Gyro ☐T(LSM) ☐T(TMP117) ☐T(STM32)  Период: [100 мс ▾]    │
│ [▶ Старт] [⏸ Пауза] [■ Стоп] [Очистить] [CSV…]   Окно: [30 с ▾]│
├─ График 1: Акселерометр (X красн, Y зел, Z син) ──────────────┤
│   QCustomPlot `plotAcc`                                        │
├─ График 2: Гироскоп (X, Y, Z) ────────────────────────────────┤
│   QCustomPlot `plotGyro`                                       │
├─ График 3: Температуры (LSM, TMP117, STM32) ──────────────────┤
│   QCustomPlot `plotTemp`                                       │
└────────────────────────────────────────────────────────────────┘
```

| Виджет | objectName | Примечание |
|---|---|---|
| Чекбоксы каналов | `chkAcc`, `chkGyro`, `chkTLsm`, `chkTTmp`, `chkTStm` | определяют, какие команды в цикле опроса |
| Период опроса | `cmbPollPeriod` | 50/100/200/500/1000/5000 мс (50 мс — только для кабеля) |
| Окно графика | `cmbTimeWindow` | 10/30/60/300 с, скользящее |
| Управление | `btnMonStart`, `btnMonPause`, `btnMonStop`, `btnMonClear`, `btnMonCsv` | |
| Графики | `plotAcc`, `plotGyro`, `plotTemp` | QCustomPlot, автомасштаб Y, общая ось X (время) |

Поведение:
- один QTimer; за тик опрашиваются только включённые каналы, последовательно
  (следующий запрос — после ответа или таймаута предыдущего, не пачкой);
- пауза останавливает отрисовку, но не сбор; стоп — всё;
- данные копятся в кольцевых буферах (глубина = окно × частота, с запасом);
- CSV: `timestamp_ms;ax;ay;az;gx;gy;gz;t_lsm;t_tmp;t_stm` (пустые поля у выключенных);
- сырые LSB пересчитываются в физические единицы по текущему FS (g, dps) — FS
  читается при старте мониторинга (0x17/0x19);
- графики скрываются/показываются по чекбоксам (layout перестраивается).

Требование производительности: при 100 мс × 2 команды UI не подвисает,
отрисовка ≤ 20 FPS (replot по таймеру, не на каждую точку).

### 4.3 Вкладка «Flash» (режимы SERVICE + LOG)

```
┌─ Состояние ────────────────────────────────────────────────────┐
│ [Питание Flash: Вкл/Выкл]  [Прочитать ID]  ID: EF 60 18  16 МБ │
│ Статус: готова / занята (WIP)            [Обновить статус]    │
├─ Заголовок лога ───────────────────────────────────────────────┤
│ [Прочитать заголовок]  Версия:1 Режим:2 Указатель: 0x0123A0    │
│ Заполнено: 1.2 МБ из 16 МБ (7%)  ▓▓░░░░░░░░░░░░░               │
├─ Выгрузка ─────────────────────────────────────────────────────┤
│ Диапазон: [Весь лог ▾ | Всё 16МБ | Адрес+размер]               │
│ Адрес: [0x000000]  Размер: [0x10000]  Файл: [dump.bin] [...]   │
│ [⬇ Выгрузить]  [Отмена]   ▓▓▓▓▓░░░░ 34%  ETA 01:12  92 КБ/с   │
├─ Стирание ─────────────────────────────────────────────────────┤
│ [Стереть страницу: N]  [⚠ Стереть всё]  (двойное подтверждение)│
└────────────────────────────────────────────────────────────────┘
```

| Виджет | objectName | Команды |
|---|---|---|
| Питание | `btnFlashPwr` (toggle) | 0x0E/0x0F |
| ID | `btnFlashId`, `lblFlashId` | 0x04 |
| Статус | `btnFlashState`, `lblFlashState` | 0x09 (WIP-бит) |
| Заголовок | `btnReadHeader`, `lblLogInfo`, `barFill` | 0x07 (чтение 0x000000) |
| Выгрузка | `cmbDumpRange`, `editAddr`, `editSize`, `editFile`, `btnBrowse`, `btnDump`, `btnDumpCancel`, `barDump`, `lblDumpStat` | цикл 0x07 по 256 байт |
| Стирание | `spinPage`, `btnErasePage`, `btnEraseAll` | 0x06, 0x05 |

Поведение выгрузки (LOG):
- последовательные запросы 0x07 по 256 байт, SEQ-матчинг, до 3 повторов на блок
  при таймауте/ошибке, затем стоп с сообщением;
- прогресс, скорость, ETA; отмена корректно завершает текущий блок;
- запись в файл потоково (не копить 16 МБ в памяти);
- на время дампа мониторинг и ручные команды блокируются (§5.2).

«Стереть всё»: QMessageBox с вводом слова «СТЕРЕТЬ» — защита от случайного клика.

### 4.4 Вкладка «Лог»

```
│ [фильтр: Все ▾ TX RX ERR]  [Поиск: ____]  ☑Автопрокрутка       │
│ QPlainTextEdit `logView` (моноширинный)                        │
│ [Очистить] [Сохранить…]  ☐ HEX-дамп пакетов                    │
```

- единый журнал обмена: `[чч:мм:сс.мс] [TX|RX|ERR] описание`;
- ERR — красным; CRC-ошибки канала — оранжевым;
- ☑ HEX-дамп: дополнительно сырые байты пакетов (для отладки протокола);
- лимит 5000 строк (старые удаляются), `QPlainTextEdit` (не QTextEdit — производительность).

### 4.5 Вкладка «Настройки»

| Параметр | objectName | Default |
|---|---|---|
| Адрес устройства | `spinDevAddr` (hex) | 0x8D |
| Скорость COM | `cmbBaud` | 921600 |
| Таймаут ответа, мс | `spinTimeout` | 500 |
| Повторы при таймауте | `spinRetries` | 2 |
| Лимит лога, строк | `spinLogLimit` | 5000 |

Хранение: `QSettings` (org «LogLSM», app «LOGLSMW»). Геометрия окна тоже сохраняется.

## 5. Архитектура

### 5.1 Слои

```
UI (MainWindow + вкладки)
   ↓ сигналы/слоты
DeviceController  — высокоуровневые операции: ping(), syncTime(), dumpFlash(...)
   ↓                 очередь запросов, SEQ-матчинг, таймауты, повторы
QLtp              — сборка/разбор пакетов LTP (готов, проверен в железе)
   ↓
ComLink           — QSerialPort (на основе текущего класса COM)
```

Bluetooth-стека на ПК нет: бесконтактный режим реализуется ретранслятором (§1.1),
для приложения это лишь другой ADDR в пакетах (`cmbTarget`). Таймауты для
ретранслируемой цели увеличиваются (×4, настройка).

### 5.2 DeviceController (новый класс — ядро v1)

- **очередь запросов**: один запрос в полёте; следующий — после ответа/таймаута;
- SEQ-матчинг: ответ принимается только с SEQ текущего запроса; поздние — в лог, игнор;
- таймаут (из настроек) + повторы; после исчерпания — сигнал `requestFailed`;
- арбитраж: эксклюзивные операции (дамп) блокируют очередь для остальных;
- сигналы результата типизированы: `axesReady(AxesSample)`, `tempReady(source, float)`,
  `dateTimeReady(...)`, `flashBlockReady(addr, QByteArray)`, `errorReceived(cmd, code)`.

UI не знает про LTP вообще — только DeviceController.

### 5.3 Файлы проекта (план)

```
SoftWare/LOGLSMW/
├── main.cpp, mainwindow.{h,cpp,ui}      — главное окно, вкладки
├── devicecontroller.{h,cpp}             — НОВЫЙ: очередь, SEQ, таймауты, targetAddr
├── comlink.{h,cpp}                      — НОВЫЙ: обёртка QSerialPort (Com.* внутрь)
├── qltp.{hpp,cpp}                       — готов
├── monitorpage.{h,cpp}                  — НОВЫЙ: логика мониторинга и графиков
├── flashpage.{h,cpp}                    — НОВЫЙ: логика Flash/дампа
└── qcustomplot/                         — есть
```

MainWindow — только каркас и маршрутизация; логика страниц — в своих классах.

## 6. Протокол — требования к поведению

| Требование | Значение |
|---|---|
| Запросы | DIR=0, SEQ автоинкремент (есть) |
| Ответы | принимать только DIR=1; FLAGS.ERR проверять до PAYLOAD (есть) |
| Таймаут | 500 мс default, настройка |
| Повторы | 2 default; для эксклюзивных операций — 3 на блок |
| Echo-защита | пакеты DIR=0 на приёме игнорируются (есть) |
| Счётчики | TX, RX, CRCerr — в статусбар |

## 7. Этапность реализации

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **1. UI-каркас** | mainwindow.ui: все вкладки, все виджеты с objectName по ТЗ, без обработчиков | окно собирается, все элементы на местах |
| **2. Ядро** | DeviceController + ILink/ComLink, перенос текущих команд | всё, что работало, работает через очередь |
| **3. Команды** | вкладка «Команды» полностью (+SET_DATETIME, PING, WHO_AM_I, FS) | проверка в железе |
| **4. Мониторинг** | графики, опрос, CSV | 100 мс опрос без подвисаний |
| **5. Flash** | статус, дамп с прогрессом, стирание | дамп 16 МБ за ~3 мин по кабелю |
| **6. Ретранслятор** | firmware: пересылка чужих ADDR в BLE-канал (USART1) и обратно; UI: активация `cmbTarget`, увеличенные таймауты | мониторинг устройства на вибростенде через ретранслятор |

После согласования ТЗ начинаем с этапа 1: полный `mainwindow.ui` без обработчиков,
затем по этапам добавляем логику и отлаживаем (план пользователя).

## 8. Открытые вопросы

1. Формат заголовка лога во Flash (§4.3 «Заполнено») — взять из `data_format_spec_v1.md`,
   уточнить парсинг указателя записи.
2. Частота потокового режима для вибростенда: командный polling даёт ~10–20 Гц на канал;
   для честных 104 Гц нужен потоковый режим LTP (CMD бит 7=1, зарезервирован в спеке) —
   предлагается заложить в firmware на этапе 6 вместе с BLE.
3. Ретрансляция (этап 6, firmware): схема пересылки — разбирать только заголовок
   и пересылать кадр целиком (FEND-граница); буферизация из-за разницы скоростей
   (кабель 921600 / BLE 115200); связывание двух HLK-B40 (master/slave, AT-команды);
   адрес второго устройства (предложение: 0x8E, задаётся в настройках).
4. Аппаратная альтернатива (обсуждалось): SoC с интегрированным BLE — STM32WB
   (например WB55: Cortex-M4 + M0+ радио, та же периферия L4, HAL совместим).
   Снимает HLK-B40, UART-узкое место и B_PWON-схему целиком. Для LOGLSMW ничего
   не меняет — ПК по-прежнему говорит с ретранслятором по кабелю. Вопрос ревизии
   C платы, не ПО.
