## 1. Назначение и концепция

LOGLSMW — приложение для ПК (Windows, Qt, CMake) для работы с автономным
инерциальным логгером LogLSM в режиме SERVICE.

### 1.1 Две части программы

| Часть | Пользователь | Содержание |
|---|---|---|
| **Операторская** (по умолчанию) | оператор эксплуатации | один экран-дашборд: паспорт устройства, активация, журнал. Минимум манипуляций |
| **Инженерная** (за ключом) | разработчик/наладчик | вкладки: Команды, Мониторинг, Flash, Лог, Настройки (+ резерв «Стенд») |

**Одна сборка**: инженерная часть скрыта, открывается через меню Сервис → ввод ключа;
дашборд при этом становится первой вкладкой. Отдельная lite-сборка — возможна в конце,
не в v2.

### 1.2 Принцип «минимум манипуляций оператора»

Цикл оператора: **подключил кабель → (автоархив, сам) → нажал «Активировать» →
дождался «отключите кабель» → отключил**. Всё остальное приложение делает само.

### 1.3 Топология и адресация LTP

ПК всегда подключается через виртуальный COM-порт. Маршрутизация — по полю ADDR:

| ADDR | Устройство |
|---|---|
| 0x8C | зарезервирован (технологический блок — в ТЗ будет внесён позже отдельно) |
| 0x8D | регистратор LogLSM (прямое подключение) |
| 0x8E | удалённый регистратор через BLE-мост (этап «BLE-мост») |

Бесконтактная работа — через регистратор в роли **BLE-моста** (HLK-B40 ↔ HLK-B40),
для приложения это лишь другой ADDR. Bluetooth-стека на ПК нет.
Сервисный кабель = USB-UART адаптер; в комплект рекомендовать CP2102/FT232
(CH340 на 921600 бод капризен).

| Меню | Пункты |
|---|---|
| Файл | Сохранить журнал…, Выход |
| Сервис | Инженерный режим… (ввод ключа) |
| Помощь | О программе |

### 2.2 Панель подключения

Кнопок «Подключить/Отключить» и комбобокса портов НЕТ. Состав:

| Элемент | Размер | Поведение |
|---|---|---|
| Кнопка-индикатор `btnInd` | 30×30 | точка зелёная (подключено) / красная (нет); клик → диагностическая панель портов |
| Кнопка `btnScan` | 56×30 | надпись «ВКЛ» ↔ «COM3»; нажатие = автопоиск / повторное = отключение |
| Карточка устройства `devCard` | растяжка до правого края | выкл: «LOGLSMW · сервис регистратора»; вкл: «LOGLSMA-регистратор» (без hex-кодов); шрифт = кнопке |

**Автопоиск порта**: перебор всех COM-портов системы — открыть на выбранной
скорости → PING (0x01) на ADDR 0x8D → таймаут ~200 мс. Найден — зелёный индикатор.
Закреплённый (📌) порт проверяется первым; хранится в QSettings.
В будущем — ping и 0x8C: индикация, кто найден на линии.

**Диагностическая панель** (по клику на индикатор; оператор о ней может не знать):

- список портов системы, каждый с результатом опроса:
  «нет ответа» / «LOGLSMA 0x8D» (зелёным) / «занят другой программой»;
- клик по порту = закрепить 📌 (проверять первым при автопоиске);
- секция «скорость подключения»: чипы 921600 (default) / 460800 / 230400 / 115200 —
  поиск идёт на выбранной скорости.

### 2.3 Карточка «Активное время» (главная, слева)

Источник данных: записи регистратора из автоархива + GET_STATS.

- Заголовок «Активное время»; наработка крупно (моно 30px): «37 ч 12 м».
- Справа столбик 4 строки без подписей: дата/время первого цикла, дата/время
  конца последнего; формат сортируемый «2026-06-03» / «08:12».
- Ниже два мини-графика (высота ~64 px, нулевая ось снизу):
  1) **максимальная скорость по циклам** — синий #2F6FB0;
  2) **максимальная вибрация по циклам** — красный #C03030.
  Графики автомасштабируются по Y на полную высоту; нижний график прижат
  к низу карточки (R21).
  Ось X — **циклы по порядку**, не время. Под каждым графиком подпись
  («максимальная скорость» / «максимальная вибрация») и значение крупно
  цветом графика: «1 240 об/мин» / «18.4 g».

### 2.4 Правая колонка (190 px, 4 секции)

Подписи слева мелким серым, значения справа моно жирным (правая колонка цифр).
Полосы памяти НЕТ (убрана — отвлекает).

| Секция | Строки | Источник |
|---|---|---|
| **Время** | текущее (ПК, живые часы) / регистратор (опрос 0x1B раз в 1 с) / разница | 0x1B |
| **Рабочие циклы** | записано / доступно — числа ТОЧНЫЕ, без «≈» | заголовок Flash (0x07) |
| **Температура** | текущая / максимальная **за время измерения** | 0x10 (IMU); максимальная — из данных при считывании (§2.6 п.4) |
| **Перезапуски** | по таймеру / по питанию | GET_STATS (счётчики из RCC_CSR) |

**Логика времени**: сравнение по полной дате-времени, допуск 1 с (точность 0x1B).
Часы регистратора зелёные при совпадении, красные при расхождении.
Разница — со знаком («−» отстаёт, «+» спешит), две группы: «−12 м 05 с», мелко.
Порог аварии настраиваемый (инженерный режим, default 10 мин):
до 1 с — синхронно (строка разницы пустая); 1 с..порог — реальное значение;
больше порога — **АВАРИЯ**: моргающее красное «XX:XX» (часы сбиты).
После шага синхронизации в активации зеленеет само.
Кнопки «Установить время» на основном экране НЕТ — только инженерный режим.

**Единица памяти зависит от режима записи устройства**:
Регистратор → циклы (30 байт/запись, 16 МБ ≈ 558 тыс. циклов; часы невозможны —
записей столько, сколько циклов); Logger → часы (поток 16 байт × ODR,
прямая связь объём↔время): «записано 37 ч / осталось 118 ч».

**Температура**: одно показание, по умолчанию — с IMU (LSM6DSO; заодно косвенная
проверка главного датчика). TMP117 и FRAM — опциональная периферия, не в базе.
Выбор датчика — настройка инженерного режима. Контроль исправности всех трёх
термодатчиков (отклик + физпределы −40..+85 + взаимный разброс) — только
в шаге активации «Проверка устройства» и в инженерном режиме.

### 2.5 Карточка активации (полоса секторов)

Только карточка — модального мастера-диалога НЕТ.

- Полоса из N секторов (N = число шагов, сейчас 6). До активации все красные.
- Верхняя строка карточки **динамическая** — тип текущей операции, не слово
  «Готовность»: «Не активировано» → «Проверка датчиков» → «Очистка памяти… 64 %»
  → … → «Готов к работе — отключите кабель».
- В процессе: завершённый сектор зелёный, текущий моргает жёлтым; ошибка — стоп,
  сектор красный, причина в подписи, кнопка повторного пуска. Tooltip — имя шага.
- Пуск — малая кнопка 34×14 (высота сектора) справа от полосы, «▶»,
  зеленеет при готовности к пуску. Большой кнопки НЕТ, подсказки под секторами НЕТ.
- Все зелёные = «ГОТОВ К РАБОТЕ — отключите кабель» (+ зелёная рамка).
- Детальный протокол активации — в журнал (акт ввода в эксплуатацию).

### 2.6 Алгоритм при подключении (последовательность заполнения дашборда)

1. Устройство найдено → **зелёный индикатор** подключения.
2. Считывается и выводится текущее время устройства (0x1B), заполняется
   **правая колонка**: Время, Рабочие циклы, Температура (+ Перезапуски из GET_STATS).
3. По GET_STATS заполняется шапка карточки «Активное время»: наработка общая,
   дата/время начала (первый цикл) и конца (последний цикл).
3a. **Число записей** вычисляется методом последовательного приближения
   (двоичный поиск первой незаполненной ячейки, стёртая Flash = 0xFF):
   ~24 чтения малых блоков (0x07) на 16 МБ — мгновенно, указатель из заголовка
   не обязателен. Корректно, т.к. запись строго последовательная, без перезаписи.
   Нюанс: «пусто» проверять по всей записи (30 байт = 0xFF), не по одному байту —
   валидная запись может содержать байты 0xFF; поиск по границам записей от 0x000100.
4. **Нормировка шкал графиков**: X — по числу отсчётов (из п.3a), сразу;
   Y — **автокалибровка по ходу считывания**: при появлении нового максимума
   шкала пересчитывается, график перерисовывается (смотрится эффектно).
   Максимумы в firmware НЕ хранятся — вычисляются приложением из данных;
   цифровые значения под графиками обновляются живьём.
5. Запускается считывание данных (автоархив, §4); по мере считывания графики
   **заполняются слева направо в реальном масштабе** — заполнение графика
   одновременно является **индикатором прогресса считывания** (отдельный
   прогрессбар не нужен).
6. По окончании считывания — **сектор 1 полосы активации зеленеет**
   (шаг «Считывание данных = автоархив» выполнен).

### 2.7 Журнал и статусбар

- Журнал: 3 строки, моно 11px; полный журнал — вкладка «Лог» (инженерный режим).
- Статусбар: моно 10px: порт·скорость | ADDR | TX·RX·CRCerr | режим (🔒 оператор / 🔧 инженер).

## 3. Активация — модель и шаги

Модель «разбег по полосе»: активация = предполётная проверка + постановка
на готовность; устройство **остаётся в SERVICE и на связи**. «Взлёт» = оператор
отключает кабель → WKUP1 пропало → PASSIVE → движение → WORK.
Снятие с линии программа детектирует по пропаже ответов («устройство снято»).

Шаги выполняются автоматически один за другим; на ошибке — стоп, причина, «Повторить»:

| № | Шаг | Содержание |
|---|---|---|
| 1 | Считывание данных = **автоархив** | гарантированная архивация содержимого Flash; пока не выполнена — сектор 1 не зелёный («самолёт к взлёту не готов») |
| 2 | Проверка устройства | WHO_AM_I + датчики (3 термодатчика: отклик, физпределы, взаимный разброс); идентификация в протокол |
| 3 | Синхронизация времени | 0x1C временем ПК, контроль чтением 0x1B |
| 4 | Очистка памяти | без подтверждений — архив уже есть (§4); синхронно **стираются графики дашборда** (визуализация очистки), данные перестают отображаться — остаётся только текущее время |
| 5 | Проверка записи | тестовая запись/чтение Flash |
| 6 | Постановка на готовность | 0x1D: взвести флаг готовности, остаться в SERVICE |

Кнопки «Считать данные» на окне НЕТ — архивация автоматическая (шаг 1 и при
подключении). Отдельного шага «связь» НЕТ (паспорт уже заполнен к моменту пуска).

**После завершения активации**: зелёная шкала + на дашборде отображается
**дата/время активации**. Первичное хранение — **в самом регистраторе**
(заголовок Flash, пишется при 0x1D, живёт до следующей активации; отдаётся
в GET_STATS); копия — в протокол активации (журнал/акт) и архив. Это опорная
точка для **оценки времени работы батарейки** (LS14250).
Терминология: максимумы — «за время измерения»
(после активации обнуляются вместе с данными; история — в автоархивах).

⚠ **Доработка firmware**: 0x1D сейчас делает немедленный QUIT из Service() —
переделать на «взвести флаг готовности, остаться в SERVICE до снятия питания».

**Идея на будущее (поддержана)**: готовность как ЖИВОЙ статус — если во время/после
активации параметр вышел из нормы → ТРЕВОГА, сектор гаснет, готовность снимается.
Реалистичные триггеры: отказ датчика, температура вне нормы, появление данных
в памяти (часы за минуты не уйдут).

## 4. Автоархив и правило разрушающих операций

При подключении устройства программа **автоматически** создаёт архивную запись —
фоном; индикатор прогресса — заполнение графиков дашборда (§2.6) + строка в статусбаре:

```
Archive/<устройство>/<дата_время>/
├── journal.txt   — паспорт, время, температуры, события сеанса
└── flash.bin     — полное содержимое Flash (если есть данные)
```

Путь — в настройках (инженерный режим).

**Правило (жёсткое, инвариант программы)**: любые разрушающие операции
(стирание, тесты записи, переразметка) разрешены ТОЛЬКО при наличии архива
текущего содержимого. Программа гарантирует это сама; действует и в инженерном
режиме. Следствие: активация стирает память автоматически, без подтверждений.

## 5. Инженерный режим

Вход: Сервис → диалог ввода ключа. Появляются вкладки; дашборд — первая вкладка.

**Ключ (решено 12.06)**: фиксированный пароль. «Заводской» задаётся при сборке
(CMake-define); смена — в Настройках инженерного режима, новый хранится хешем
(SHA-256) в QSettings этого ПК; сброс настройки возвращает заводской.
В диалоге ввода — галочка **«запомнить на этом компьютере»** (QSettings):
с ней программа стартует сразу в инженерном режиме, без неё — режим только
на сессию. Выход из режима — пункт меню Сервис (снимает и запоминание).
Состав вкладок: **Дашборд, Команды, Мониторинг, Flash, Лог, Настройки**
(+ зарезервирована вкладка «Стенд» — содержимое будет внесено в ТЗ позже отдельно).

Содержимое вкладок «Команды», «Мониторинг», «Flash», «Лог» — по ТЗ v1 §4.1–4.4
без изменений (виджеты, objectName, команды LTP, поведение выгрузки, лимиты лога).
Изменения против v1:

- панель подключения — новая (§2.2), без `cmbPort`/`btnRefresh`/`btnConnect`/`cmbTarget`;
  выбор цели (0x8D/0x8E) переносится в Настройки до этапа «BLE-мост»;
- «Стереть всё», стирание страниц, тест записи — подчиняются инварианту §4;
- кнопки PING и WHO_AM_I — добавить (замечание со стенда);
- кнопка «Синхронизировать время» — есть на вкладке «Команды» (закрывает RTC=01/01/2000).

### 5.1 Вкладка «Настройки» (расширена против v1)

| Параметр | Default |
|---|---|
| Адрес устройства (hex) | 0x8D |
| Скорость COM | 921600 |
| Таймаут ответа, мс | 500 |
| Повторы при таймауте | 2 |
| Лимит лога, строк | 5000 |
| **Порог аварии расхождения времени** | 10 мин |
| **Датчик температуры дашборда** | IMU (LSM6DSO) / TMP117 / STM32 |
| **Путь архива** | `Archive/` |
| Ключ инженерного режима | заводской из сборки; смена → хеш в QSettings (§5) |

Хранение: QSettings (org «LogLSM», app «LOGLSMW») + геометрия окна + закреплённый порт.

## 6. Архитектура

```
UI (MainWindow: дашборд + инженерные вкладки)
   ↓ сигналы/слоты
ActivationController — машина состояний активации (шаги §3, протокол в журнал)
ArchiveWriter        — автоархив (§4), инвариант разрушающих операций
PortScanner          — автопоиск (§2.2): перебор портов, PING, закреплённый порт
DeviceController     — очередь запросов, SEQ-матчинг, таймауты, повторы, targetAddr
QLtp                 — сборка/разбор LTP (готов, проверен в железе)
ComLink              — QSerialPort
```

Принципы из v1 сохраняются: один запрос в полёте; SEQ-матчинг; эксклюзивные
операции (дамп, автоархив, активация) блокируют очередь; UI не знает про LTP —
только DeviceController; типизированные сигналы результата.

Файлы (план): `mainwindow`, `dashboardpage`, `activationcontroller`,
`archivewriter`, `portscanner`, `devicecontroller`, `comlink`, `qltp` (готов),
`monitorpage`, `flashpage`, `qcustomplot/`.

## 7. Требования к firmware (для поддержки v2)

| Доработка | Описание |
|---|---|
| **0x1D переработать** | взвести флаг готовности, остаться в SERVICE до снятия питания (сейчас — немедленный QUIT) |
| **GET_STATS (новая команда)** | наработка суммарная; дата/время первого и последнего цикла; счётчики перезапусков (по таймеру/по питанию из RCC_CSR). Максимумы (скорость/вибрация/температура) в firmware НЕ хранятся — приложение вычисляет их из данных при считывании (§2.6 п.4); число записей тоже не нужно (§2.6 п.3a) |
| Запись наработки | по окончании КАЖДОГО активного цикла вычислять суммарное время и писать свежую запись во Flash (при сбое теряется максимум незакрытый цикл — приемлемо) |
| Счётчики перезапусков | причина сброса из RCC_CSR (IWDG/POR/BOR/SW), инкремент во Flash при старте |
| **Время активации — хранится в регистраторе** (решено 12.06) | при 0x1D (шаг 6) дата/время активации записывается в заголовок Flash — это информация устройства, всегда при нём до следующей активации (перезаписывается новой). Отдаётся в GET_STATS; на дашборде → оценка остатка батарейки на любом ПК. Копия в протоколе/архиве — вторична |

FRAM НЕ в базовой комплектации — счётчики в ней не делаем (вернуться, только
если FRAM попадёт в финальную конфигурацию).

### 7.1 CMD_GET_STATS = 0x1E (формат, согласован 12.06)

Запрос: payload пустой. Ответ (little-endian, 22 байта):

| Смещение | Размер | Поле | Примечание |
|---|---|---|---|
| 0 | 4 | uptime_total | суммарная наработка, секунды |
| 4 | 4 | ts_first_cycle | unix; 0xFFFFFFFF — данных нет |
| 8 | 4 | ts_last_cycle | unix; 0xFFFFFFFF — данных нет |
| 12 | 4 | ts_activation | unix, из заголовка Flash; 0xFFFFFFFF — не активировано |
| 16 | 2 | restarts_timer | перезапуски по таймеру (IWDG) |
| 18 | 2 | restarts_power | перезапуски по питанию (POR/BOR) |
| 20 | 1 | mode | режим записи: 1 — Регистратор, 2 — Logger |
| 21 | 1 | stats_ver | версия структуры = 1 |

Реализационная заметка (NOR, без стирания): счётчики перезапусков хранить
унарно в зарезервированных байтах заголовка — каждый рестарт гасит очередной
бит (1→0), счётчик = число погашенных бит; перезапись в 0xFF-ячейки легальна.

Определения MAX_RPM / MAX_vibration — в `data_format_spec_v1.md` (дополнение 12.06).

## 8. Этапность реализации

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **1. UI-каркас** | операторское окно по эскизу R20 + инженерные вкладки (виджеты v1), без обработчиков | окно собирается, все элементы на местах |
| **2. Ядро** | DeviceController + ComLink + PortScanner (автопоиск); перенос текущих команд | всё, что работало, работает через очередь; автопоиск находит устройство |
| **3. Паспорт + автоархив** | живые индикаторы дашборда (0x1B 1 Гц, заголовок Flash, температура), ArchiveWriter | подключил — паспорт заполнился, архив создался |
| **4. Активация** | ActivationController, 6 шагов; параллельно firmware: 0x1D + GET_STATS | полный цикл оператора на стенде |
| **5. Инженерный режим** | ключ, вкладки Команды/Мониторинг/Flash/Лог/Настройки полностью | мониторинг 100 мс без подвисаний; дамп 16 МБ ~3 мин |
| **6. BLE-мост** | firmware: пересылка чужих ADDR в BLE (USART1); UI: цель 0x8E, таймауты ×4 | мониторинг удалённого устройства |

## 9. Перспективы (в v2 не реализуются, держать в уме)

- **Технологический блок (стенд)**: вкладка «Стенд», профили циклограмм, единый
  журнал «задал ↔ измерил» — будет внесено в ТЗ позже всё разом.

  FAT с файлом LOG.BIN, ~20–30 с на 16 МБ; возможен composite MSC+CDC.
  Для варианта A — только выгрузка по UART.
- **Загрузчик поверх LTP**: полевое обновление прошивки через COM-порт без BOOT
  (прецедент: `Doc/.../PROJECT_STRUCTURE.md` — `bl_ltp.c`, `ota_service.c`).
- **Живой статус готовности** с тревогами (§3).
- Потоковый режим LTP (CMD бит 7=1) для честных 104 Гц мониторинга — на этапе 6.
