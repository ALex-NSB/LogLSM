## Сделано

### Firmware (Firmware/LOGLSMA)

- **`App/Inc/ltp.h` + `App/Src/ltp.c`** — новые. FSM-парсер + сборщик по спеке LTP v1.0:
  - заголовок 7 байт после FEND: ADDR | CMD | FLAGS | SEQ[2] LE | LEN[2] LE
  - CRC16-CCITT (0x1021/0xFFFF/no reflect/xor 0), big-endian, по сырым байтам ADDR..PAYLOAD
  - stuffing C0→DB DC, DB→DB DD; FEND — безусловная точка ресинхронизации
  - `LTP_MAX_PAYLOAD = 512`, счётчик `crc_errors` для диагностики
- **`com.c`** переведён на LTP:
  - `WakeContext` → `LtpPacket` (поля addr/cmd/n/data совместимы — обработчики не менялись)
  - ответы: FLAGS.DIR=1, SEQ копируется из запроса (`cur_seq`)
  - входной фильтр: только `addr == LTP_DEV_ADDRESS && DIR == 0`
  - новые обработчики: **CMD_PING (0x01)**, **CMD_WHO_AM_I (0x02)** — читает LSM6DSO WHO_AM_I
  - неизвестная команда → `sendError()`: FLAGS.ERR=1 + код `LTP_ERR_UNKNOWN_CMD`
- **`com.h`**: `WAKE_DEV_ADDRESS` → `LTP_DEV_ADDRESS` (0x8D)
- **`CMakeLists.txt`**: + `App/Src/ltp.c`, − `App/Src/wake.c` (оставлен в репо как справочник)

### Qt (SoftWare/LOGLSMW)

- **`qltp.hpp` + `qltp.cpp`** — новые. Зеркало firmware-реализации:
  - `QLtp::build(cmd, addr, flags, seq, payload)`, `feed()`, сигнал
    `packetReceived(addr, cmd, flags, seq, payload)`
  - `crc16()`, `errorName()`, счётчик `crcErrors()`
- **`mainwindow.h/cpp`**:
  - `QWake *wake` → `QLtp *ltp`; `m_seq` — автоинкремент SEQ исходящих
  - `sendCmd(cmd)` — единая точка отправки (DIR=0, SEQ++)
  - приём: пакеты с DIR=0 отбрасываются (защита от echo); FLAGS.ERR проверяется
    до разбора PAYLOAD, ошибки — красным в лог
  - новые ветки разбора: CMD_PING, CMD_WHO_AM_I
- **`CMakeLists.txt`**: qwake → qltp

### Верификация (host, gcc)

- CRC тест-вектор `"123456789"` → **0x29B1** ✅
- Round-trip build→parse: пустой payload, 300 байт со спецбайтами C0/DB, два пакета подряд ✅
- Битый CRC → отброс + ресинхронизация; мусор/ложный escape → восстановление ✅
- LEN > MAX_PAYLOAD → отброс ✅
- Байт-в-байт сверка с независимой эталонной реализацией (Python):
  ```
  PING:               C0 8D 01 00 00 00 00 00 F5 9D
  ERR-ответ seq=0x1234: C0 8D 7F 03 34 12 01 00 01 0E 85
  stuffing-пакет:     C0 8D 1A 01 DB DC DB DC 03 00 DB DC DB DD 00 BF 5E
  ```

## ⚠️ Найдена неточность в спеке

`LTP_PROTOCOL_v1.0_RU.docx` §4.1: текст «заголовок 8 байт (от ADDR до LEN)» —
но ADDR(1)+CMD(1)+FLAGS(1)+SEQ(2)+LEN(2) = **7 байт**. Таблица позиций в той же
спеке однозначна (PAYLOAD с позиции 8, считая FEND=0) — реализовано по ней:
**7 байт заголовка после FEND**. При случае поправить текст спеки.

## 📌 На будущее: технологический блок (стенд) — В ТЗ ПОКА НЕ ВНОСИТЬ

Со слов пользователя (11.06.2026), изменения внесём позже «всё разом»:
- назначение: управление шаговыми двигателями, **2 канала**, готовые силовые драйверы
- скорость вращения = частота импульсов на драйвер; шаговик 200 шагов/оборот + дробление шага
- контроллер: **Nucleo-L476**, подключение к ПК через VCP (виртуальный COM ST-Link)
- команды: установить скорость 0–max
- открытые вопросы (заданы, ответа пока нет): протокол Nucleo (перевод на LTP?),
  единицы в UI (об/мин ↔ Гц), направление/рампа/профили испытаний
- **топология**: VCP Nucleo — единственный порт к ПК; Nucleo анализирует команды:
  свои (управление шаговиком) обрабатывает, чужие ретранслирует на второй UART →
  сервисный разъём, куда подключён регистратор (там же программатор Nucleo).
  На линии **два устройства** за одним COM-портом
- следствие: схема 1-в-1 повторяет BLE-ретранслятор из ТЗ §1.1 — маршрутизация
  по ADDR пакета LTP. Предложение адресов: Nucleo (стенд) = 0x8C, регистратор = 0x8D,
  удалённый через BLE = 0x8E. В LOGLSMW второй порт НЕ нужен — только выбор цели
- для LOGLSMW это вкладка «Стенд», физическое подключение то же
- **была пробная программа управления стендом**: отрабатывала временные интервалы
  запуска шаговиков с различной скоростью (циклограммы испытаний) и вела лог:
  начало/конец рабочего цикла, длительность, скорость. Этот функционал — прообраз
  вкладки «Стенд»: профили (скорость + длительность) и журнал циклов
- **главная боль старого подхода**: проверка регистратора шла сравнением двух логов
  (лог регистратора + лог стенда) — два устройства, разные форматы, ручная сводка.
  Всё было видно, но крайне неудобно
- **следствие для LOGLSMW**: единый журнал испытания с общей шкалой времени ПК —
  приложение само пишет циклы стенда И данные регистратора в один файл/таблицу;
  автоматическое сопоставление «задал ↔ измерил» (стенд задал N об/мин ↔ гироскоп
  регистратора показал соответствующие dps), отчёт по испытанию одним документом.
  Это сильный аргумент единой системы на LTP-адресации через один порт
- подтверждено пользователем: регистратор и отладочный стенд сознательно вешаются
  на одну линию ради одновременного управления и одновременного лога
  («что даёт регистратор» ↔ «что реально на стенде»)
- **две части программы (две редакции)**:
  1) **основная** — эксплуатация устройства: считывание данных, вывод основных
     параметров, установка времени, активация устройства для передачи в эксплуатацию;
  2) **расширенная** — полное тестирование (стенд, мониторинг, Flash и т.д.),
     входит только в полную версию.
  **Решение пользователя**: одна сборка, инженерная часть скрыта и открывается
  ключом — так удобнее на старте; отдельную lite-сборку можно сделать в конце

## Обсуждение основного окна (операторский режим) — решения

- Оператор без вкладок: один экран-дашборд. Паспорт устройства (4 карточки:
  тип/IMU, время с контролем расхождения с ПК, температуры, заполненность памяти)
  + 3 крупных действия + журнал полосой внизу + статусбар с индикатором режима
- Инженерный режим: Сервис → ключ → появляются вкладки (Команды, Мониторинг,
  Flash, Стенд, Настройки); дашборд становится первой вкладкой
- **«Активировать» = мастер-чеклист**: операции автоматически одна за другой,
  у каждой индикатор успеха; на ошибке — стоп, причина, «Повторить»;
  итоговый протокол активации в журнал (акт ввода в эксплуатацию).
  Шаги (6): 1) проверка устройства (WHO_AM_I + датчики, идентификация в протокол)
  2) синхронизация времени 3) очистка памяти 4) проверка записи
  5) старт регистрации (0x1D) 6) контроль перехода в WORK.
  Отдельный шаг «связь» убран (избыточен — паспорт уже заполнен)
- **Автопоиск порта**: перебор всех COM-портов (открыть 921600 → PING 0x8D →
  таймаут ~200 мс); найден — зелёный индикатор с именем устройства; список портов
  остаётся для ручного выбора; последний удачный порт в QSettings проверяется первым;
  в будущем ping и 0x8C (стенд) — индикация, кто найден на линии
- **Модель активации уточнена (аналогия «разбег по полосе»)**: активация = предполётная
  проверка + постановка на готовность; устройство ОСТАЁТСЯ в SERVICE и на связи.
  «Взлёт» = оператор отключает кабель → WKUP1 пропало → PASSIVE → движение → WORK.
  Шаги (финал R17): 1) **считывание данных = автоархив** (кнопка «Считать данные»
  УБРАНА с окна — архивация гарантированная, автоматическая, без оператора;
  пока данные не считаны, сектор 1 не зелёный — «самолёт к взлёту не готов»)
  2) проверка устройства 3) синхронизация времени 4) очистка памяти
  5) проверка записи 6) постановка на готовность. Все зелёные = «отключите кабель».
  Кнопка действия (R18–R20): большая кнопка УБРАНА; пуск активации — малая кнопка
  34×14 (высота = высоте сектора) справа от полосы, «▶», зеленеет при готовности.
  Подсказка под секторами убрана; журнал 3 строки; статусбар мелким моно (10px).
  Идея на будущее (поддержана пользователем): готовность как ЖИВОЙ статус —
  если во время/после активации параметр вышел из нормы → ТРЕВОГА (alarm),
  сектор гаснет, готовность снимается. Реалистичные триггеры: отказ датчика,
  температура вне нормы, появление данных в памяти (часы за минуты не уйдут —
  замечание пользователя).
  Программа детектирует снятие с линии по пропаже ответов («устройство снято»).
  ⚠ Доработка firmware: 0x1D сейчас сразу QUIT из Service() — переделать на
  «взвести флаг готовности, остаться в SERVICE до снятия питания»
- **Считывание данных, вариант 1 (только вариант B, USB)**: устройство прикидывается
  флешкой — USB MSC с виртуальной read-only FAT, один файл LOG.BIN поверх P25Q128;
  слив штатным проводником, ~20–30 с на 16 МБ. Возможен composite MSC+CDC
  (флешка + LTP одновременно). Для варианта A — только выгрузка по UART через приложение
- **Принцип «минимум манипуляций оператора» + автоархив**: при подключении устройства
  программа АВТОМАТИЧЕСКИ создаёт архивную запись: журнальная часть (паспорт, время,
  температуры, события сеанса) + приложение — полное содержимое Flash (если есть данные).
  Фоном, с прогрессом в статусбаре. Предложенная структура:
  `Archive/<устройство>/<дата_время>/journal.txt + flash.bin` (путь в настройках)
- Вопрос стирания закрыт: данные всегда в архиве с момента подключения →
  активация стирает память автоматически, без подтверждений.
  Цикл оператора: подключил → (автоархив) → «Активировать» → отключил кабель
- **Правило (жёсткое)**: после автоархива память свободна — любые разрушающие
  операции (стирание, тесты записи, переразметка) разрешены ТОЛЬКО при наличии
  архива текущего содержимого; программа гарантирует это сама, инвариант
  действует и в инженерном режиме
- Сервисный кабель = дешёвый USB-UART адаптер; для комплекта рекомендовать
  CP2102/FT232 (CH340 на 921600 бод капризен)

### Индикаторы основного окна (обсуждение, решения)

1. **Время**: карточка с двумя живыми циферблатами — «Время ПК» (эталон) и
   «Регистратор» (опрос 0x1B раз в секунду в SERVICE). Без лишних строк:
   часы регистратора КРАСНЫЕ при расхождении, ЗЕЛЁНЫЕ при совпадении.
   При несовпадении в середине карточки — разница со знаком (не «Δ»):
   «−» регистратор отстаёт, «+» спешит; формат — две группы: минуты и секунды
   («−12 м 05 с»), шрифт мелкий. **Порог аварии настраиваемый** (Настройки,
   инженерный режим, default 10 мин): до 1 с — синхронно; 1 с..порог — реальное
   значение; больше порога — АВАРИЯ, моргающее красное «XX:XX»
   (часы сбиты, мгновенно отличается от обычного дрейфа);
   при совпадении середина пустая. Панель компактная (~300 px).
   Допуск: 1 с (точность RTC по 0x1B). Сравнение по полной дате-времени
   (не только часам). После шага синхронизации в активации зеленеет само.
   Кнопка «Установить время» убрана с основного экрана → только инженерный режим

2. **Наработка**: карточка — крупно суммарное активное время, под чертой
   «первый цикл» (дата+время начала) и «конец последнего». 
   ⚠ FRAM НЕ в базовой комплектации — счётчики в ней не делаем (решение пользователя;
   вернуться, только если FRAM попадёт в финальную конфигурацию).
   Реализация: firmware по окончании КАЖДОГО активного цикла вычисляет суммарное
   время и записывает свежее значение во Flash (новая запись каждый раз);
   при сбое теряется максимум незакрытый цикл — приемлемо.
   Для приложения — команда чтения статистики (GET_STATS, добавить в LTP).
3. **Память**: полоса красный/зелёный (красный = израсходовано, зелёный = остаток),
   единица зависит от режима записи:
   - **Logger**: ЧАСЫ — точные (поток 16 байт × ODR, прямая связь объём↔время):
     «записано 37 ч | осталось 118 ч»;
   - **Регистратор**: ЦИКЛЫ — точные (30 байт/запись, 16 МБ ≈ 558 тыс. циклов):
     «записано 41 230 циклов | осталось 517 000» (часы здесь невозможны: записей
     столько, сколько циклов, длительность цикла не влияет — отметил пользователь).
4. **Температура**: на основном экране ОДНО показание, по умолчанию — с IMU
   (LSM6DSO): заодно косвенная проверка главного датчика. TMP117 — опциональная
   периферия (как FRAM), не в базе. Выбор датчика — настройка инженерного режима.
   Все 3 термодатчика с контролем исправности (отклик + физпределы −40..+85 +
   взаимный разброс) — только в тестах: шаг активации «Проверка датчиков»
   и инженерный режим. Оператору лишнее не показывать.
5. **Готовность (активация)**: карточка-полоса из N секторов (N = число шагов
   активации, сейчас 6). До активации все красные («не активировано»); в процессе
   сектора зеленеют по одному, текущий мигает жёлтым, под полосой имя шага и %;
   ошибка — стоп, сектор красный, причина в подписи. Все зелёные =
   «ГОТОВ К РАБОТЕ — отключите кабель» (+ зелёная рамка). Tooltip на секторе — имя шага.
   **РЕШЕНО: только карточка, модального мастера-диалога НЕТ.** Верхняя строка
   карточки динамическая — тип текущей операции (не слово «Готовность»):
   «Не активировано» → «Проверка датчиков» → «Очистка памяти… 64 %» → … →
   «Готов к работе — отключите кабель». Активный сектор моргает, завершённый
   зелёный, далее моргает следующий. Одна поясняющая строка, без нагромождения.
   Детальный протокол — в журнале внизу экрана.
6. **Перспективные параметры статистики** (метод вычисления согласуем позже):
   максимальная скорость за все периоды, максимальный уровень вибрации за все
   периоды, **максимальная температура за все периоды** (добавлена при итерациях
   эскиза — показывается в правой колонке, секция «Температура → максимальная»).
   Открытые вопросы: «скорость» = обороты по гироскопу? «вибрация» =
   пик |a| / RMS / по какой оси?
   Правая колонка основного окна (финал R16): узкая карточка 190 px, 4 секции:
   Время (текущее/регистратор/разница), Рабочие циклы (записано/доступно —
   число ТОЧНОЕ, без «≈»), Температура (текущая/максимальная),
   **Перезапуски (по таймеру / по питанию)** — резерв под статусную информацию.
   Подписи слева мелким серым, значения справа моно жирным (правая колонка цифр).
   Полоса памяти убрана (отвлекает, смысла не несёт).
   Для firmware: счётчики перезапусков из RCC_CSR (причина сброса: IWDG/POR/BOR/SW),
   инкремент во Flash при старте → в GET_STATS вместе с максимумами.

  финальную полировку шрифтов делать в Qt, не в эскизе (браузер на дробных
  масштабах рендерит по-разному — пользователь подтвердил «пускай так пока»).
- Верхняя строка: [● 30×30 диагностика] [ВКЛ/COM3 56px] [карточка: выкл —
  «LOGLSMW · сервис регистратора», вкл — «LOGLSMA-регистратор»; без hex-кодов];
  правый край карточки выровнен с главной карточкой; шрифт = кнопке ВКЛ.

### Панель подключения — финал (итерации по mockup_main_window_v1.html)

- Кнопки «Подключить/Отключить» и текстовая строка состояния УБРАНЫ
- Две кнопки фиксированного размера: квадратная 30×30 (индикатор: зелёный/красный)
  + длинная 180 px («Поиск устройства» ↔ «COM3 · LOGLSMA»); повторное нажатие
  длинной = отключение
- Клик по квадратной кнопке-индикатору → диагностический список портов системы:
  каждый порт с результатом опроса («нет ответа» / «LOGLSMA 0x8D» зелёным /
  «занят другой программой»). Отдельного комбобокса портов НЕТ
- В диагностическом списке клик по порту = «закрепить» (📌): закреплённый порт
  проверяется первым при автопоиске (полезно при нескольких устройствах);
  хранится в QSettings
- Длинная кнопка ужата до 100 px, надписи: «Включить» ↔ «COM3» (кухня поиска скрыта)
- В диагностической панели вторая секция — «скорость подключения»: чипы
  921600 (default) / 460800 / 230400 / 115200; поиск идёт на выбранной скорости.
  Панель — чисто диагностический инструмент, оператор о ней может не знать
- Под панелью — карточка устройства одной строкой: LOGLSMA · адрес · IMU · режим · порт

## ИТОГИ ДНЯ (11.06.2026) — общая картина подключений

**Регистратор подключается к ПК всегда через виртуальный COM-порт**, двумя путями:

| Путь | Что подключено | Возможности |
|---|---|---|
| **USB-UART адаптер** (сервисный кабель) | только UART (XP2) | вся работа по LTP; программатора НЕТ → **прошивка загружается через COM-порт** (не забыть: загрузчик!) |
| **Через стенд** (Nucleo-ретранслятор, VCP) | UART + **программатор** (ST-Link Nucleo) | вся работа по LTP + штатная отладка SWD |

- Оба сервисных разъёма могут подключаться к стенду через **вращающуюся контактную
  муфту** на оси шагового двигателя стенда → отладка и проверка инерциальных
  датчиков ПРЯМО ВО ВРАЩЕНИИ, с живой связью и отладчиком
- **РЕШЕНИЕ по загрузке прошивки (склоняемся)**: собственный загрузчик поверх LTP.
  Обоснование: при тестировании всегда можно прошить программатором; полевое
  обновление — через LTP-загрузчик без манипуляций с BOOT.
  Прецедент в доках: `Doc/LogLSM Transport Protocol/TMP/PROJECT_STRUCTURE.md`
  уже содержит `/Bootloader/bl_ltp.c` и `ota_service.c` — идея закладывалась изначально.
  Справочно: у LOGLSMB пин BOOT разведён — штатно GND (программатор/нормальный старт),
  на +VDD — системный загрузчик STM32 (резервный путь восстановления).
- **Одна программа для обоих устройств** (стенд + регистратор), работают
  ПАРАЛЛЕЛЬНО на одной линии — подтверждено пользователем
