### 🔥 КРИТ. ФИКС ЗАВИСАНИЯ (A 14:19) — не хранить ts во внутр. Flash в горячем пути
Прибор перестал отвечать («не отвечает», перепрошивка НЕ лечила). Причина — МОЯ правка:
`ts_activation` хранился на внутр. Flash стр.121 и **читался в GET_STATS при КАЖДОМ
опросе (~5с)**. Полевой срыв питания (батарейка в зажиме + вибрация, см. iflash.h)
мог оставить стр.121 в БИТОМ ECC → любое чтение = NMI/hardfault → зависание на каждом
GET_STATS; обычная перепрошивка не стирает стр.121 → не лечит. **Лечение прибора:
STM32CubeProgrammer → Full chip erase → прошить A 14:19** (подтверждено — ожил).
**Фикс в коде:** `ts` → ОЗУ (`s_actts`, `actts_read/write/clear`), внутр. Flash в
GET_STATS больше НЕ читается; убран автовзвод флага стр.122 из `Data.c::SaveParamOnEEPROM`
(единственная автономная внутр.-Flash операция в поле). Флаг стр.122 теперь пишет только
приложение (CYCLE_PUSH / 0x30=4 при загрузке образа) — на кабеле, питание стабильно.
**Открыто:** `ts` теперь НЕ переживает перезагрузку (метка «Активация» слетает при
питании). Безопасное энергонезависимое хранение — ОТДЕЛЬНО и НЕ в периодически читаемой
внутр. Flash (варианты: NOR служебная стр.0 / FRAM / писать в iflash но НЕ читать в
горячем пути + provision-стирание на старте). Урок: внутр. Flash STM32 — только
редкое чтение вне периодики; запись — с защитой от прерывания питанием.

### ✅ БАГ ДАМПА ЗАКРЫТ (W 13.59) — было переполнение quint16
Дамп сохранял 1 страницу вместо всех. Причина: `ActDumpState::pageEnd` был `quint16`, а
`m_actDump.pageEnd = quint16(kFlashTotalPages)` = quint16(65536) = **0** (переполнение).
Тогда `finish = allFF || (page+1 >= pageEnd)` → `2 >= 0` истина → стоп после 1-й стр.
Диагностика `[dump]` показала: `стр.1 allFF=0` → сразу «сохранён (1 стр.)», стр.2 нет.
ФИКС: `pageEnd` → `quint32` (mainwindow.h), убран `quint16()`-каст (mainwindow.cpp
startDataDump), диагностический лог убран. Теперь самотерминация по первой пустой (0xFF)
странице работает верно — читает все занятые. ⚠ подтвердить на железе (52 стр. → HEX ~13 КБ).

## Что сделано в этой сессии — УСКОРЕНИЕ ЧТЕНИЯ ФЛЕША (готово, работает)

**Задача:** минимальное время считывания — приоритетный потребительский параметр.

1. **Разгон Сервиса до 80 МГц** (было; PLL, `ServiceClock_Config`). Рабочий
   режим — 16 МГц HSI, не тронут. Флеш-делитель QSPI по умолчанию 255 (~312 кГц),
   команда 0x2C ставит 80/40/20/10/5 МГц (индексы 0..4).
2. **memory-mapped чтение** (главное). Причина прежнего потолка ~820 КБайт/с —
   `HAL_QSPI_Receive` вычитывает FIFO CPU-поллингом (упор в процессор, не в
   линию). Решение: `P25Qx_MemMapped`/`P25Qx_ExitMemMapped` (p25q128.c/.h) —
   флеш проецируется в `0x90000000`, контроллер сам качает по AHB. НЕ требует
   DMA-канала/правки .ioc. Замер 0x2D читает область непрерывным бёрстом.
   **Результат: ~13 МБайт/с (SPIx4@80), ×16 к прежнему; 16 МБ: 20 с → 1.2 с.**
3. **Критерий целостности:** чтение сверяется с эталоном `buf[i]=i` (ramp).
   Не сошлось → «ошибка (данные)» = частота/режим для чтения ненадёжны.
4. **Кнопка «Скорость» — самодостаточна, двухфазная** (mainwindow.cpp): 1-е
   нажатие пишет эталон на БЕЗОПАСНЫХ 10 МГц+quad с verify, затем читает на
   ВЫБРАННОЙ конфигурации и сверяет; дальше только читает. Члены класса:
   `m_speedRefReady/m_speedPhase/m_speedRefStart/m_speedRefPages`. Кнопка сама
   применяет выбранные SPI+МГц (0x2B+0x2C) перед замером → артефакт «152»
   (неприменённый делитель) устранён. Дефолт списка = SPIx4.
5. Прошивка (A) без изменений с 00:10 по сути — 00:45 только бамп версии.

**Замеренные факты (важно для понимания):**
- read CPU-word-loop bound на высокой частоте: **40 и 80 МГц дают одинаково
  ~13.5 МБайт/с** (обе быстрее, чем CPU успевает забирать); ниже ~25 МГц —
  линия-bound (20 МГц ≈ 9.7, 10 ≈ 4.8). Чтобы обогнать 13.5 → **mem-to-mem DMA**.
- **Транспорт — реальное узкое место:** UART 921600 ≈ 90 КБайт/с (16 МБ ≈ 3 мин);
  USB VCP (плата B, USB FS) ≈ 1 МБайт/с (≈16 с, ×10); флеш 13 МБайт/с раскрылся
  бы только на USB HS (у L433 нет). Флеш-скорость гарантирует, что флеш не узкое
  место, реальный выигрыш выгрузки — переход на USB VCP.
