# LogLSM — Форматы хранения данных

**Статус: финал, согласовано 19.06.2026**
Документ для включения в итоговый отчёт. Источник: `data_format_spec_v1.md`
(рабочая спецификация с историей решений — `session_notes_2026-06-19_logger_format.md`,
`session_notes_2026-06-19_registrator_format.md`).

Применимость: оба варианта контроллера (LOGLSMA, LOGLSMB), все варианты плат расширения.

---

## 1. Общая архитектура хранения

Данные хранятся в NOR Flash P25Q128H (16 МБ), запись — только в предварительно
стёртые ячейки (`0xFF`). Стирание выполняется только в сервисном режиме при
подключении к ПК; в рабочем и пассивном режимах устройство только дописывает
данные в чистые адреса.

Минимальный физический блок записи — **256 байт** (одна страница NOR Flash).

Устройство поддерживает два независимых режима регистрации с принципиально
разным потоком данных:

| Режим | Что пишет | Объём на событие |
|---|---|---|
| **Регистратор** | Один итоговый «сэмпл цикла» раз в цикл вращения | 28 байт |
| **Logger** | Непрерывный поток сырых сэмплов IMU постранично | до 256 байт/страница |

---

## 2. Регистратор — структура записи (28 байт)

### Идеология

Регистратор не хранит сырые сэмплы IMU — они обрабатываются на лету (отдельный
вычислительный контур), и в Flash попадает только один компактный итоговый
сэмпл цикла: начало, конец, экстремумы. Признак цикла — наличие вращения.
Поскольку записей мало (раз в цикл) и они не конкурируют за место с потоком
сэмплов, никакой фрейм/type-byte машинерии (как в Logger) не требуется — запись
всегда одной и той же фиксированной структуры.

### Структура записи

| Поле | Размер | Формат | Примечание |
|---|---|---|---|
| timestamp_start | 32 бита | uint32 | Unix timestamp начала цикла |
| timestamp_end | 32 бита | uint32 | Unix timestamp конца цикла |
| duration | 32 бита | uint32 | Длительность текущего цикла, с |
| duration_total | 32 бита | uint32 | Накопительная длительность по всем циклам устройства |
| MAX_vibration | 32 бита | float32 | Максимальная ВЧ-вибрация за цикл, g |
| MAX_RPM | 32 бита | float32 | Максимальная скорость вращения за цикл, об/мин |
| temperature | 8 бит | uint8 | Целый °C, смещение −60: `°C = raw − 60` (диапазон −60…195, рабочий −60…190) |
| status | 8 бит | uint8 | биты[2:0] = `voltage_zone` (0..7), биты[7:3] резерв |
| CRC | 16 бит | uint16 | CRC записи; `0xFFFF` = запись не завершена |

**Итого: 6 × 4 + 1 + 1 + 2 = 28 байт.**

### Сжатие диагностических полей

Температура и напряжение батареи — диагностические поля, не основной измеряемый
результат, поэтому для них не действует правило «всё по 32 бита»:

- **temperature** — uint8 целый градус Цельсия со смещением −60. Точность
  0.01°C избыточна; промежуточный вариант 0.1°C экономии не даёт — в 1 байт
  (256 значений) при таком шаге влезает только ~25.6°C, чего недостаточно для
  рабочего диапазона. Диапазон −60…190°C несимметричен относительно нуля
  (горячий хвост шире холодного — реальные условия у оси колеса), поэтому
  выбран смещённый uint8, а не симметричный int8.
- **battery_voltage** как числовое значение убрано полностью: замеры напряжения
  без нагрузки не объективны, точное значение в рабочем цикле не нужно (при
  необходимости измеряется напрямую в сервисном режиме). Вместо числа — грубая
  **3-битная зона `voltage_zone`** (0..7) в поле `status`: диапазон 2.9–3.6 В,
  шаг 0.1 В, с насыщением по краям (`≤2.9 В → 0`, `≥3.6 В → 7`). Диапазон
  подобран под профиль разряда элемента LS14250 (Li-SOCl₂): почти всю жизнь
  батареи напряжение держится у верхней границы, разрешение нужно только в
  «интересном» нижнем хвосте перед истощением. В RAM за цикл хранится
  минимальная зона, увиденная за цикл (худший случай перекрывает
  кратковременные просадки под нагрузкой).

MAX_vibration и MAX_RPM остаются float32 — это содержательные измеренные
величины, а не диагностика.

### Схема записи — stub + дозапись

1. **Начало цикла:** записывается stub — только `timestamp_start`, остальные
   28 байт записи — `0xFF`. `write_ptr` сдвигается на 28 байт сразу (резерв
   места под дозапись).
2. **Во время цикла:** MAX_vibration, MAX_RPM, temperature накапливаются в RAM;
   `voltage_zone` — минимум зоны, увиденный за цикл.
3. **Конец цикла (штатный):** поля дозаписываются в порядке `timestamp_end →
   duration → duration_total → MAX_vibration → MAX_RPM → temperature → status
   → CRC`. CRC пишется последним — финальная «печать» завершённости записи.
4. **duration_total пишется рано** (сразу после `duration`) специально для
   надёжности: при аварии в середине backfill накопительный итог почти всегда
   успевает сохраниться на Flash, даже если остальная запись осталась неполной.
5. **Завершение страницы:** после записи CRC `write_ptr` переходит на начало
   следующей страницы Flash. 1 запись = 1 страница; неиспользуемые 228 байт
   страницы остаются `0xFF` (≈0.0014% потерь от 16 МБ Flash).
6. **Обнаружение незавершённых записей:** запись с `CRC == 0xFFFF` —
   прерванный цикл (сбой питания/сброс); `timestamp_start` при этом сохранён.
7. **Источник накопительного duration_total:** отдельной ячейки состояния нет.
   При backfill читается `duration_total` последней записи, где поле физически
   записано (≠ `0xFFFFFFFF`) — благодаря раннему расположению поля это, как
   правило, просто предыдущая запись, даже неполная по CRC. Если такой записи
   нет (первый цикл устройства) — база 0.

## 3. Logger — типология фреймов (потоковая регистрация)

### Идеология

Logger формирует непрерывный поток сырых сэмплов IMU в течение рабочего цикла.
1 фрейм = 1 страница Flash (256 байт), фреймы пишутся строго вперёд, без
возврата. Программное масштабирование не используется — вместо него работает
аппаратный auto-range IMU.

### Термины

| Термин | Размер | Что это |
|---|---|---|
| Сэмпл | 12 байт | Ax/Ay/Az/Gx/Gy/Gz — 6 каналов × 16 бит, полная разрядность |
| Фрейм | 256 байт | 1 страница Flash, типизированный контейнер |
| Цикл | N фреймов | Данные одного рабочего цикла (от начала до конца вращения) |

### Базовый принцип

Байт `[0]` каждого фрейма — тип. `0xFF` = чистая память (конец записанных
данных). Типы — линейный список фиксированных констант без битовой кодировки.

### Список типов фреймов

| Байт | Тип | Назначение |
|---|---|---|
| `0xFF` | чистая память | не фрейм, конец записанных данных |
| `0xFE` | ЗАГОЛОВОК | полные метаданные начала цикла (без экономии страницы) |
| `0xFD` | ДАННЫЕ | обычный фрейм сэмплов |
| `0xFC` | СТАРТ+Д+T0 | сэмплы + старшая часть часов на старте цикла (экономия страницы) |
| `0xFB` | СТАРТ+Д+T1 | сэмплы + младшая часть часов на старте цикла |
| `0xFA` | ДАННЫЕ+E1 | сэмплы + температура+статус батареи (периодическое обновление, 2 байта) |
| `0xF9` | *свободно* | освобождено объединением бывших E1/E2 в один тип (см. ниже) |
| `0xF8` | ДАННЫЕ+E3 | сэмплы + старшая часть часов в момент записи (чекпойнт восстановления) |
| `0xF7` | ДАННЫЕ+E4 | сэмплы + младшая часть часов в момент записи (чекпойнт восстановления) |
| `0xF6` | СТОП | штатное завершение цикла: точная длительность + накопительный итог |

Цикл начинается одним из двух способов (выбор по ситуации, формат не
ограничивает):
```
Вариант А (полные метаданные):  [0xFE] [0xFD] [0xFD] ...
Вариант Б (экономия страницы):  [0xFC] [0xFB] [0xFD] [0xFD] ...
```

### Layout фреймов

**ЗАГОЛОВОК (`0xFE`)**
```
[0]       0xFE
[1..4]    unix timestamp начала цикла (uint32)
[5]       температура (uint8, целый °C, смещение −60: °C = raw − 60, диапазон −60…195)
[6]       status (uint8: биты[2:0] = voltage_zone, биты[7:3] резерв)
[7]       тип датчика (0 = DSO/вариант A, 1 = DSV/вариант B)
[8]       ODR-байт: показатель степени относительно ODR_base
[9]       FS-байт: AccelExp[2:0] | GyroExp[2:0]
[10..255] 0xFF резерв (новые поля добавляются последовательно сюда)
```

**ДАННЫЕ (`0xFD`)**
```
[0]        0xFD
[1]        FS-байт: AccelExp[2:0] | GyroExp[2:0]
[2..253]   до 21 сэмпла × 12 = 252 байта
[254..255] 0xFF резерв (или занято в вариантах ДАННЫЕ+E)
```

**СТАРТ+Д+T0 / СТАРТ+Д+T1 (`0xFC` / `0xFB`)**
```
[0]        0xFC или 0xFB
[1]        FS-байт
[2..3]     T0 (старшая часть часов старта) или T1 (младшая часть)
[4..251]   до 20 сэмплов × 12 = 240 байт (1 сэмпл отдан под экономию страницы)
[252..255] 0xFF резерв
```
T0/T1 — части одного 32-битного значения часов (RTC/unix timestamp), снятого
на старте цикла; та же кодировка, что у E3/E4 (отличается только момент снятия).

**ДАННЫЕ+E1 / +E3 / +E4 (`0xFA`/`0xF8`/`0xF7`)**
```
[0]        тип (один из E1, E3, E4)
[1]        FS-байт
[2..253]   до 21 сэмпла × 12 = 252 байта (сэмпл не теряется — занимаем штатный резерв)
[254..255] значение E
```
- **E1** — температура+статус батареи: `[254] temperature (uint8, целый °C,
  смещение −60, диапазон −60…195)`, `[255] status (uint8: биты[2:0] =
  voltage_zone, биты[7:3] резерв)` — тот же 2-байтовый формат, что в
  ЗАГОЛОВКЕ и в Регистраторе.
- **E3** — старшая часть часов (тот же источник/формат, что T0).
- **E4** — младшая часть часов (тот же источник/формат, что T1).

Назначение E1/E3/E4 — чекпойнты для восстановления после сбоя/сброса/потери
питания: последний успешно записанный ДАННЫЕ+E восстанавливает последнее
известное состояние без штатного завершения цикла.

**Объединение бывших E1+E2 в единый E1.** Изначально температура (E1) и
напряжение батареи (E2) занимали два отдельных типа фрейма по 2 байта каждый.
После пересмотра упаковки этих полей в Регистраторе (temperature → uint8 со
смещением, напряжение → 3-битная зона) оба значения стали укладываться в те же
2 байта вместе — отдельный тип E2 больше не нужен, константа `0xF9` освобождена.
Один код сериализации temp+status используется и в ЗАГОЛОВКЕ/E1 Logger, и в
Регистраторе.

**СТОП (`0xF6`)**
```
[0]        0xF6
[1]        FS-байт
[2..241]   20 сэмплов × 12 = 240 байт (1 сэмпл отдан под доп. данные)
[242..245] длительность текущего цикла (uint32, секунды)
[246..249] суммарная длительность по всем циклам устройства (uint32, секунды)
[250..255] 0xFF резерв
```
Пишется только при штатном завершении цикла: ОЗУ не теряется, поэтому
длительность считается точно (часы_стоп − часы_старт) и пишется готовым
числом. Суммарная длительность — накопительный счётчик по всем циклам
устройства; прочитав последний записанный СТОП-фрейм, можно сразу получить
суммарный наработанный ресурс без сканирования всей истории (тот же принцип,
что у `duration_total` в Регистраторе — отдельной ячейки состояния нет).

### Масштабирование — аппаратный auto-range

IMU сам переключает Full Scale (FS) диапазон — аппаратный аналог программного
масштабирования. Поскольку шаги изменения чувствительности (accel и gyro)
кратны 2, FS-байт хранит показатель степени (экспоненту) относительно базового
диапазона:
```
FS-байт: AccelExp[2:0] | GyroExp[2:0]   — 6 бит заняты, 2 бита резерв
LSB_actual = LSB_base(датчик, канал) × 2^Exp
```
ODR-байт в ЗАГОЛОВКЕ кодируется тем же способом: `ODR = ODR_base × 2^Exp`.
Таблицы констант `LSB_base`/`ODR_base` для обоих датчиков (LSM6DSO-MOD,
LSM6DSV320X-MOD) — открытый пункт, см. раздел 5.

### Конец данных в последнем фрейме цикла

Парсер читает сэмплы, пока не встретит 12 байт `0xFF` подряд — это конец
данных в этом фрейме. Если реальный сэмпл оказался бы весь `0xFF` (коллизия с
сентинелом), firmware вычитает 1 из любого канала перед записью этого сэмпла.

## 4. Обоснование надёжности

| Сценарий | Регистратор | Logger |
|---|---|---|
| Штатное завершение цикла | Stub на Flash с начала цикла, дозапись полей при завершении (28 байт) | Пишется фрейм СТОП с точной длительностью и накопительным итогом |
| Сбой питания / reset во время цикла | CRC=`0xFFFF` → запись помечается неполной; `timestamp_start` и, как правило, `duration_total` успевают сохраниться | Восстановление по последнему записанному фрейму (в т.ч. ДАННЫЕ+E1/E3/E4 — температура/напряжение/часы) |
| Дребезг контактов батареи (<10 мс) | Компенсируется буферным конденсатором (полимерный танталум 470 мкФ + резистор 3.3 Ом) | Аналогично |
| Накопительный наработанный ресурс | `duration_total` в каждой записи — без сканирования истории | Аналогичное поле в каждом фрейме СТОП — без сканирования истории |

## 5. Открытые вопросы

- Таблицы `LSB_base`/`ODR_base` (акселерометр, гироскоп) для датчиков LSM6DSO-MOD
  и LSM6DSV320X-MOD — взять из даташитов, не табулированы.
- Резерв 5 бит `status[7:3]` (Регистратор и Logger) — не распределён, оставлен
  для будущих диагностических флагов.
- Обновление `build_tz.js` и пересборка `LogLSM_TZ_v4_consolidated.docx` под
  оба формата — не выполнено.
- USB MSD-эмуляция + переключение в VCP при подключении по USB — отдельная
  тема, вынесена на будущую сессию (не входит в формат данных).
