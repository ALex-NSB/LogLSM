## 1. Терминология «Тест» vs «Работа» — зафиксировано (не переоткрывать)

Два вида тестирования режимов работы регистратора = **две разные команды**:

- **Работа** (`CMD_START_REGISTER` 0x1D) — рабочая программа СО сном:
  автомат SLEEP→CONFIRM→ROTATING, в фазе SLEEP уходит в сон, связь с ПК на
  время сна теряется, наружу — только `CMD_CYCLE_PUSH` после каждого цикла.
- **Тест** (`CMD_START_TEST` 0x23, НОВАЯ) — та же рабочая программа БЕЗ сна:
  контроллер всё время на связи. В фазе SLEEP не спит, а бодро крутится с
  `ComPoll()` и ловит фронт INT1/WKUP2 **опросом флага WUF2 на ходу** (тот же
  фронт, что будит из сна в «Работе», — но здесь виден как факт «прерывание
  пришло», под контролем). Всё остальное общее: детект → CONFIRM → ROTATING
  → анализ цикла → запись во Flash → пуш.
- **Стоп для обоих — общий `CMD_STOP_REGISTER` (0x22)** (снимает
  monitoringActive и testNoSleep, закрывает идущий цикл → возврат в Service).

**Ценность «Теста»:** контроллер бодр → своими глазами видно, что нужное
прерывание при пробуждении реально приходит (в «Работе» на ULTRA_LOW_POWER
не срабатывало), и колонка «Регистратор» заполняется в реальном времени.

## 2. Сон в «Работе» = STANDBY, НЕ Stop2 — исправлено противоречие в CLAUDE.md

Пользователь «в который раз» уточнил: глубокий сон рабочего цикла — целевой
**Standby 280 нА с RTC** (даташит: 280 nA Standby with RTC против 1.0/1.28 µA

пауз. Причина повторов — таблица «Режимы работы» в CLAUDE.md говорила
«PASSIVE = MCU в Stop2», что расходилось с согласованной целью.

**Исправлено в CLAUDE.md:** строка PASSIVE переписана, добавлен блок
«⚠️ Сон в „Работе“: Standby, НЕ Stop2» + подраздел «Тест vs Работа».
Зафиксировано: выход из Standby = сброс МК (ОЗУ теряется, восстановление по
backup-регистрам + Flash-stub — перенос `reset.c` из rp_device ещё TODO);
из Standby будит только WKUP-пин / RTC / сброс (EXTI не работает) — поэтому
**оба пина PA0/PC13 в .ioc заведены как SYS_WKUP1/SYS_WKUP2** (проверено в
`LOGLSMA.ioc`: `PA0.Signal=SYS_WKUP1`, `PC13.Signal=SYS_WKUP2`), EXTI на них
НЕ заводить. (Мой ранний план «оживить EXTI15_10» отменён — не нужен, WUFx
латчится и в Run-режиме, поэтому в «Тесте» флаг просто опрашивается.)

Текущая прошивка = только Stop2 (средний ярус). Standby-ярус (вход по
таймауту бездействия, восстановление по backup/stub) — по-прежнему TODO.

## 3. Прошивка LOGLSMA — режим «Тест» (0x23)

- `RegistratorData.testNoSleep` — новое поле (Data.h). Инициализация `0` в
  `main.c` (USER CODE BEGIN 2, рядом с monitoringActive=0).
- `CMD_START_TEST = 0x23` в таблице `CMD[128]` (com.c) + `cmdStartTest()`:
  как `cmdStartRegister`, но `testNoSleep=1` и чистый «взвод» —
  `__HAL_PWR_CLEAR_FLAG(WUF1/WUF2)` (чтобы стартовать с ожидания СВЕЖЕГО
  фронта, а не сработать на старый флаг). `cmdStartRegister` теперь явно
  ставит `testNoSleep=0`; `cmdStopRegister` снимает `testNoSleep=0`.
- `main.c`, ветка SLEEP — развилка: `if (monitoringActive && testNoSleep)` —
  НЕ входим в Stop2, а бодро: `ComPoll()` (при кабеле) + `WUF1`→стоп
  (monitoringActive=0 → Service), `WUF2`→гироскоп+CONFIRM. Иначе (`else`) —
  прежний реальный Stop2. Структура скобок проверена.
- **Проверено на железе (04.07):** «Тест» гоняет цикл, колонка
  «Регистратор» на «Стенде» заполняется (Старт/Стоп/Интервал/Общее/Скорость
  по каждому циклу). Цепочка 0x23 → автомат без сна → WUF2/CONFIRM → анализ
  → Flash → пуш прошла целиком.
- **ОТКРЫТО (отложено пользователем «потом рассмотрим»):** дельты/«Ошибка»
  больше прежних — «Общее» копит −10 с за цикл, «Скорость» расходится
  (видел +19.0% / +6.8% на скриншоте). Разобрать отдельно.

## 4. LOGLSMW — «Тест»

- `LtpCmd::START_TEST = 0x23` (devicecontroller.h).
- `stendStart(noReg=true)` («Тест») теперь шлёт `START_TEST` (0x23) ПЕРВЫМ,
  мотор стартует из `stendKickoff()` по ACK (как «Работа» по 0x1D). Опросы
  0x8D НЕ подавляем (устройство на связи — гейты по `!m_stendNoReg`), пуши
  `CYCLE_PUSH` приходят → колонка «Регистратор».
- ACK 0x23 и его таймаут обработаны (onResponse/onRequestFailed, оба
  START_REGISTER|START_TEST).
- `stendStop`: `STOP_REGISTER` (0x22) теперь шлётся для ОБОИХ видов (прежде
  был гейт `if (!m_stendNoReg)` — в старом noReg регистратор не запускался;
  теперь «Тест» запускает автомат, стоп нужен). В «Тесте» устройство
  бодрое → 0x22 доходит без таймаута.
- Приём CYCLE_PUSH безусловный; база «Общей» (`m_preTestRegTotS`) защищена
  гейтом `!m_stendActive` в обработчике GET_STATS — повторный опрос во время
  «Теста» её не затрёт.

## 5. Прошивка — курсор записи Flash БЕЗ кэша (важный принцип)

Пользователь: **всегда использовать алгоритм поиска первой свободной
страницы, кэш не вести, питание не передёргивать.** Причина: после внешнего
стирания чипа старый прошивочный курсор (`s_writePage`/`s_writeSlot`
кэшировались до перезагрузки МК) продолжал писать «за 100-й страницей».

Исправлено (Data.c):
- `SaveParamOnEEPROM` вызывает `flashFindWritePos()` при КАЖДОЙ записи (был
  гейт `if (s_writePage==0)`), локальный инкремент позиции убран — следующий
  вызов находит первую свободную позицию сам.
- `LoadTotalSec` — тоже всегда `flashFindWritePos()` (без гейта).
- Следствие: стёр чип → следующая запись цикла сама уходит на стр. 1, БЕЗ
  перезагрузки/передёргивания. Записи редкие (раз в цикл), цена скана
  несущественна. (Скан линейный, читает 4 байта заголовка каждой страницы;
  бинарный поиск — только на стороне LOGLSMW, `flashBinSearch`.)

Наблюдение по ходу: образ 100 страниц был на чипе, «Тест» дописал циклы
дальше — это нормально (курсор = первая свободная страница).

## 9. Панель «Стенд»: лок-степ вывода + «нет ответа» (подтверждено на железе)

**Проблема (по скриншотам):** колонка «Регистратор» съезжала на один цикл —
данные пуша показывались напротив НЕ своего стенд-цикла (reg-время/скорость
совпадали со СЛЕДУЮЩИМ циклом). Плюс «2 неполных столбца»: стенд бежал
вперёд, показывая следующий цикл до прихода результата по текущему.

**Корень:** матчинг `stendFillRegColumn` чисто позиционный («первый
незаполненный завершённый цикл»). Один пропущенный пуш (регистратор не
поймал вращение) → следующий пуш падал в чужую строку → весь столбец ехал.

**Модель пользователя (лок-степ, по одному циклу):** вывели параметры
цикла (левая колонка) → ждём результат → пришёл пуш → заполнили правую →
и ТОЛЬКО потом выводим следующий цикл. В любой момент — максимум одна
ждущая строка.

**Реализация (LOGLSMW, только вывод панели):**
- `StendCycleRecord.regNoAnswer` (mainwindow.h) — новый флаг «пуша так и не
  было».
- `stendResolvePendingReg()` — вызывается в `stendBeginWork` и
  `stendNextNStartStop` НА СТАРТЕ следующего цикла, ДО добавления новой
  строки: если по предыдущей завершённой строке пуша нет → `regNoAnswer=1`
  (регистратор пропустил цикл), строка закрывается.
- **Точка решения «пришёл/не пришёл» = старт следующей «Работы»** (пауза уже
  прошла — весь её срок регистратору был дан на пуш). Параметр решения —
  факт наличия `CYCLE_PUSH` по строке; никаких таймеров-констант.
- `stendFillRegColumn` — матчинг пропускает закрытые строки
  (`!regNoAnswer`), поэтому поздний/чужой пуш в них уже не падает →
  **съезд столбца вылечен**.
- `stendRenderReport` — ветка `regNoAnswer`: правая колонка пустая, метка
  **«нет ответа»** в колонке «Ошибка». «Общее» стенда растёт, регистратора
  стоит — реальный разрыв виден честно (а не как артефакт).
- **Подтверждено на железе:** на малых скоростях (6, 8, 10 об/мин)
  регистратор не просыпается → «нет ответа», столбцы не едут. Следующий
  шаг проверки — смешанный прогон (часть циклов ловится, часть нет), чтобы
  убедиться, что стыки «нет ответа» ↔ пара не сдвигают колонку.

## 10. Стирание чипа сбрасывает lifetime «Общая» (источник правды — Flash)

**Проблема:** пользователь стёр Flash, но «Общая наработка» (352 ч)
осталась и в панели «Наработка», и в `GET_STATS`. Причина — тот же
«стейл-кэш», что у курсора: `r->totalSec` (lifetime) — переменная в ОЗУ,
читается из Flash (`durationTotal` последней записи) только `LoadTotalSec`
при входе в Service. Стирание Flash ОЗУ не трогало → 352 ч «воскресали» бы
и в новых записях (`durationTotal = r->totalSec`).

**Откуда 352 ч в ОЗУ:** из 100-страничного образа — `LoadTotalSec` при
старте Service положила `durationTotal` последней записи в `r->totalSec`,
дальше цикл прибавлял (`RotationFinishCycle: totalSec += dur`).

**Фикс (обе стороны):**
- Прошивка: `cmdFlashChipEraseHandler` после `EraseChip` зовёт
  `LoadTotalSec(s_reg)` — перечитывает теперь пустой Flash → `totalSec=0`.
  Тот же принцип «без кэша, из Flash», что и у курсора.
- LOGLSMW: по завершении стирания чипа (ветка TagManual в FLASH_STATE)
  сбрасывает снимок `m_lastRegTotS`/`m_preTestRegTotS`/`m_pushCount` и
  **перезапрашивает `GET_STATS`** — панель берёт lifetime прямо с устройства
  (а оно из Flash). Иначе PC-снимок «висел» бы старым (симптом «а здесь
  осталось»).

**Про два разных индикатора наработки (не путать):**
- «Активное время» (`lblUptime`, вкладка «Данные») — из РАЗОБРАННОГО
  архива Flash (`m_arc.valid`); после стирания архив пуст → пусто (верно).
- «Наработка: Общая» (`lblFlashStat`, вкладка «Стенд») — lifetime-счётчик
  прошивки `totalSec` (из `GET_STATS`/`CYCLE_PUSH`).
После прошивки+пересборки стирание → оба показывают 0.

**Поправка к §10 (важно):** первая версия фикса звала `LoadTotalSec` сразу
после `EraseChip` — но стирание чипа **асинхронное** (~30 с, WIP, ПК опрашивает
FLASH_STATE), и `LoadTotalSec` читала ещё НЕ стёртый Flash → старые 352 ч.
Исправлено: в `cmdFlashChipEraseHandler` обнуляем **напрямую**
`s_reg->totalSec = 0` (полное стирание = точно пусто, чтение Flash не нужно и
вредно во время bulk-erase). Курсор не трогаем — `SaveParamOnEEPROM` сам
сканирует.

## 11. «Циклов» — считаем только совпавшие пуши (фикс)

Симптом: «Циклов» завышен вдвое. Причина: `m_pushCount++` стоял **до
матчинга**, поэтому «отброшенные» пуши (тормозные хвосты мотора в паузах,
закрытые «нет ответа» строки) тоже накручивали счёт. Фикс: `m_pushCount++`
перенесён **внутрь ветки совпадения** (`stendFillRegColumn`) — считаются
только реально легшие в цикл пуши. «Общая»/«Сессия» по-прежнему из каждого
пуша. **Подтверждено на железе:** Циклов сошёлся (1, потом реальные числа);
«Общая» накапливается, «Сессия» с нуля на прогон, после «Стоп» держит
результат.

## 12. Панель «Память устройства» ОЖИВЛЕНА (основная тема)

- **Кнопки Память…/Образ…/Журнал…/Очистить** перенесены из группы «Память
  устройства» **под большое окно вывода** `cmpReport` (в `groupCompare`) —
  они наполняют именно его (Память→Регистратор, Образ/Журнал→Стенд). Группа
  «Память устройства» осталась чистым индикатором Flash.
- **Наполнение панели** (`flashBinSearchUpdateUi`): Содержимое
  (Регистратор/Logger/пусто, из `probeFlashImageState` — добавлен вызов при
  входе на «Стенд»), Адрес записи (`стр. K (0xKKKK00)` = первая свободная),
  Занято/Свободно (стр.), Циклов(~)/Фреймов (оценка: РГ — used×10, LOG — used).
- **Адаптивный масштаб бара**: «старшее значение» по ступеням
  {10,50,100,500,1000,5000,10000,50000,65535} чуть выше занятого — малая
  занятость видна как заметная заливка (а не 0% из 65535). В баре — абсолютные
  «N стр.».
- **Штриховка (сеточка)** вместо яркого сплошного чанка: `QProgressBar::chunk`
  = `qlineargradient(spread:repeat …)`, диагональ, два мягких тона — не режет
  глаз.
- **Живое обновление в «Тесте»**: гейты `flashBinSearchStart`/`SendNext`
  ослаблены — запрет только для «Работы» (`m_stendActive && !m_stendNoReg`,
  там регистратор спит); в «Тесте» устройство на связи → поиск идёт. Триггер —
  каждый CYCLE_PUSH перезапускает поиск (guard `m_binSearch.running` от
  наложений). Занятость растёт шагами по странице (~10 циклов = +1 стр.).
  ⚠ На железе с этими правками ещё не гонялось (пользователь пересобирает).
  Если поиск во время теста начнёт мешать трафику — дросселировать (не каждый
  пуш, а раз в N сек).

## 13. Принцип: НИКАКИХ обесточиваний (жёсткое требование пользователя)

**Устройство на БАТАРЕЙКЕ в поле — обесточить физически нельзя.** Значит из
ЛЮБОЙ ситуации/сбоя контроллер обязан **сам** вернуться в рабочую точку,
программно, без щелчков питания. Это конечная цель, не переоткрывать.

**Реализовано (04.07.2026):** `P25Qx_Reset(handle)` в `p25q128.c` — сброс чипа
Reset-Enable(0x66)+Reset(0x99) сначала в QPI (4-line), затем в SPI (1-line),
только команды (не виснет в любом режиме), `HAL_Delay(1)` tRST. Вызывается
ПЕРВЫМ в `P25Qx_Init` (до `ReadSR`). Лечит QPI-залипание после SWD-прошивки
(NRST чип не сбрасывает → раньше «команды не проходят», спасало только
питание). ⚠ На железе ещё НЕ проверено — нужна пересборка+прошивка LOGLSMA.
Симптомы, которые должно закрыть: «нет ответа Flash», пустые Общая/Сессия
(регистратор не отвечал/не пушил), зависание команд.

⚠ **ОТКАЧЕНО (04.07, вечер):** первая реализация СЛОМАЛА Flash — вызов
`P25Qx_Reset` в `P25Qx_Init` оставлял чип в SPI / сбрасывал QE, а pwr.c далее
зовёт `P25Qx_SetQPI`, который QPI не поднимал → «нет ответа Flash», регистратор
молчал (весь правый столбец «нет ответа»). Вызов из `P25Qx_Init` убран
(функция `P25Qx_Reset` оставлена в файле). **Нужна перепрошивка LOGLSMA
откаченной версией — вернёт рабочее состояние.** Переделать QPI-сброс с
корректным восстановлением: после 0x66/0x99 → `P25Qx_SetQuadSpi` (re-enable QE)
→ `P25Qx_SetQPI`, и проверить на железе. Нормальный поток инициализации
(pwr.c): `P25Qx_Init` → `P25Qx_SetQPI`.

**2-я попытка ПРИМЕНЕНА (04.07, вечер):** `P25Qx_Init` теперь =
`P25Qx_Reset()` → `P25Qx_SetQuadSpi()` (вернуть QE) → ready; дальше pwr.c
`P25Qx_SetQPI` поднимает QPI. Недостающий шаг 1-й попытки (SetQuadSpi/QE)
добавлен. **✅ ПОДТВЕРЖДЕНО НА ЖЕЛЕЗЕ (04.07, вечер):** после SWD-прошивки A
чип сам вышел из QPI — «Память устройства» показала 140 стр. (не «нет ответа
Flash»), «● Регистратор» зелёный, lifetime на месте, БЕЗ передёргивания
питания. Самовосстановление работает. Симптом, что чинит: после каждой
SWD-прошивки A чип оставался в QPI → «нет ответа Flash», регистратор молчал.

### 🔑 Диагностическая зацепка (вечер 04.07, из лога)

Зависание регистратора КОРРЕЛИРУЕТ С ВЫСОКОЙ СКОРОСТЬЮ, а не просто «QPI
после прошивки». По логу «Тест» (N старт/стоп, 10..300 об/мин):
- малые скорости (10, 42, 74) — пуши идут (`durS=10c`), циклы совпадают,
  Flash растёт (138→140);
- в 09:21:02 — сплошные `[ТАЙМАУТ] cmd=0x1b/0x11 — нет ответа после повторов`,
  пуши прекратились;
- дальше высокие (300, 268, 236, 203, 171) — регистратор молчит полностью.
Вывод: на высоких об/мин устройство перестаёт обслуживать LTP / виснет.
Кандидаты: автомат/поллинг гироскопа на высокой ODR забивает главный цикл;
тайминг записи во Flash; ВЧ-вибрация шаговика. **Это — реальная цель
самовосстановления, а не только QPI-сброс.** Вся построенная сегодня
диагностика (панель/вывод/Сессия/лог) — инструмент, чтобы это ловить.

**✅ ПРИЧИНА НАЙДЕНА (силой разума, без дебага) — `Poll_Sensor` (Data.c):**
цикл ожидания data-ready БЕЗ таймаута:
`do { LSM6DSO_ACC_Get_DRDY_Status(...) } while(!status);`
Пока DRDY идёт — ок; стоит ему пропасть (сбой датчика/ВЧ-вибрация/рассинхрон
ODR после Wake-Up-детекта) — крутится ВЕЧНО → главный цикл заблокирован →
`ComPoll` не зовётся → вся LTP-связь мертва (ровно симптом: работал, потом
наглухо тишина; зависит от оборотов). **ФИКС:** добавлен таймаут
`HAL_GetTick()−t0 < 500ms` на ожидание DRDY (не пришёл — берём что есть, идём
дальше, устройство остаётся на связи) + страховка `if(len==0) len=2` от
деления на ноль. HAL_GetTick валиден (Poll_Sensor только в бодрых фазах).
**✅ ПОДТВЕРЖДЕНО НА ЖЕЛЕЗЕ (04.07, вечер):** прогон «Тест» дошёл до 268 об/мин
(139/171/203/236/268 — все совпали, дельты ±%<1), НЕ завис, связь живёт.
Зависание на оборотах побеждено. Глубинная причина «почему DRDY пропадает»
(ODR/Wake-Up) — вторично: даже если пропадает, теперь НЕ виснем.

**UI-правки вывода (вечер):** дельты секунд `N секунд` → короткое `N с`
(оба secDelta — живой и офлайн). История циклов панели `> 3` → `> 200`
(держим весь прогон, панель прокручиваемая) + прокрутка к свежему циклу
(moveCursor End) — «должен контролировать весь цикл»; листать весь прогон
удобно после «Стоп».

## 14. Финал панели памяти + «Сессия» без фантомов (вечер 04.07)

- **Панель «Память устройства» — минимальная:** бар (занято, «N стр.», белая
  сеточка `qlineargradient spread:repeat`, светлая полоса ~#dfe3e8) + ОДНА
  строка «Свободно: M стр.». Убраны как дубли: «Адрес записи» (= Занято+1) и
  «Занято» (= число на баре). Значения — колонкой у левого края (align=right
  резался узким окном).
- **Формат вывода жёсткий:** Старт/Стоп со стороны «Стенд» показываются ВСЕГДА
  (были спрятаны при несинхронном RTC регистратора — год<2020; условие с 03.07
  просто раньше не срабатывало, т.к. часы были синхронны). Рег-Старт/Стоп —
  только при синхронном RTC. Длительности регистратора считаются верно даже
  при несинхронных часах (RTC тикает, абсолютное время мусор).
- **«Сессия» = только ОБРАБОТАННЫЕ ответы** (`m_sessRegMatched` += durS в ветке
  совпадения `stendFillRegColumn`; сброс в stendStart; вместо `total_s−снапшот`).
  Нет ответа по циклу → не добавляем → 0. Никаких фантомных времён (прямое
  требование: «если ответа нет — ноль, не выдумываем»). Подтверждено: 3 цикла,
  1-й «нет ответа» → Сессия = 20 с (2 обработанных×10), не 30.
- **«Циклов» в «Наработке»** = завершённые стенд-циклы за сессию (`m_pushCount++`
  в `stendRecordCycle`, не по пушам) + `stendUpdateFlashStat()` там же (без него
  панель не обновлялась). Панель истории — снова **3 цикла** (5 не влезали со
  Старт/Стоп; высота cmpReport 300).
- ⚠ Всё это — сборка W; проверено на экране, выглядит «похоже на правду».

## Решения, которые НЕ переоткрывать

- Тест/Работа = 2 команды: 0x23 (без сна) / 0x1D (со сном); стоп общий 0x22.
- Сон «Работы» = Standby (цель, 280 нА с RTC), Stop2 — средний ярус.
- Оба пина PA0/PC13 = SYS_WKUP (Standby будит только WKUP/RTC/сброс).
- В «Тесте» фронт INT1/WKUP2 ловится опросом флага WUF2, EXTI не заводить.
- Курсор записи Flash — всегда через `flashFindWritePos`, без кэша, без
  передёргивания питания.
- Lifetime «Общая» (`totalSec`) — тоже без кэша: стирание чипа перечитывает
  Flash (`LoadTotalSec` → 0); наработку ВСЕГДА показываем из Flash, не из
  залипшего снимка ни в ОЗУ прошивки, ни на ПК.
- Панель «Стенд» — лок-степ: строка цикла ждёт результат; следующая
  появляется только после заполнения (или «нет ответа» на старте следующего
  цикла). Матчинг пуша по позиции, но закрытые строки пропускаются — привязка
  по времени отвергнута как «в корне неправильная».
- «Старт стенда» есть и на «Мониторинге», и «Тест» на «Стенде» — обе нужны.
- **НИКАКИХ обесточиваний** — контроллер сам выходит из любого состояния;
  QPI-залипание лечим программным сбросом 0x66/0x99, не питанием (§13).
- «Циклов» = только реально совпавшие пуши (не считать тормозные хвосты, §11).
- Стирание чипа: `s_reg->totalSec = 0` НАПРЯМУЮ (не `LoadTotalSec` — стирание
  асинхронное, чтение мимо); ПК по завершении перезапрашивает GET_STATS.
- Кнопки Память/Образ/Журнал/Очистить — под окном вывода `cmpReport`, а не в
  «Память устройства» (та группа — только индикатор Flash, §12).
- Панель «Память устройства»: адаптивный масштаб бара + штриховка + живое
  обновление занятости в «Тесте» (§12).
