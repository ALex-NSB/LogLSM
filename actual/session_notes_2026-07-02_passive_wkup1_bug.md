## Что делали (архитектура режимов A/B — согласована, не переоткрывать)

Цель — PASSIVE (Stop2) для LOGLSMA. Два независимых, не пересекающихся
режима на общем LTP-порту:

- **Режим B (`Service()`, com.c)** — полноценный сеанс для произвольных
  LTP-команд («Тест памяти», «Мониторинг» и т.п.). Вход — **только по
  текущему УРОВНЮ WKUP1** (`wkup1_pin_set()`, потенциал на PA0, кабель
  подключён/нет), без фронта/флага WUF1 — так решено явно пользователем
  («гадать не надо, он всегда по единице, фронт ловить не надо»).
- **Режим A (автомат `SLEEP->CONFIRM->ROTATING`, `RotationStateStep()`,
  com.c, вызывается только из main.c)** — автономное распознавание
  вращения через настоящий Stop2. Запускается **только явной командой**
  `CMD_START_REGISTER` (0x1D, `cmdStartRegister()` в com.c — старый
  простаивавший опкод переиспользован) → `regist.monitoringActive = 1`.
  После запуска работает **независимо от состояния WKUP1** — кабель
  подключат или нет, автомат не прерывается (явное решение
  пользователя, подтверждено через AskUserQuestion).
  `PushCycleRecord()` сама проверяет уровень WKUP1 в момент завершения
  цикла — дублирует данные по LTP, если кабель есть, иначе молча
  ничего не шлёт.
- В main.c верхняя проверка (`if (wkup1_pin_set())`) решает вход в B;
  автомат A — отдельный блок ниже, гейтится `regist.monitoringActive`,
  Stop2-ветка симметрично разбирает оба флага пробуждения (`WUF1`/`WUF2`)
  — **это НЕ то же самое, что решение о входе в Service()**: флаги нужны
  только чтобы физически выйти из Stop2 (пока МК спит, читать уровень
  некому — будит именно событие на пине), а какое действие предпринять
  ПОСЛЕ пробуждения — решает отдельно, по уровню (для WKUP1/Service) или
  по факту WUF2 (для входа в CONFIRM). Обе проверки не мешают друг другу,
  это важное уточнение пользователя, которое я сначала неправильно понял
  как «взаимоисключающие».

Изменённые файлы (все — **Firmware/LOGLSMA**, требуют перепрошивки A):
`Core/Src/main.c`, `Core/Inc/main.h`, `App/Src/com.c`, `App/Inc/com.h`,
`App/Inc/Data.h`. `LOGLSMW` (W) в этой сессии не трогали.

## НАЙДЕННЫЙ БАГ — причина «вообще ничего не работает» (частично исправлено)

После перехода входа в Service() на чистый уровень WKUP1 пользователь
сообщил: ни одна команда не проходит, включая базовые (PING/WHO_AM_I/
SET_DATETIME) — не только Flash. Раскопки:

`git diff -- Firmware/LOGLSMA/Core/Src/gpio.c` (сравнение с последним
коммитом) показал, что в РЕПОЗИТОРИИ (до сегодняшних правок) `gpio.c`
**уже содержал** явные `HAL_GPIO_Init(..., GPIO_MODE_INPUT, GPIO_NOPULL)`
для `WKUP1_Pin` (PA0) И `INT1_Pin` (PC13) — а в текущем рабочем дереве
их нет вообще. То есть где-то раньше (видимо, при регенерации `.ioc`
после назначения PA0/PC13 ролей `SYS_WKUP1`/`SYS_WKUP2` под Stop2 —
CubeMX для `SYS_WKUPx` не генерирует `HAL_GPIO_Init`, см. комментарий в
`main.h`) эти строки **молча выпали** из `gpio.c` при регенерации, и
это осталось незамеченным до сегодняшнего дня — раньше баг маскировался
безусловным входом в Service() (`if (1 || ...)`, задокументировано в
CLAUDE.md как обход диагностики от 22.06).

Следствие: PA0 остался в сбросовом состоянии GPIO (Analog, MODER=11).
У STM32L4 в Analog-режиме цифровой входной триггер (Шмитта) аппаратно
отключён (нулевое потребление) — `HAL_GPIO_ReadPin()` в этом состоянии
не отражает реальный уровень на ноге, читает недостоверно (по факту
почти всегда 0). Когда я убрал резервную проверку по флагу WUF1 и
оставил вход в Service() только по `wkup1_pin_set()` (по прямому
указанию пользователя — само решение верное, не отменять), устройство
перестало видеть «1» на кабеле вообще → в Service() не заходит →
полная тишина на любые команды. Само пробуждение из Stop2 по WKUP1
(`PWR_FLAG_WUF1`) этим не затронуто — у PWR отдельный, не через
GPIO-триггер, тракт детекта на этот вывод, поэтому оно продолжало
работать само по себе (это и создавало обманчивое впечатление, что
проблема специфична для «уровня», а не для чтения пина в принципе).

### Фикс (применён, НЕ подтверждён на железе)

Добавлен явный `HAL_GPIO_Init(GPIOA, {Pin=GPIO_PIN_0, Mode=GPIO_MODE_INPUT,
Pull=GPIO_NOPULL})` — **не в `gpio.c`**, а в `main.c`, `USER CODE BEGIN 2`
(внутри `main()`, сразу после `MX_USART2_UART_Init()`, до настройки
`HAL_PWR_EnableWakeUpPin`). Первая попытка вставить это прямо в `gpio.c`
дала ошибку сборки (`expected declaration specifiers before '.'`) — там
`USER CODE BEGIN 2` расположен ПОСЛЕ закрывающей `}` `MX_GPIO_Init()`
(файловая область видимости, не функция), туда нельзя писать исполняемые
операторы. Перенесено в `main.c`, где `USER CODE BEGIN 2` — легитимно
внутри тела `main()`. `gpio.c` в итоге **не изменён** (откачен обратно,
`git diff` по нему сейчас пустой относительно рабочего дерева этой
сессии, но по-прежнему отличается от исходного коммита на те самые
пропавшие 12 строк — это надо явно раскомментировать выше).

### ⚠️ НЕ ИСПРАВЛЕНО — тот же баг, вероятно, и на PC13 (INT1/WKUP2)

`git diff` показал, что `INT1_Pin` (PC13) **тоже** лишился
`HAL_GPIO_Init` в том же самом выпадении. Я исправил только PA0 —
PC13 остался нетронутым. Код нигде не читает уровень PC13 напрямую через
`HAL_GPIO_ReadPin` (только `__HAL_PWR_GET_FLAG(PWR_FLAG_WUF2)` — флаг, не
уровень), так что функционально WKUP2 может и не пострадать так же, как
WKUP1 пострадал — но это не проверено и не факт. **Рекомендация на
завтра**: на всякий случай добавить симметричный `HAL_GPIO_Init` и для
PC13 (тем же способом, в `main.c`) — дёшево, снимает неизвестность.

### Побочно замечено, не трогали

В `com.c` есть отдельный, не связанный с этой темой код —
`cmdSetAcquisitionData()` (LTP-команда `CMD_SET_ACQUISITION_DATA`)
динамически переключает PC13/`INT1_Pin` в `GPIO_MODE_IT_RISING` (для
потокового чтения IMU по DRDY-прерыванию, легаси, не относится к
Stop2/WKUP2-детекту). Если эта команда когда-нибудь вызывается — она
переконфигурирует PC13 и может сломать детект пробуждения WKUP2 до
следующего сброса МК. Не мешает текущей задаче, но стоит иметь в виду.

## Продолжение (сессия 2, 02.07.2026) — найдена вероятная настоящая причина

Пользователь подтвердил: перепрошивал УЖЕ С PA0-фиксом — связи всё равно
нет («ошибки кода» где-то ещё). Полный осмотр рабочего дерева (по реальным
файлам, не по git-снимку песочницы — тот оказался устаревшим и показывал
ложно обрезанный main.c; main.c на диске цел, 499 строк) нашёл ещё ДВЕ
потери той же регенерации `.ioc`, что съела HAL_GPIO_Init PA0/PC13:

1. **`usart.c`: `huart2.Init.BaudRate` откатился на 115200** (и в
   `LOGLSMA.ioc` `USART2.BaudRate=115200`) — а LOGLSMW/стенд с 22.06.2026
   работают на 921600. `ComInit()` вызывает `MX_USART2_UART_Init()` заново,
   т.е. прошивка слушала порт на 115200, ПК стучался на 921600 → полная
   тишина на ЛЮБУЮ команду при полностью исправной остальной логике.
   **Это объясняет «команды не проходят» целиком, даже с работающим
   PA0-фиксом.** Исправлено: 921600 в `usart.c` + `.ioc`, с предупреждающим
   комментарием у обоих мест.
2. **`usart.c`: USER CODE блоки `USART1_MspInit`/`USART1_MspDeInit`
   (BLE HLK-B40, PA9/PA10) выпали целиком** — `MX_USART1_UART_Init()`
   остался, но без тактирования/GPIO первый же `bleActiv()` (pwr.c,
   вызывается из command.c по команде) уходил бы в Error_Handler.
   К текущему симптому отношения не имеет (BLE при старте не включается),
   мина на будущее. Восстановлено из git HEAD.
3. PC13 (INT1/WKUP2): добавлен симметричный `HAL_GPIO_Init` в `main.c`
   рядом с PA0-фиксом (п.4 плана) — неизвестность снята.

**Откат на `if (1 || ...)` (п.3 плана) НЕ делали** — не понадобился, пока
есть более вероятная причина. Идея «проверить на 115200 без перепрошивки»
**отвергнута пользователем как нерабочая для текущей топологии**:
регистратор подключён через стенд (Nucleo-ретранслятор), а обе линии
стенда жёстко на 921600 — смена скорости в LOGLSMW ломает участок
ПК→стенд, а участок стенд→регистратор (USART3) на 115200 не переключить
вообще. Проверка возможна только при прямом подключении регистратора к
USB-UART мимо стенда — не стали. Решение: сразу пересобрать и перешить
исправленную прошивку (921600); если после этого молчит — п.3
(безусловный Service()) как следующий шаг изоляции.

**Проверка компиляции**: реальный arm-gcc в песочнице недоступен;
правки — самодостаточные сбалансированные блоки (huart1 определён один
раз, extern в usart.h на месте, GPIOC-клок включается в MX_GPIO_Init до
USER CODE 2). Собрать в CubeIDE.
