# Сессия 19 июня 2026 — Формат упаковки данных Регистратор (пересмотр v2)

## Статус: завершено, перенесено в `data_format_spec_v1.md` (раздел «Режим 1 — Регистратор цикла вращения»)

---

## Зачем пересматривали

После закрытия Logger v2 возник вопрос — применить ли к Регистратору ту же
frame-архитектуру (type-byte, NOR-safe rewrite trick 0xF5→0xF4 и т.п.).
Решение: **нет**. У Регистратора принципиально другой поток данных:

- Logger непрерывно льёт сырые сэмплы IMU постранично — отсюда вся борьба за
  байты внутри страницы (T0/T1, E1–E4 поверх резерва сэмпла, type-byte).
- Регистратор сырые сэмплы **не хранит вообще** — они обрабатываются на лету
  (математика отдельным пунктом), и в Flash попадает только один маленький
  итоговый «сэмпл цикла» раз в цикл. Конкурировать за место внутри страницы не
  с чем — задачи Logger здесь просто не существует.

Поэтому Регистратор разбирался от печки, без переноса механизмов Logger.

## Список полей — что сохраняем (зафиксировано)

Базовый костяк (без изменений от исходной версии):

1. timestamp_start
2. timestamp_end
3. duration
4. MAX_RPM (гироскоп)
5. MAX_vibration (акселерометр, ВЧ-составляющая)
6. temperature
7. battery_voltage *(далее пересмотрено — см. ниже)*
8. CRC + флаг

Добавки по итогам сегодняшнего обсуждения:

- **duration_total** — накопительная длительность по всем циклам устройства
  (та же идея, что у накопительного поля СТОП-фрейма Logger v2). Добавлено,
  т.к. позволяет, прочитав последнюю запись на Flash, сразу получить суммарный
  наработанный ресурс — без сканирования истории.
- Промежуточные чекпойнты в середине цикла — **рассмотрены и отклонены**:
  авария в середине цикла продолжает терять накопленные в RAM MAX_vibration/
  MAX_RPM целиком, как и раньше. Решение подтверждено явно.

## Сжатие temperature и battery_voltage (согласовано, уточнено повторно 19.06.2026)

Исходная унификация «все поля по 32 бита» (код проще, экономия незначительна)
была пересмотрена для двух диагностических полей:

- **temperature → uint8, целый °C, со смещением.** Сначала рассматривался int16
  (0.01°C, как в ЗАГОЛОВКЕ Logger v2), но решили, что сотые доли градуса
  избыточны. Промежуточный вариант 0.1°C не даёт экономии: в 1 байт (256
  значений) при шаге 0.1°C влезает только ~25.6°C диапазона — мало для рабочего
  диапазона. Взяли целый градус — но рабочий диапазон уточнён повторно
  (19.06.2026) до **−60…190°C**, несимметричного относительно нуля (горячий
  хвост шире холодного — реальные условия у оси колеса). Симметричный int8
  (−128…127) под это не подходит, поэтому формат — **uint8 со смещением −60**:
  `°C = raw − 60`, raw 0..255 → диапазон −60…195°C (с запасом над требуемыми
  190°C).
- **battery_voltage как число — выброшено целиком.** Причины:
  - замеры напряжения без нагрузки не объективны;
  - в рабочем цикле точное значение никому не нужно;
  - в сервисном режиме напряжение спокойно измеряется напрямую;
  - для разбора причин отказа достаточно знать «опускалось ниже нормы в
    течение цикла» (батарея ещё жива, но на последнем дыхании).

Вместо числового поля — сначала рассматривался 1 бит `low_battery`, но решили
взять **3-битную зону `voltage_zone`** (0..7) в поле `status` — почти бесплатно
(в байте всё равно есть запас) и даёт градацию вместо чистого да/нет:

- диапазон **2.9–3.6В, шаг 0.1В**, с насыщением по краям
  (`≤2.9В → код 0`, `≥3.6В → код 7`);
- подобрано под профиль разряда LS14250 (Li-SOCl₂): почти всю жизнь батареи
  напряжение у верхней границы (код 7 — «всё нормально, деталей не надо»),
  разрешение даётся только нижнему «интересному» хвосту перед истощением;
- в RAM за цикл хранится минимальная зона, увиденная за цикл (худший случай
  перекрывает кратковременные просадки под нагрузкой).

MAX_vibration и MAX_RPM остались float32 — это содержательные измеренные
величины, а не диагностика, сжимать их не обсуждалось.

## Итоговая структура записи (28 байт)

| Поле | Размер | Формат |
|---|---|---|
| timestamp_start | 32 бита | uint32 |
| timestamp_end | 32 бита | uint32 |
| duration | 32 бита | uint32 |
| duration_total | 32 бита | uint32 |
| MAX_vibration | 32 бита | float32 |
| MAX_RPM | 32 бита | float32 |
| temperature | 8 бит | uint8, целый °C, смещение −60 (`°C = raw − 60`, диапазон −60…195) |
| status | 8 бит | uint8 (биты[2:0] = voltage_zone, биты[7:3] резерв) |
| CRC | 16 бит | uint16, `0xFFFF` = не завершена |

**Итого: 6×4 + 1 + 1 + 2 = 28 байт.** (было 30 в исходной версии без
duration_total/status; путь: 30 → 34 (добавили duration_total и
battery_voltage остался float32) → 29 (battery_voltage → 1 бит, temperature →
int16 0.1°C) → 28 (temperature → uint8 целый градус со смещением −60
(диапазон −60…195°C), battery → 3-битная зона).)

## Схема записи — stub + дозапись (без изменений в принципе, обновлены смещения)

1. **Старт цикла:** `Flash[write_ptr] ← { timestamp_start | 0xFF×24 }` (28 байт),
   `stub_addr = write_ptr`, `write_ptr += 28`.
2. **Во время цикла:** MAX_vibration/MAX_RPM/temperature накапливаются в RAM;
   `voltage_zone` — минимум зоны, увиденный за цикл.
3. **Конец цикла (штатно), порядок дозаписи:**
   `timestamp_end → duration → duration_total → MAX_vibration → MAX_RPM →
   temperature → status → CRC` (CRC всегда последним — финальная «печать»).
4. **duration_total пишется рано** (сразу после duration) специально для
   надёжности: при аварии в середине backfill накопительный итог, как правило,
   уже на Flash, даже если вся остальная запись осталась неполной.
5. **Завершение страницы:** после CRC `write_ptr` переходит на следующую
   границу страницы (256 байт); 1 запись = 1 страница, как и раньше.
6. **Источник «текущего» duration_total** (закрывает старый открытый вопрос):
   отдельной ячейки состояния нет. При backfill берём `duration_total` последней
   записи, где это поле физически записано (≠ `0xFFFFFFFF`) — благодаря раннему
   расположению поля это почти всегда просто предыдущая запись, даже неполная по
   CRC. Если такой записи вообще нет (первый цикл устройства) — база 0.

То же решение (читать накопительный итог из последней записи, без отдельной
ячейки состояния) задним числом закрывает аналогичный открытый вопрос и для
Logger v2 (там — из последнего фрейма СТОП).

## Унификация с Logger v2 (согласовано 19.06.2026)

Формат `temperature+status` (2 байта: uint8 со смещением −60 + uint8 статус с
`voltage_zone`) теперь общий для обоих режимов — используется в ЗАГОЛОВКЕ и
ДАННЫЕ+E1 Logger v2 (см. `session_notes_2026-06-19_logger_format.md`). Раньше
Logger хранил температуру и напряжение в двух разных типах фреймов (E1/E2,
по 2 байта каждый); после унификации это один тип (E1) — константа `0xF9`
освобождена. Один код сериализации/разбора на оба режима.
