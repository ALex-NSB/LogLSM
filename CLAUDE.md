## Что это за проект

Автономный инерциальный логгер на базе STM32L433CC. Устанавливается на ось колеса.
Записывает вибрации и вращение в NOR Flash, выгрузка через UART (сервисный кабель) или USB-C (плата расширения B).

---

## Два аппаратных варианта

| | **LOGLSMA + MA00** | **LOGLSMB + MB00** |
|---|---|---|
| Статус | ✅ **Собран, на стенде, отлаживаем** | 📐 Запланирован, не собран |
| IMU | LSM6DSO-MOD (±16g) — WHO_AM_I=**0x6C** | LSM6DSV320X-MOD (±320g) — WHO_AM_I=**0x70** |
| FRAM шина | SPI1 (PA11/PA12/PA15/PB3) | SPI3 (PB4/PB5/PA15/PB3) |
| QUADSPI CLK | PB10 (пин 21) | PA3 (пин 13) |
| QPWR | PA8 (пин 29) | PB10 (пин 21) |
| USB | Нет | PA11/PA12 → USB-C через MB00 |
| Сервисный UART | USART2, PA2/PA3 (XP2) | USART1, PA9/PA10 (XP1+XP2) |

MA00 = модуль расширения A, номер 00 (бывшее название E1 — та же плата).
MB00 = модуль расширения B, номер 00 (USB-C, FRAM, TMP117 на SPI3).

## Протокол связи — LTP

Используем **LTP (LogLSM Transport Protocol)** — эволюция WAKE.

```
Пакет: FEND | ADDR | CMD | FLAGS | SEQ | LEN | PAYLOAD | CRC16

FEND  = 0xC0   (маркер фрейма)
FESC  = 0xDB   (escape)
TFEND = 0xDC
TFESC = 0xDD

CRC16-CCITT: poly=0x1021, init=0xFFFF, no reflect, xor=0x0000
```

**Скорости UART:**

| UART | Скорость | Обоснование |
|---|---|---|
| USART1 → HLK-B40 (BLE) | **115 200 бод** | BLE-эфир ≈ 30–50 KB/s, UART не узкое место; достаточно для графиков и команд |
| USART2 → XP2 (сервисный кабель, регистратор LOGLSMA) | **921 600 бод** | Поднято 22.06.2026 (было 115200, см. ниже) — статический дефолт в прошивке, без живого переключения |
| USART2 (к ПК) / USART3 (к регистратору) на стенде (Nucleo-L476) | **921 600 бод** | Поднято 22.06.2026 после перехода приёма на DMA (было временно снижено до 230400 — см. «DMA-приём на стенде» ниже) |

HLK-B40 поддерживает до 921600 (подтверждено даташитом). Скорость меняется AT-командой.  
Sleep-пины HLK-B40 (PC6/PC7) не разведены на MCU — BLE переводится в off через B_PWON (PB6, p-FET).

**Скорость сервисного UART поднята с 115200 на 921600 (22.06.2026).** Мотивация —
вкладка «Мониторинг» (см. ниже): на высоких об/мин стенда опрос гироскопа/
акселерометра по 115200 не успевал за реальной частотой вращения (видна
пилообразная, а не гладкая картина даже там, где физика гладкая — см.
раздел «Мониторинг» ниже). Решено (обсуждали живое переключение по
команде `SET_BAUD`/0x0B, которая в прошивке уже существует и работает —
`com.c::cmdSetBaud`) **не делать живое переключение**, а поднять статический
дефолт в обеих прошивках и перешить — проще и без гонок по времени на
переключении UART прямо во время передачи (живой вариант для топологии
стенда требовал бы доп. разбора CMD в байтовой ретрансляции `com_interr.c`,
которая сейчас слепая по ADDR, — посчитали лишним риском).
Изменено везде, синхронно (иначе разные звенья перестанут понимать друг
друга — UART не поддерживает автоопределение скорости):
- `Firmware/LOGLSMA/Core/Src/usart.c` (`MX_USART2_UART_Init`) + `LOGLSMA.ioc` (`USART2.BaudRate`) — сервисный UART регистратора.
- `Stend/Stend LOGLSM/Core/Src/main.c` (`MX_USART2_UART_Init`/`MX_USART3_UART_Init`) + `Stend LOGLSM.ioc` — обе линии стенда (к ПК и к регистратору-ретранслятору).
- `SoftWare/LOGLSMW/mainwindow.cpp` — дефолт `cmbBaud` при первом запуске (без сохранённой настройки) теперь 921600.
- `test_ping_stend.bat` — ручной PowerShell-пинг стенда, скорость в скрипте обновлена.

**Важно:** после перешивки обоих устройств они понимают ТОЛЬКО 921600 —
без отдельного обновления всех тестовых скриптов/настроек, ожидающих
115200, связи не будет (UART — фиксированная скорость, не автоопределение).

**Найден и исправлен сопутствующий баг ретрансляции (22.06.2026, всплыл
при проверке 921600, но существовал и на 115200 — просто не был замечен).**
Симптом: прямой одиночный PING на 0x8C через `test_ping_stend.bat` проходил
идеально (ACK байт-в-байт совпадал с ожидаемым), а сканирование из LOGLSMW
(шлёт PING на 0x8D и 0x8C подряд, см. `PortScanner`) — нет, с разным числом
мусорных байт на приёме при каждой попытке (12, 13…), 0 ошибок CRC (мусор не
доходил до разбора пакета). Причина: `PC11` (USART3_RX, линия стенд→
регистратор) была настроена `GPIO_NOPULL` — без подключённого регистратора
вход висел в воздухе и ловил наводку; `com_interr.c` ретранслирует ВСЕ байты
с этой линии на ПК не глядя (см. `HAL_UART_RxCpltCallback`, ветка `huart3`),
включая случайный шум. PING на 0x8D в составе сканирования ненадолго
включает приём на этой линии (ожидая возможный ответ от регистратора) —
оттуда и мусор именно при сканировании, а не при одиночном PING на 0x8C
(тот вообще не трогает relay-логику). Исправлено: `PC11.Pull` →
`GPIO_PULLUP` в `stm32l4xx_hal_msp.c` (+ синхронно в `.ioc`,
`PC11.GPIO_PuPd=GPIO_PULLUP`) — линия в покое держится HIGH, не плавает.

**Второй, более серьёзный баг найден следом (22.06.2026) — потеря самого
ACK на 0x8C, не просто мусор.** После фикса PULLUP сканирование из LOGLSMW
всё равно не находило стенд (то 0, то N байт мусора на разных попытках).
Проверено в обход Qt/LOGLSMW: одиночный PING на 0x8C (`test_ping_stend.bat`)
проходит идеально каждый раз; два PING подряд без паузы (0x8D, затем 0x8C —
именно так делает `PortScanner`, см. `test_ping_dual.ps1`/`.bat`, с байтами
пакетов, посчитанными и сверенными через Python с тест-вектором CRC из
`ltp.c`) — ACK на 0x8C **не приходит вообще**, хотя сам по себе он
гарантированно рабочий. Причина: приём USART2 на стенде — побайтовый, по
прерыванию (`HAL_UART_Receive_IT(..., 1)`), не DMA (в отличие от
регистратора, у которого `HAL_UARTEx_ReceiveToIdle_DMA`). На 921600
(~11 мкс/байт) и тактовой частоте всего 16 МГц (HSI без PLL) обработчик не
успевает обработать релей-ветку первого пакета (PING на 0x8D — чужой адрес,
лишняя логика поиска UART и постановки в кольцевой буфер) и переустановить
приём до прихода первого байта второго пакета — тот пропадает (overrun),
ломая разбор всего второго пакета.

Исправлено **на стороне ПК, не прошивки** (дешевле и безопаснее, чем
переводить приём стенда на DMA): `PortScanner::sendPings()`
(`portscanner.h/.cpp`) теперь шлёт PING на алгоритм-адрес сразу, а PING на
альт-адрес — через `QTimer::singleShot(5, ...)`, не впритык. Сценарий «два
разных пакета без ожидания ответа между ними» возникает только при
сканировании порта — в обычной работе (Мониторинг, Стенд, Тест памяти)
команды и так идут по одной, с ожиданием ответа/таймаута, поэтому пауза
ничего не блокирует в штатной работе. DMA-приём на стенде (по образцу
регистратора) — более капитальное решение, в этот проход не делали,
зафиксировано как возможное улучшение на будущее, если когда-нибудь
понадобится слать на стенд несколько команд впритык без ожидания ответа.

**Третий, итоговый вывод (22.06.2026) — стенд не держит 921600 вообще, ни
в каком сценарии, даже одиночный PING без сканирования.** После фикса
PortScanner (выше) проверка одиночного PING на 0x8C через чистый
PowerShell-скрипт (`test_ping_stend.bat`, без Qt/LOGLSMW) внезапно стала
возвращать 0 байт — притом что физическая плата подтверждённо прошита и
выполняет код (доказано временным heartbeat на busy-counter без
зависимости от HAL_GetTick — диод мигал). Долгий перебор переменных по
одной (PULLUP/NOPULL на PC11, разные физические платы Nucleo, физическое
переподключение USB-кабеля, COM4 vs COM5 в Device Manager, CubeIDE Run vs
Debug vs отдельный STM32CubeProgrammer для прошивки) ничего не дал — при
921600 и при 460800 одиночный PING стабильно не возвращал ничего (на
460800, уже после восстановления PULLUP, — честный 0 байт без мусора, что
само по себе подтвердило, что PULLUP-фикс баг №1 отдельно работает
корректно). Спуск на **230400** — сразу рабочий результат: PING отвечает,
LOGLSMW подключается и идентифицирует устройство, команда `STEND_START`
проходит («старт циклограммы» в логе).

Причина — та же, что и у бага №2 выше (общий корень, не новая находка):
приём/передача USART на стенде побайтовые, по прерыванию
(`HAL_UART_Receive_IT(..., 1)`), не DMA, на тактовой частоте всего 16 МГц
(HSI без PLL — это текущая настройка `SystemClock_Config()`
(`PLL.PLLState=RCC_PLL_NONE`), не предел кристалла: L476 умеет до 80 МГц
через PLL, просто тактирование под это не настроено). На регистраторе (LOGLSMA) аналогичная служба работает на
921600 устойчиво, потому что там `HAL_UARTEx_ReceiveToIdle_DMA` — приём не
зависит от того, успевает ли обработчик прерывания между байтами. На
стенде это ограничение оказалось не только при двух пакетах впритык
(баг №2, уже пофикшен паузой 5 мс на ПК), а фундаментальным даже для одного
изолированного пакета — на 921600 (~1.1 мкс/бит) и 16 МГц обработчик
прерывания просто не успевает отработать `HAL_UART_RxCpltCallback` и
перевзвести приём между байтами одного и того же пакета. 460800 — та же
история (~2.2 мкс/бит всё ещё мало). 230400 (~4.3 мкс/бит) — достаточный
запас.

**Решение: для стенда статический дефолт снижен до 230400** (обе линии —
USART2 к ПК и USART3 к регистратору-через-ретранслятор), отдельно от
регистратора (LOGLSMA), который остаётся на 921600 (DMA-приём, эту
проблему не имеет). Изменено:
- `Stend/Stend LOGLSM/Core/Src/main.c` (`MX_USART2_UART_Init`/`MX_USART3_UART_Init`) — `BaudRate=230400`.
- `Stend LOGLSM.ioc` — `USART2.BaudRate=230400`, `USART3.BaudRate=230400`.
- Временный диагностический heartbeat (busy-counter + мигание LD2 в `main()`) убран — он сослужил свою роль (подтвердил, что ядро выполняет код независимо от UART/таймеров) и больше не нужен; `main.c` снова чистый CubeMX-вид с `ComPoll()` в цикле.
- `PC11.Pull=GPIO_PULLUP` (баг №1 выше) подтверждён и оставлен как есть — не имел отношения к этой находке, но и не мешает.

**DMA-приём на стенде реализован (22.06.2026) — возврат на 921600.**
Вместо того чтобы оставаться на 230400, перевели приём обоих UART стенда
на `HAL_UARTEx_ReceiveToIdle_DMA` по образцу регистратора (`Firmware/LOGLSMA/App/Src/com.c`).
DMA-периферия сама забирает байты в буфер без участия CPU, поэтому скорость
больше не ограничена тем, успевает ли обработчик прерывания между байтами —
корень проблемы (см. «Третий, итоговый вывод» выше) снят полностью, без
необходимости трогать тактовую частоту (PLL).

Сделано через CubeMX/CubeIDE (`.ioc`, GUI): добавлены DMA-запросы
`USART2_RX` (DMA1 Channel 6) и `USART3_RX` (DMA1 Channel 3), режим Circular
(TX отдельно не добавляли — TX остаётся на прерываниях через кольцевой
буфер, он не был источником проблемы). После генерации кода CubeMX:
- `main.c` — добавлен `MX_DMA_Init()` (вызывается перед `MX_USART2_UART_Init()`/`MX_USART3_UART_Init()`), глобальные `hdma_usart2_rx`/`hdma_usart3_rx`.
- `stm32l4xx_hal_msp.c` — линковка DMA в `HAL_UART_MspInit()` для обоих UART; PC11 пересоздан с `GPIO_PULLUP` — фикс бага №1 пережил регенерацию, синхронно с `.ioc`.
- `stm32l4xx_it.c` — добавлены `DMA1_Channel3_IRQHandler`/`DMA1_Channel6_IRQHandler` (вызывают `HAL_DMA_IRQHandler`).

Дальше вручную (`App`-уровень, CubeMX не трогает): `Core/Src/com_interr.c`
переписан — два буфера приёма (`RxBufPc[256]`/`RxBufReg[256]`), запуск через
`HAL_UARTEx_ReceiveToIdle_DMA` в `ComInit()`, рестарт DMA после каждого IDLE
отложен в `ComPoll()` (не из ISR, как и у регистратора). Relay-логика (байт
от ПК с ADDR≠0x8C форвардится на регистратора-линию, байт от регистратора
форвардится на ПК) сохранена 1:1 по смыслу со старой ISR-версией, но теперь
работает по байтам из буфера (`HAL_UARTEx_RxEventCallback`), а не по
аппаратному прерыванию на каждый байт — поэтому больше не требует успевать
переустановить приём между байтами. Динамическое открытие/закрытие приёма на
huart3 под конкретный relay-пакет (было в старой версии) убрано как
ненужное — DMA-приём на huart3 теперь всегда активен независимо.

Статический дефолт стенда вернули на **921600** (`main.c` + `.ioc`,
синхронно с регистратором). 230400 оставлен только как зафиксированный в
истории промежуточный результат диагностики, не текущее значение.

## Стенд (циклограмма испытаний) — статус и план

> Обсуждалось 11.06.2026 (`session_notes_2026-06-11_ltp_implementation.md`,
> раздел «На будущее: технологический блок», помечено «в ТЗ пока не
> вносить» — отсюда и терялось между сессиями). Восстановлено и сведено
> сюда 20.06.2026.

**Железо:** стенд = драйвер шагового двигателя (готовый, современный,
управляется импульсами — 1 импульс = 1 шаг) + сам шаговик (200 шагов/оборот)
+ контроллер **Nucleo-L476** (другая плата, не LOGLSMA — STM32L433 там, а
тут L476), подключённый к ПК через VCP (виртуальный COM ST-Link).
Дробление шага — **DIP-переключатели на самом драйвере**, не команда по
протоколу: для софта это просто константа для расчёта частоты импульсов
под нужную скорость (об/мин ↔ Гц), реально на стенд не передаётся.
Назначение — 2 канала (2 шаговика), не один.

**Топология линии связи (решено 11.06.2026):** VCP Nucleo — единственный
порт к ПК, второй порт LOGLSMW не нужен. Регистратор (LOGLSMA) физически
подключён к Nucleo через второй UART (он же служебный разъём, куда обычно
подключают программатор Nucleo). Nucleo разбирает входящие LTP-пакеты по
ADDR: свои (управление шаговиком) обрабатывает сам, чужие — ретранслирует
на второй UART к регистратору. Схема 1-в-1 повторяет планируемый
BLE-ретранслятор (ТЗ §1.1) — маршрутизация по ADDR пакета LTP.
**Адреса:** Nucleo/стенд = `0x8C`, регистратор (LOGLSMA) = `0x8D` (уже
действующий, см. `LTP_DEV_ADDRESS` в `com.h`), удалённый по BLE = `0x8E`.

**Зачем на одной линии (подтверждено пользователем 11.06.2026):** старый
подход проверки регистратора — сравнение двух раздельных логов (лог
стенда + лог регистратора, разные форматы, ручная сводка) — был крайне
неудобен, хотя в принципе работал. Замысел LOGLSMW — единый журнал
испытания на общей шкале времени ПК: приложение само пишет и циклы стенда,
и данные регистратора в одну таблицу, с автосопоставлением «стенд задал
N об/мин ↔ гироскоп регистратора показал соответствующее значение» — это и
есть вкладка «Стенд» (`tabStend` в `mainwindow.ui`: циклограмма работа/
простой/смена скорости/число циклов, Старт/Стоп, колонки «Стенд
задал»/«Регистратор измерил»/«Расхождение», график `plotStend`, журнал
`tblTestJournal`).

**Был прообраз функционала** — со слов пользователя, ранее существовала
пробная программа управления стендом, отрабатывавшая временные интервалы
запуска шаговика на разной скорости (циклограммы) и вела лог начало/конец
цикла + длительность + скорость. Лог там был **по событиям и относительному
времени физики цикла** (старт вращения на скорости X, потом стоп/отметка),
**не привязанному к реальным часам** — отсюда и трудность сводки с
регистратором, у которого записи на абсолютном Unix-времени (уточнено
20.06.2026). У LOGLSMW эта проблема решается естественно: раз именно ПК
формирует команды стенду, он же ставит реальную метку времени на отправку
каждой команды — общая шкала появляется сама, без необходимости синхронизировать
часы самого стенда отдельно.

Сама программа (или её код) **не найдена
в этом репозитории** — ни папки под Nucleo-L476/`.ioc`-проекта, ни исходников
протокола стенда нигде нет. Пользователь обещал показать эту программу
отдельно.

**Минимальный набор команд Nucleo (уточнено 20.06.2026):** LOGLSMW общается
с 2 устройствами через один порт. Адресовано регистратору (0x8D) — Nucleo
просто ретранслирует пакет на второй UART (служебный разъём) без обработки.
Адресовано самому Nucleo (0x8C, то есть фактически драйверу шагового
двигателя) — Nucleo обрабатывает сам, и набор команд здесь минимальный:
**задать частоту импульсов (= скорость)** или **остановить**. Сама
циклограмма (рандомизация work/pause, выбор скорости в диапазоне, счётчик
циклов — все поля группы «Циклограмма испытания» в `tabStend`) считается и
планируется **на стороне LOGLSMW (ПК)**, а не во прошивке Nucleo — ПК сам
решает, когда отправить очередную команду «частота X» или «стоп» по
сценарию, Nucleo логики циклограммы не содержит.

**Прошивка Nucleo — функционал (уточнено 20.06.2026):** программа,
зашиваемая в Nucleo-L476, должна понимать входящие LTP-пакеты и по ADDR
делать одно из двух: (1) адресовано регистратору (0x8D) — ретранслировать
пакет как есть на второй UART (служебный разъём); (2) адресовано самой
Nucleo (0x8C) — разобрать команду («частота X»/«стоп») и задать нужные
параметры **своему аппаратному таймеру/счётчику** (PWM-канал STM32),
который и генерирует импульсы нужной частоты на вход драйвера шагового
двигателя. То есть генерация импульсов — задача таймера МК, а не
программного цикла.

**Прошивка Nucleo — реализована (21.06.2026), стенд распаян и проверен.**
Проект `Stend/Stend LOGLSM/` (CubeIDE, Makefile, MCU STM32L476RGTx) собирается
без ошибок. `ltp.c`/`ltp.h` скопированы без изменений из
`Firmware/LOGLSMA/App/Src|Inc` (чистый C11, без зависимостей от HAL).
`com_interr.c` реализует приём LTP по USART2 (линия к ПК), побайтовую
маршрутизацию по ADDR (свой `0x8C` → в парсер `ltp_parser_feed`, чужой,
сейчас всегда `0x8D` → ретранслируется как есть на USART3 к регистратору) и
передачу через кольцевые буферы (`ring_buffer.c`) с разруливанием по
`HAL_UART_TxCpltCallback`/`SendUart()`. `StepDriver.c` — TIM1 канал 1 (PWM,
PA8) генерирует импульсы; `StepDriverSetSpeed()` уже делает плавный разгон/
торможение шагами по 200 об/мин каждые 50 мс, если новое значение
отличается от текущего больше чем на 200 — рампа уже есть, отдельно
реализовывать не нужно. Осталось перешить плату (через ST-Link:
STM32CubeIDE Debug/Run As, либо STM32CubeProgrammer — открывает `.elf`
напрямую без конвертации в `.bin`/`.hex`).

**Формат payload CMD_SPEED/CMD_START/CMD_STOP — уже реализован в коде,
закрывает открытый вопрос №1.** `cmdSpeedHandler()`/`StepDriver.c`:
payload `CMD_SPEED` (0x05) = `speed` (uint16, LE) + `coefficient` (uint8) —
и важно: `speed` — это **сразу об/мин**, не Гц. Пересчёт в реальную частоту
импульсов (Гц) на вход драйвера делает сам `SetTimPeriod()` по формуле
`f = speed × 200 × coef / 60` (200 — шагов/оборот при полном шаге,
`coef = 1 << coefficient` — множитель дробления шага). `CMD_START` (0x04) и
`CMD_STOP` (0x06) — без payload. Раз протокол уже говорит в об/мин — вопрос
№2 (единицы в UI) автоматически закрыт тем же выбором: LOGLSMW может
передавать об/мин из UI в payload без пересчёта на своей стороне.

**Сравнение «задал/измерил» — два режима (решено 20.06.2026):** старая
программа сверяла по событиям/постфактум (см. выше — лог стенда и лог
регистратора сводились вручную, без живого мониторинга во время вращения,
по крайней мере по уточнённым данным). Для LOGLSMW решено не ограничиваться
только этим: основной режим — сверка по завершённым записям (журнал стенда
+ запись регистратора из Flash, сведённые по времени ПК), но **дополнительно
стоит добавить живой режим как опцию** — постоянный поллинг гироскопа
регистратора во время самого вращения, для более тщательного теста. Не
обязателен по умолчанию, но не исключается из плана.

**Текущее состояние реализации (обновлено 21.06.2026 — логика циклограммы
написана):** LOGLSMW теперь умеет реально вращать стенд по LTP.

- `DeviceController` (devicecontroller.h/.cpp) научен говорить на ДВА адреса
  одновременно: `m_targetAddr` (регистратор, настраивается в UI, обычно
  0x8D) и `LtpAddr::STEND` (0x8C, константа). Добавлен `enqueueTo(addr, cmd,
  payload, tag)`, `Request` хранит свой `addr`, `transmit()` шлёт по
  `m_current.addr`, `onPacket()` фильтрует и сверяет ADDR/SEQ/CMD так, чтобы
  ответ с одного адреса не мог подтвердить запрос к другому (коды
  STEND_START/SPEED/STOP численно совпадают с FLASH_READ_ID/ERASE/
  PAGE_ERASE регистратора — это нормально, т.к. адреса разные, но в
  `mainwindow.cpp::onResponse()` ответы стенда (`tag == TagStend`) теперь
  разбираются отдельной веткой `stendHandleResponse()` ДО общего
  `switch(cmd)`, чтобы не попасть в обработчик флеш-команд).
- `LtpCmd::STEND_START/STEND_SPEED/STEND_STOP` (0x04/0x05/0x06, как и
  зафиксировано в `com_interr.c`/`StepDriver.c`) добавлены в
  devicecontroller.h. Коэффициент дробления шага для payload STEND_SPEED —
  константа в коде (`kStendMicrostepCoef` в mainwindow.cpp, сейчас 5 → 32
  микрошага), т.к. само дробление задаётся DIP-переключателями на драйвере
  и программно не управляется (см. выше) — но прошивке всё равно нужен этот
  байт для расчёта частоты, отсюда константа вместо поля UI.
- В mainwindow.h/.cpp реализована полная циклограмма work/pause для всех 4

программа (LOGLSMW) одновременно и задаёт режим двигателя, и считывает лог
— разделения на «программу управления» и «программу чтения» нет, как в
старом подходе с двумя раздельными логами. По кнопке «Старт» запускается

«частота Y» без остановки мотора, в конце — «стоп») и фаза простоя (пауза
заданной длительности, без команд). Каждая отправленная команда пишется в
журнал с реальной отметкой времени ПК (см. выше про общую шкалу времени).
Сравнение «задал/измерил» — сведение этого журнала с записями регистратора
(см. два режима выше).

### Вкладка «Стенд» в LOGLSMW — UI и архитектура данных (сессия 21.06.2026)

**UI «Циклограммы испытания» (слева, `groupCyclogram`, `QGridLayout`,
фиксированная ширина) — финальная раскладка.** Время работы / Время
простоя: строки «Минимум»/«Максимум» (полные слова, не «Мин»/«Макс» —
чтобы не путать с минутами времени), по 2 спинбокса (мин+сек, суффиксы
« мин»/« сек» внутри поля). Смен скоростей и Скорость, об/мин — по 2 голых
спинбокса (Мин/Макс) без подписей: порядок «левый ≤ правый» самодостаточен.
Все 12 спинбоксов одного размера (90px, без стрелок —
`QAbstractSpinBox::NoButtons`) — иначе при разном содержимом (число с
префиксом/суффиксом против простого числа) колонка визуально «гуляет».
Режим — 4 радиокнопки: «Случайно ±» / «Только +» / «Только −» /
«N старт/стоп» (последний — отдельный треугольный алгоритм: N шагов вверх
от Мин до Макс, потом N шагов вниз, по кругу до ручного Стоп; остальные
три — смена скорости без остановки мотора в рамках фазы работы). Строка
«Дробление шага» убрана из UI совсем (была нередактируемая статичная «32»,
без смысла — шаг и направление всё равно задаются перемычками на драйвере,
не программно, см. открытый вопрос №3 выше). Чекбокс «Не считывать данные
с регистратора» (`chkStendNoRead`) и кнопки «Старт»/«Стоп» — в одной строке
(`stendButtonsLayout`), чтобы сразу было видно, какой режим использован при
старте. Группа зафиксирована `sizePolicy: Fixed×Maximum` (не растягивается
ни по ширине, ни по высоте сверх содержимого) + `alignment="Qt::AlignTop"`
у обоих элементов `stendTopLayout` — без этого панель растягивалась по
высоте соседней (правой) и центрировалась в строке, открывая пустоту сверху
и снизу.

**Правая панель «задал/измерил» (`groupCompare`/`cmpReport`) — текстовый
лог, не таблица и не график.** Заголовок группы убран, график
(`QCustomPlot plotStend`) и статус-лейбл (`lblStendStatus`) удалены —
активность стенда видна по цвету кнопки «Старт», отдельный индикатор не
нужен. Поле — `QPlainTextEdit name="cmpReport"`, readOnly,
`lineWrapMode=NoWrap` (иначе моноширинная таблица ломается переносом строк
при недостатке ширины — нужен горизонтальный скролл, а не перенос), шрифт
Consolas 10pt (отдельно от общего лог-шрифта 8pt у `logBrief`/`logView` —
иначе на глаз мельче рядом с обычными подписями), `minimumWidth=460`,
`minimumHeight=maximumHeight=480` (фиксированная высота независимо от
заполненности — иначе пустая/короткая панель не совпадала по высоте с
левой колонкой).

Формат записи на цикл (одинаковый и в живой панели, и в будущем файле
журнала):
```
             Стенд        Регистратор
Старт     14:31:00     14:31:00
Стоп      14:31:20     14:31:21
Интервал  00:00:20     00:00:21     +1 секунда
Общее     00:07:05     00:07:06     +1 секунда
Скорость  180          179          −1 об/мин
```
(метка переименована 02.07 из «Общая» в «Общее» — путалась с полем
«Наработка»/«Общее» отдельной панели «Память устройства», см. заметку в
шапке файла.)
Заголовок «Стенд/Регистратор» — один раз сверху, не повторяется в каждой
строке (раньше повторялся словами «стенд»/«рег.» в каждой строке —
признано избыточным). Время — чч:мм:сс, без долей секунды (касается и
Старт/Стоп, и Интервал/Общее — единый формат). Δ — только число со знаком
и полным словом единицы (секунда/секунды/секунд по русским правилам
числительных, об/мин), без отдельного значка «Δ». Δ есть у «Интервал»,
«Общее» и «Скорость» — в этом и смысл сравнения; у «Старт»/«Стоп» Δ не
считается (это абсолютное время, не разница). Блоки циклов разделены
пустой строкой — без неё все строки визуально слипаются. Панель держит
последние 4 цикла (подбирали по факту вместимости панели, было 2→3→4).

**Нижняя секция «Журнал испытания» (`groupTestJournal`/`tblTestJournal`)
убрана из `mainwindow.ui` целиком**, вместе с кнопками «Экспорт отчёта…»/
«Очистить», которые в ней были. Полная история теста не дублируется на
экране (это повторяло бы правую панель) — вместо этого пишется прямо в
файл на диске: при «Старт» файл создаётся, после каждого завершённого
цикла дозаписывается/флешится, чтобы авария/зависание программы не теряло
уже отработанные циклы. Смысл кнопок «Экспорт отчёта…»/«Очистить» (открыть
файл отчёта, начать новый файл) пока никуда не перенесён — отдельная
задача на этапе реализации файловой записи.

**Архитектура заполнения записи — частичная, не атомарная.** Сторона
«Стенд» в строке известна сразу (ПК сам отправил команды и засёк время).
Сторона «Регистратор» — не сразу: либо приходит с небольшой задержкой (на
связи), либо только постфактум при отдельном совмещении (автономный
регистратор). Технически: не редактировать конкретную строку текста в
`QPlainTextEdit` на месте, а держать историю циклов как структуру данных
(список записей с опциональными полями ПК/регистратор) и перерисовывать
видимый текст (`setPlainText`) целиком при каждом изменении.

**Два сценария совмещения с регистратором — оба сводятся к одной операции
«сопоставить запись стенда с записью регистратора по времени», просто
запускаемой в разный момент:**
1. *На связи* — регистратор в сервисном режиме, физически подключён через
   Nucleo (ретранслятор, адрес 0x8D, ничего в прошивке стенда менять не
   нужно — она уже прозрачно ретранслирует чужие пакеты). После каждого
   «Стоп» LOGLSMW сам пытается прочитать журнал регистратора (обычные
   таймаут/ретраи `DeviceController`) и дозаполняет строку почти сразу.
2. *Два разных лога* — регистратор работал автономно от батарейки без
   связи во время теста (или физически отвечает, но другая/несовместимая
   прошивка — поэтому решили не делать автоопределение по принципу «есть
   ответ/нет ответа», а явный чекбокс). Тогда колонка «Регистратор»
   остаётся пустой весь тест, а совмещение — отдельное ручное действие
   позже (даже в другой сессии программы): прочитать архив регистратора
   (тот же разбор, что уже умеет вкладка «Данные» — отдельный механизм
   чтения не нужен) и сопоставить с уже сохранённым файлом журнала стенда
   по времени. Кнопка такого совмещения — на вкладке «Стенд», не на
   «Данные» (у обычного пользователя «Данные» нет и не будет дампа стенда
   для сравнения, его результат по сути и есть правая колонка «Регистратор»).
Чекбокс `chkStendNoRead` явно выключает попытку чтения после каждого
«Стоп» — сценарий 2 выбирается вручную, не автоопределением.

**Три типа данных, не два:** Стенд / Регистратор (режим 1, описано выше) /
Logger (режим 2, потоковая запись по 256-байтным фреймам). Всё совмещение,
спроектированное в этом разделе, — только про Регистратор. Для
Logger-режима устройства стенд во время теста ведёт только свой собственный
журнал, без попытки опроса вообще — Logger не структурирован по циклам
вращения, опрашивать после каждого «Стоп» нечего. Проверка временной
точности для Logger возможна только полностью постфактум: прочитать дамп
Logger и журнал стенда раздельно, затем сопоставить (по сути — найти в
потоке сырых отсчётов IMU моменты начала/конца вращения и сверить с тем,
что скомандовал стенд). **Алгоритм поиска границ цикла в сыром потоке не
спроектирован — отдельная задача на будущее.**

**«Симуляция» (`chkSimulation`, верхняя панель подключения, рядом с
индикатором «● Регистратор») — общий сервисный флажок, не привязан только
к стенду.** Виден только в режиме «Сервис» (`setServiceMode`). При
включении заполняет `cmpReport` тестовыми данными в финальном формате —
чтобы оценивать вёрстку без подключённого железа. **Важно (уточнено
21.06.2026): это чисто визуальная заглушка, не имитация работы устройства
или процесса испытания** — задача только показать, как нынешний интерфейс
будет выглядеть с данными, никакой более точной симуляции (поведения
прибора, протокола, циклограммы и т.п.) не требуется и не планируется.
Это узкая черновая заготовка под одну конкретную вкладку, не полноценный
режим демонстрации программы без устройства целиком (тот более крупный
замысел — см. «Идеи
на будущее» ниже, отдельная нерешённая задача).

### Алгоритм циклограммы и совмещения журналов (сессия 21.06.2026)

**Построение ступенек скорости (решено).** N (количество ступенек) берётся
из «Смен скоростей» Мин/Макс (для режимов «Случайно ±»/«Только +»/«Только
−») или напрямую равно количеству уровней обхода в «N старт/стоп». Сами N
ступенек строятся от минимальной до максимальной скорости **включительно**:
первая ступенька = Мин, последняя = Макс, шаг = (Макс−Мин)/(N−1) (при N=1 —
одно значение, Мин=Макс). Длительность фазы «Работа» D берётся случайно из
Мин/Макс «Время работы», делится на N — это и есть время одной ступеньки;
по истечении этого времени берётся следующая ступенька.

**Режимы выбора следующей ступеньки (решено):**
- «Случайно ±» — случайный выбор из тех же N готовых ступенек (с повторами,
  это нормально, не баг — так ступеньки распределены равномернее, чем при
  выборе произвольного числа в диапазоне).
- «Только +» — последовательно по возрастанию через все N ступенек.
- «Только −» — последовательно по убыванию через все N ступенек.

**«N старт/стоп» — назначение и механика (важное уточнение 21.06.2026):**
это не сравнение точности времени, а **калибровка порога пробуждения
регистратора**. Стенд проходит ступеньки от Мин к Макс (та же формула
построения ступенек), и на **каждой** ступеньке делает полный старт/стоп
(а не смену скорости без остановки, как в трёх режимах выше), проверяя,
отозвался регистратор или нет. Не отозвался на скорости 5 — нормально,
идём на следующую ступеньку (6, 7…); как только отозвался — это и есть
минимальная скорость пробуждения регистратора, можно фиксировать и
переходить к оценке. Длительность ступеньки в этом режиме — та же логика
Мин/Макс «Время работы»/«Время простоя», отдельного поля не нужно (если
нужно быстро — просто ставится маленькое значение там же). Лог — тот же
формат, что и в остальных режимах, колонка «Регистратор» у нижних ступенек
закономерно пустая, пока порог не пройден. Применяется редко, разовая
калибровка — для него **не нужна** аккуратная долговременная логика
совмещения журналов (см. ниже), это не основной сценарий использования
стенда.

**Основной сценарий использования (уточнено 21.06.2026):** длительные
прогоны на «Случайно ±»/«Только +»/«Только −» — постановка на несколько
дней, на неделю. Чем дольше прогон, тем больше может «убежать» дрейф часов
между ПК/стендом и внутренними часами регистратора — отсюда и важность
именно поля «Общая» (накопленная длительность) и её Δ, а не только Δ
отдельного интервала.

**Совмещение записи стенда с записью регистратора по времени (решено,
заменяет более раннюю идею «допуск ±N секунд»):** не допуск и не поиск
ближайшего соседа для каждой записи отдельно — достаточно найти **одну
точку совмещения в начале** (первая реально совпадающая пара), а дальше
идти по обоим логам параллельно по порядку (запись N стенда ↔ запись N
регистратора со сдвигом, найденным в начале), без повторного поиска на
каждом шаге. При необходимости (если сильно разойдётся) можно будет
сделать повторную точку совмещения где-то дальше — вручную, отдельная
задача, не автоматика.

**Пропуски записей у регистратора — известный, но редкий случай.** В
реальной практике бывали случаи, когда регистратор не записывал какой-то
интервал вовсе (пропуск). Раньше при ручном сведении это означало вставку/
вырезание строки — муторно, но решили: раз это редкость, а главный интерес
при длительном прогоне — агрегированная «Общая» Δ по всему тесту, а не
идеальное совпадение каждой отдельной строки, отдельную автоматическую
логику обнаружения пропуска **специально не строим**. Совпадение строк
по отдельности важно скорее как диагностика (искать, в какой момент начал
копиться разбег, когда что-то пошло не так) — для уже отлаженного,
проверенного устройства это не критично.

**Формат файла журнала на диске (решено, закрывает последний открытый
вопрос):** тот же читаемый текстовый блочный формат, что и в `cmpReport`
(не CSV/таблица) — рендерим туда то же самое. Обоснование: совпадение
строк нужно прежде всего для ручного разбора глазами (искать место
разбега), для этого читаемый текст удобнее таблицы; машинный анализ (если
когда-то понадобится) к формату файла не привязан. **Это решение — только
для Регистратора.** Для Logger-режима (см. «Три типа данных» выше) объём
данных принципиально другой («куча данных», которые потом нужно будет
обрабатывать программно, не просматривать глазами построчно) — там
**решено (21.06.2026): CSV**, не читаемый текстовый блок (минимум кода для
записи из Qt через `QTextStream`, открывается в Excel/Python для анализа).
Точная раскладка столбцов CSV **не выбрана** — естественно откладывается
вместе с самим алгоритмом поиска границ цикла (см. выше): структуру
столбцов разумно проектировать вместе с алгоритмом, а не раньше него.

## Firmware — правила работы с кодом

- **Весь пользовательский код** — только в `App/Src/` и `App/Inc/`
- `Core/` — генерируется CubeMX, не редактировать вручную

## Режимы работы

| Режим | Источник питания | Активность |
|---|---|---|
| PASSIVE | Батарея LS14250 (3.6В) | Глубокий сон, IMU low-power. **Цель — Standby 280 нА с RTC** (см. «Сон» ниже) |
| WORK | Батарея | Сбор данных, запись в Flash |
| SERVICE | Внешнее (+VEX / +5VU) | UART/USB активен, все команды доступны |

Переход PASSIVE→SERVICE: WKUP1 (PA0) — детект внешнего питания.
Переход PASSIVE→WORK: WKUP2 (PC13) — INT1 от IMU (движение).

### ⚠️ Сон в «Работе»: Standby, НЕ Stop2 (не путать — согласовано, фиксировано)

Глубокий сон рабочего цикла — **STANDBY 280 нА с RTC**, а НЕ Stop2. Stop2
(1.28 мкА) — только средний ярус для коротких внутрицикловых пауз. Двухъярусно:

- **Долгий простой** (большой лаг бездействия) → **Standby 280 нА** (с RTC).
  Выход из Standby = **сброс МК** (ОЗУ теряется — заложено: stub во Flash +
  дозапись, теряется максимум 1 незакрытый цикл); восстановление —
  backup-регистры + Flash-stub (перенос `reset.c`-механики из rp_device —
  TODO). Из Standby будит **только WKUP-пин / RTC / сброс** (EXTI не работает)
  — поэтому PA0/PC13 в `.ioc` заведены как **SYS_WKUP1/SYS_WKUP2**, это
  единственно верно, EXTI на них не заводить.
- **Короткие паузы/перепроверки внутри рабочего эпизода** → Stop2 (контекст
  жив, ОЗУ сохраняется).

**Текущая прошивка = только Stop2 (средний ярус).** Standby-ярус (вход по
таймауту бездействия, восстановление по backup/stub) — ещё не реализован
(TODO). Целевое значение источника цитируется по даташиту: 280 нА Standby с
RTC против 1.0/1.28 мкА Stop2 — экономия существенная, поэтому цель именно
Standby.

**Тест vs Работа (два вида, две команды — не путать):**

- **Работа** (`CMD_START_REGISTER` 0x1D) — рабочая программа СО сном: автомат
  SLEEP→CONFIRM→ROTATING, в SLEEP уходит в сон (цель Standby, сейчас Stop2),
  связь с ПК на время сна теряется, наружу — только `CMD_CYCLE_PUSH`.
- **Тест** (`CMD_START_TEST` 0x23, новая) — та же рабочая программа БЕЗ сна:
  контроллер всё время на связи, в SLEEP-фазе не спит, а бодро крутится с
  `ComPoll()` и опросом флага `WUF2` (тот же фронт INT1/WKUP2, что будит из
  сна в «Работе», но здесь ловится флагом на ходу — видно, что прерывание
  пришло). Всё остальное общее с «Работой»: детект → CONFIRM → ROTATING →
  анализ цикла → запись во Flash → пуш. Стоп для обоих — `CMD_STOP_REGISTER`
  (0x22).

**WKUP2 (PC13) жёстко разведён только на INT1 LSM6DSO (подтверждено
22.06.2026) — другого назначения у этого пина нет.** Это важно для отладки
на стенде с тумблерами VDD/WAKE (см. ниже): тумблер «WAKE» не может
управлять переходом в SERVICE, даже если кажется логичным по названию —
SERVICE зависит только от WKUP1 (PA0), а WAKE на стенде, скорее всего,
относится к WKUP2/имитации движения, либо вообще к другой цепи.

**Загадка 22.06 «PA0 не видит HIGH ни при одной комбинации тумблеров» —
разгадана и закрыта 02.07.2026** (см.
`session_notes_2026-07-02_passive_wkup1_bug.md`): дело было не в цепи
платы, а в том, что `HAL_GPIO_Init` для PA0 молча выпал из `gpio.c` при
регенерации `.ioc` — пин оставался в сбросовом Analog-режиме, где у
STM32L4 входной триггер Шмитта аппаратно отключён и `HAL_GPIO_ReadPin`
недостоверен (почти всегда 0). Пробуждение из Stop2 по WKUP1 при этом
работало (у PWR свой тракт детекта, не через GPIO-триггер) — это и
запутывало. Фикс: явный `HAL_GPIO_Init` (Input/NOPULL) для PA0 И PC13 в
`main.c`, `USER CODE BEGIN 2` (в `gpio.c` нельзя — там USER CODE секция
вне тела функции). Подтверждено на железе: тумблер питания реально
управляет входом в Service().

**Обход `if (1 || ...)` снят (02.07.2026).** Архитектура входа —
финальная, согласована, не переоткрывать:
- **Режим B (SERVICE)** — вход ТОЛЬКО по текущему УРОВНЮ WKUP1
  (`wkup1_pin_set()`, кабель/внешнее питание есть = сидим в `Service()`),
  без фронта/флага WUF1.
- **Режим A (WORK, автомат SLEEP→CONFIRM→ROTATING,
  `RotationStateStep()`/com.c, вызывается только из main.c)** — реальный
  Stop2; запускается ТОЛЬКО командой `CMD_START_REGISTER` (0x1D) →
  `regist.monitoringActive=1`; после запуска от УРОВНЯ WKUP1 не зависит.
  `PushCycleRecord()` в конце цикла сама смотрит уровень WKUP1: кабель
  есть — дублирует запись по LTP (CMD_CYCLE_PUSH), нет — молчит.
- **Гейт входа в Service (03.07.2026, найдено при первой проверке
  стенда):** верхняя проверка main.c — `if (!monitoringActive &&
  wkup1_pin_set())`. Без гейта запущенный автомат при подключённом кабеле
  (на стенде — всегда, через Nucleo) немедленно затягивался обратно в
  Service() и не делал ни одного шага — вкладка «Стенд» не получала ни
  одного CMD_CYCLE_PUSH («вкладка перестала работать» после перестройки
  A/B 02.07).
- **Остановка режима A (03.07.2026, согласовано):** основной путь —
  `CMD_STOP_REGISTER` (0x22, `cmdStopRegister()`/com.c): в бодрых фазах
  автомата (CONFIRM/ROTATING) main.c попутно зовёт `ComPoll()` (только
  при кабеле) — команда доходит, идущий цикл закрывается штатно
  (`RotationFinishCycle()` — общий помощник с дебаунс-веткой), затем по
  верхней проверке — Service(). Дополнительный путь — ФРОНТ WKUP1 во
  время Stop2 (тумблер на линии, если есть в конкретной сборке стенда —
  фишка, не основной механизм; подключение кабеля к спящему автономному
  устройству даёт тот же фронт → выход в Service, это осмысленно). В
  SLEEP (Stop2) LTP недостижим по определению: команды в паузах теста
  таймаутят — штатно, не баг.
- Флаги WUF1/WUF2 в Stop2-ветке разбираются оба, симметрично — это
  механизм ВЫХОДА из Stop2 (пока МК спит, уровень читать некому), не
  решение о входе в Service(); решение — отдельно, по уровню.
- **Стендовый сценарий (LOGLSMW, 03.07.2026):** «Старт» циклограммы шлёт
  0x1D ПЕРВЫМ (до команд мотору — автомат должен уже ждать вращение),
  «Стоп» — 0x22 сразу после STEND_STOP (мотор тормозит по рампе →
  регистратор ещё в ROTATING и слышит LTP). Во время теста LOGLSMW НЕ
  опрашивает 0x8D (гейты по `m_stendActive`: опрос часов/температур
  `m_devClockTimer` — добавлен 03.07, двоичный поиск Flash — был с
  02.07) — связь только входящими CYCLE_PUSH. Таймаут 0x22 (стоп нажат
  в паузе — регистратор спит) — подсказка в журнале: тумблер/питание,
  либо повторный краткий прогон.
- ⚠️ Весь стендовый сценарий 0x1D/0x22 и Stop2 (ток, пробуждение по
  WKUP2, калибровка порога Wake-Up датчика) на железе после правок 03.07
  ещё не проверялись — проверка на стенде в работе.

## Управление питанием периферии (вариант A)

| GPIO | Label | ON | OFF | Что управляет |
|---|---|---|---|---|
| PA8 | QPWR | Output HIGH | **Analog (Hi-Z)** | Flash P25Q128H |
| PB4 | T_PWR | Output HIGH | **Analog (Hi-Z)** | TMP117 |
| PB5 | M_PWR | Output HIGH | **Analog (Hi-Z)** | FRAM |
| PB6 | B_PWON | Output LOW | **Analog (Hi-Z)** или Output HIGH | BLE (BSS215P через P-канальный транзистор) |

**⚠️ OFF = Analog (Hi-Z), не Output-LOW.**  
Output-LOW — активный сток: конденсаторы периферии разряжаются через MCU-вывод.  
Analog — вывод Hi-Z, нода питания держится внешними резисторами без участия MCU.

B_PWON: делитель R1/R2 на VDD + P-канальный управляющий транзистор перед затвором BSS215P.  
- MCU LOW → P-канальный транзистор открыт → затвор BSS215P притянут к GND → BSS215P ON → BLE питается  
- MCU HIGH/Hi-Z → транзистор закрыт → R1 держит затвор BSS215P у VDD → BSS215P OFF → BLE обесточен  
Для B_PWON оба OFF-варианта приемлемы: Hi-Z и HIGH дают один результат.

При старте всё обесточено. Включать только нужное для текущего режима.

## Организация Flash P25Q128H

- 0x000000–0x0000FF: заголовок (версия, режим, указатель записи, флаги)
- 0x000100+: записи лога
- При заполнении запись прекращается, старые данные не перезаписываются
- Стирание только по команде из SERVICE режима

**Режим 1 (Регистратор):** запись 24 байта за цикл вращения, до 10 записей
на страницу Flash (пересмотрено 20.06.2026 — было 1 запись = 1 страница)  
**Режим 2 (Logger):** потоковая запись фреймов по 256 байт (1 фрейм = 1
страница), внутри — сэмплы Ax/Ay/Az/Gx/Gy/Gz по 12 байт  
Спека форматов: `actual/data_format_spec_v1.md`

**`SaveParamOnEEPROM` реально пишет во Flash (реализовано 02.07.2026)** —
раньше была заглушка (`return HAL_OK` без действий, данные никогда не
попадали на чип). Раскладка записи (24 байта): tsStart(u32) | duration(u32)
| durationTotal(u32) | maxVibro(float, пока всегда 0.0 — акселерометр не
подключён к подсчёту) | maxRpm(float) | reserved(2) | CRC16-CCITT(2).
Курсор записи ищется линейным сканом страниц при первом обращении
(`flashFindWritePos`, читает первые 4 байта каждой страницы: 0xFFFFFFFF =
пусто) и кэшируется до перезагрузки МК. `LoadTotalSec` восстанавливает
lifetime `totalSec` из последней записи с проверкой CRC (откат на 0 при
несовпадении — старые записи без CRC или повреждение).

**Баг FLASH_READ (0x07) «не отвечает» — найден и исправлен (02.07.2026,
поздний вечер).** Долго казалось багом QSPI-драйвера/dummy-циклов Fast Read
(перебирались 10/8/4 — ни один не помог), пока диагностика сырыми LTP-
байтами напрямую по COM-порту (в обход LOGLSMW) не показала: ответ
корректен для size вплоть до 240, а с size≈250+ систематически обрывается
(приходит только «хвост», пропорционально размеру). LOGLSMW всегда
запрашивает целую страницу (256 байт) — отсюда стабильный «нет ответа»,
маскировавшийся под баг чтения Flash. **Настоящая причина**: `sendPacket`/
`sendError` (`com.c`) слали весь ответ одним блокирующим
`HAL_UART_Transmit()`; на 921600 бод без аппаратного flow control
(`HwFlowCtl=NONE`) внутренний буфер USB-UART моста не успевает сливать
данные по USB при непрерывном куске длиннее ~250 байт и роняет середину
потока. **Исправлено**: новая `UartTransmitChunked()` шлёт ответ кусками по
64 байта с паузой `HAL_Delay(2)` между ними — протокол LTP не менялся,
правки на стороне LOGLSMW не понадобилось. Подтверждено на живом железе
(«Тест памяти» → «Чтение» реально читает страницы). dummy-циклы Fast Read
в итоге оставлены на исходном значении 10 (QPI-режим, `p25q128.c`) —
подтверждённо рабочее значение (сверено с `rp_device` и историческим
тестированием записи/чтения на том же чипе), к самому багу отношения не
имели. Подробности перебора и диагностики —
`actual/session_notes_2026-07-02_flash_and_reg_column.md`.

## LOGLSMW — соглашения UI (`SoftWare/LOGLSMW/`)

- **Пустое/неизвестное значение в индикаторах — пробел, не прочерк.** Везде,
  где QLabel показывает «факт»/индикатор без значения (нет связи, нет
  данных, образ не загружен) — текст-плейсхолдер `" "` (пробел), **не**
  `"—"` (решение 20.06.2026). Касается любых новых индикаторов на вкладках
  LOGLSMW.
- **«Факт»-ячейки (индикаторы)** — это `QLabel` с QSS-стилем (рамка
  `border`, скругление `border-radius`, серый фон `background: #F5F4F0`,
  `padding`) — список селекторов в `mainwindow.cpp`,
  `QPushButton::setStyleSheet` ближе к концу `applyStyles()`/настройки
  стилей. Любой новый «факт»-индикатор должен попасть в этот же список
  селекторов, иначе будет выглядеть как голый текст без рамки.
- В сетке параметров (`memParamsGrid`, вкладка «Тест памяти») каждая строка
  — 3 ячейки: подпись | бокс | бокс (даже если у строки нет настоящего
  «Задать» — тогда левый бокс — статичный пробел, а не растянутая на оба
  столбца ячейка).
